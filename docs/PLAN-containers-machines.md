## Rules for every brief

- Read root `CLAUDE.md`, the scoped `CLAUDE.md` of the area, the latest `docs/DEVLOG.md` entry, this plan's "Notes from implementation" and the ADRs named in the brief. Version facts live only in `packages/targets`; engine-mod uses Mojang names, Java 25, Fabric events over Mixins (no Mixin is planned in this batch); a 26.3/26.4 difference goes behind a seam in `engine-mod/src/mc/<mc>/` (every version implements every seam). None is expected: every member the batch uses is "same" in the fact table; the members of F7, F17 and F18 stay untouched.
- **Worktrees.** Each executor works in its own git worktree in the scratchpad (`<scratchpad>/wt-B<nnn>`, from the commit the orchestrator names), builds and tests there (parallel Gradle builds in one checkout collide), commits on its own branch, does not push and does not merge. Commits carry no `Co-Authored-By`, `Claude-Session` or other credit lines and are authored as the user (HANDOFF).
- **Stubs first.** Every new GameTest and parity class of the batch is registered in Wave 0 (B309) as an empty class with its entry point, so no later brief edits `engine-mod/src/gametest/resources/fabric.mod.json` or `engine-mod/parity/src/main/resources/fabric.mod.json`.
- **One owner per shared file per wave.** Parallel briefs in one wave never touch the same file; ownership is listed per brief. A brief that needs a file owned by another brief of the same wave stops and reports. Lines that only register something (a plugin's `index.ts` export list) belong to the brief that owns the file in that wave.
- **Notes.** Each executor ends its report with "Notes for the plan": new facts, names, signatures, seams and what a later brief must change, with its brief number. The orchestrator appends them to "Notes from implementation" below when it merges the brief; executors do not edit this file. Each executor appends one DEVLOG entry in its commit (the orchestrator resolves append conflicts at merge).
- A format change moves the mcdoc, the corpus (`packages/schemas/mcdoc/msm/conformance/definition/`, new files prefixed `container-`, `machine-` and `machine-recipe-`), the runtime Codecs and the generator together across ordered waves; each brief keeps its own package green. Run `node tools/build-msm-mcdoc/index.ts --check` after any mcdoc change.
- Exit criteria always include, for the touched packages: `pnpm lint`, `pnpm typecheck` and the package tests; for engine-mod `JAVA_HOME=/root/jdk/jdk-25.0.5+8 ./gradlew build` (26.3), `./gradlew build -Pmc=26.4` and `./gradlew build -PwithoutGeckolib` (JUnit and the GameTests run in each). App and library briefs also run `pnpm build` and `node tools/check-size/index.ts` and report `app.asar` (stop and report if it passes 31.8 MB: B329 then runs first). A runtime component without a GameTest is refused at review; a parity-visible behaviour without a parity test is refused at B325's review.
- Executors: Opus (`claude-opus-5-5`) at medium effort; Sonnet (`claude-sonnet-5-5`) for B309, B322, B326 and B327. A stuck brief is rerun on Opus at high effort.

## Vanilla pack safety (ADR 0066)

- Container and machine blocks and their items are mod-only ids already: recipes, loot tables and advancements naming them are left out of vanilla data packs, and tag entries naming them become `required: false`, by the existing rule.
- Machine recipes name the machine's id in `type` (ADR 0075 D2), which is a mod-only block id, so they are left out even when every item in them is vanilla. B313 proves it with a test and, if the generic scan skips `type`, extends the rule with a `recipe_serializer` registry of mod-only ids.
- The keep-contents loot preset copies components from the block entity of a mod-only block; it is left out with the block's other loot.
- A machine that takes vanilla cooking recipes (`minecraft:smelting` and others) needs no recipe of its own; vanilla recipes written by the project for vanilla items stay in the vanilla pack.
- Nothing in the `msm/` definitions reaches a vanilla pack. The CI library vanilla server check covers the new starters and examples on both targets (B320).
