## Rules for every brief

- Read root `CLAUDE.md`, the scoped `CLAUDE.md` of the area, the latest `docs/DEVLOG.md` entry, this plan's "Notes from implementation" and the ADRs named in the brief. Version facts live only in `packages/targets`; engine-mod uses Mojang names, Java 25, Fabric events over Mixins (no Mixin is planned in this batch); a 26.3/26.4 difference goes behind a seam in `engine-mod/src/mc/<mc>/` (every version implements every seam). None is expected: every member the batch uses is "same" in the fact table; the members of F7, F8 and F9 stay untouched (never `PoiTypes`, `PoiManager`, `PoiHelper`, `PortalForcer`, `ServerLevel.getPortalForcer`, `PortalShape.findAnyShape` or `findEmptyPortalShape`).
- **Clean room.** Vanilla classes are read with `javap` for their rules and signatures; no vanilla method body is copied or transcribed. The frame detector, the exit search and the exit builder are written from ADR 0077's rules.
- **Worktrees.** Each executor works in its own git worktree in the scratchpad (`<scratchpad>/wt-B<nnn>`, from the commit the orchestrator names), builds and tests there (parallel Gradle builds in one checkout collide), commits on its own branch, does not push and does not merge. Commits carry no `Co-Authored-By`, `Claude-Session` or other credit lines and are authored as the user (HANDOFF).
- **Stubs first.** Every new GameTest and parity class of the batch is registered in Wave 0 (B330) as an empty class, so no later brief edits `engine-mod/src/gametest/resources/fabric.mod.json` or `engine-mod/parity/src/main/resources/fabric.mod.json`.
- **One owner per shared file per wave.** Parallel briefs in one wave never touch the same file; ownership is listed per brief. A brief that needs a file owned by another brief of the same wave stops and reports. Registration lines (a plugin's `index.ts` list, `MsmRuntime` initialiser calls) belong to the brief that owns the file in that wave.
- **Notes.** Each executor ends its report with "Notes for the plan": new facts, names, signatures and what a later brief must change, with its brief number. The orchestrator appends them to "Notes from implementation" below when it merges the brief; executors do not edit this file. Each executor appends one DEVLOG entry in its commit (the orchestrator resolves append conflicts at merge).
- A format change moves the mcdoc, the corpus (`packages/schemas/mcdoc/msm/conformance/definition/`, new files prefixed `portal-` and `action-light-portal-`), the runtime Codecs and the generator together across ordered waves; each brief keeps its own package green. Run `node tools/build-msm-mcdoc/index.ts --check` after any mcdoc change. Until B334 lands, `ConformanceCorpusTest`'s `PENDING` list skips the new prefixes (B331 adds them, B334 removes them).
- Exit criteria always include, for the touched packages: `pnpm lint`, `pnpm typecheck` and the package tests; for engine-mod `JAVA_HOME=/root/jdk/jdk-25.0.5+8 ./gradlew build` (26.3), `./gradlew build -Pmc=26.4` and `./gradlew build -PwithoutGeckolib` (JUnit and the GameTests run in each). App and library briefs also run `pnpm build` and `node tools/check-size/index.ts` and report `app.asar` (stop and report if it passes 31.8 MB: the reserve brief B329 then runs first). A runtime behaviour without a GameTest is refused at review; a parity-visible behaviour without a parity test is refused at B343's review. No brief adds a dependency (no lockfile change in this batch).
- Executors: Opus (`claude-opus-5-5`) at medium effort; Sonnet (`claude-sonnet-5-5`) for B330, B340 and B344. A stuck brief is rerun on Opus at high effort.

## Vanilla pack safety (ADR 0066)

- No rule change. The portal block (and a project frame block or key item) is a mod-only id, so: the `#minecraft:portals` tag entry becomes `{ "id": ..., "required": false }` in vanilla data packs (ADR 0066 D4); loot tables, recipes and advancements naming the frame block or key are left out with `export.mod-only-reference` (D3); a function naming the portal block (such as a `setblock`) is kept with `export.mod-only-function` (D5). B335 proves each with a test.
- A portal cannot exist in a vanilla pack at all (a block registry entry; limit P1). The `portal` definition, the `light_portal` action and the `on_travel` event are `msm/` files that never reach a vanilla pack.
- The dimension the flows write is vanilla data (vanilla dimension type, vanilla noise settings or flat layers of vanilla blocks) and stays in the vanilla pack; the Portal flow also writes the Dimension flow's travel function, so the vanilla pack keeps a way in. A flow must never use the project frame block in a flat layer or a feature: that would leave the whole dimension out (ADR 0066's dimension row). B338's tests check this.
- The CI library vanilla server check covers the new flow, the Dimension flow's portal answer and the example on both targets automatically.
