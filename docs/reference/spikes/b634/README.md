# B634 spike: jigsaw assembly and processors by observation

Answers 4S1 to 4S10 of `docs/PLAN-live-views.md` (batch 4, assembled structures, [ADR 0122](../../../adr/0122-live-views-assembled-structures.md)), measured on 2026-11-23 on this cloud machine (4 cores, 15 GB, shared with other sessions) for the targets 26.3 and 26.4-snapshot-7 (it reports itself as `26.4-alpha.7`). Both versions behaved the same everywhere below unless a line says otherwise.

Clean room: `javap` without `-c` on `JigsawStructure` and `JigsawStructure$MaxDistance` only (signatures: a `MaxDistance(horizontal, vertical)` record). No Mojang method body was read. Registries came from the server jar's own `--reports` run at run time (`registries.json`, `blocks.json`), deleted afterwards. The jar's structure files and worldgen JSON were opened at run time only to count, size and time them; no vanilla file, listing or picture is kept here. Everything else is behaviour of the real dedicated server on MSM's own throwaway fixture pack.

## What was run

- **The fixture pack `b634`** (written by a throwaway script, deleted): 55 own templates (NBT written with palette entries `{id, properties}` at the target's `DataVersion`, 5023 and 5127, as B547 found the game needs), 87 own template pools, 62 jigsaw structures, one structure set per test dimension (`random_spread`, mostly spacing 2 and separation 1), 30 processor lists, own biomes `land_p` and `land_t`, and 18 test dimensions in use: 16 flat (bedrock, two dirt, grass; surface first air at y -60) with `structure_overrides` naming one set, and 2 noise dimensions (`minecraft:overworld` noise over a fixed own biome, so no other fixture lands there). Every template carries a wool or block marker; every jigsaw block a `final_state`.
- **Natural generation** (`structures.starts` read back): each dimension force-loaded over 32 by 32 chunks (64 by 64 for the village dimension, 48 by 48 for two others), saved, and every saved structure start read from the region files with the reference pack's `region.py`. Each start's piece list (template, rotation, position, box, `ground_level_delta`, `junctions`) was rebuilt into a tree by matching each piece's jigsaw blocks (from the fixture's own templates, turned by the piece's rotation) to its neighbour's. Worlds: seed 634 on 26.3 and 26.4, seed 635 on 26.3; 841 starts for each single-structure dimension, 50 to 300 for each structure of a shared one.
- **The game's own commands** on a flat overworld (seeds 634 and 635 on 26.3, 634 on 26.4): `place jigsaw` of 37 processor variants on one sample template (8 by 4 by 8, 40 candidate blocks on a checkerboard, three corner markers), 6 placements each over a prefilled box of glass (water, lava or bedrock for the location, lava and protection tests); `place template` raw, rotated, with integrity and seed; `place structure` and `place jigsaw` of the assembly fixtures (12 to 2 placements each, markers counted); the same position twice (placed, cloned away, cleared, placed again); timings of `place structure` for `minecraft:village_plains`, `minecraft:trial_chambers` and MSM's lattice fixtures.
- **Decode probes**: a one-file pack per value (size, distance, weight, field forms), started on a fresh server per variant, both versions.
- **In JavaScript** (Node 24, fflate 0.8.3 as the app uses): the jar's structure files unzipped and inflated, timed; a throwaway assembler written only from the rules below (not kept) timed on MSM's lattice fixture and on the plains village pools read from the user's jar at run time.

Evidence files beside this README are MSM's own measurements: `results/assembly-<v>-<world>.json` (piece statistics per structure), `detail-*.json` (the rule-specific counts), `cmd-<v>-<seed>.json` (command world read-back), `processors-<v>-<seed>.json` (template block to placed block, per processor list), `terrain-*.json` (projection and terrain adaptation read-back), `decode-*.json` and `decode2-*.json`, `extract-time.json`, `jar-structures.json` and `jar-template-sizes.json` (counts and sizes only), `proto-speed.json`, `gen-time-*.json`, `probe-26.3.json`. The fixture names below (`match`, `chain_s3`, ...) are the structure ids in those files.

## Answers

### 4S1 The jigsaw block, the element types, and which rules the game's own commands confirm

- **Jigsaw block** (both): block state `orientation` with 12 values (`down_east`, `down_north`, `down_south`, `down_west`, `up_east`, `up_north`, `up_south`, `up_west`, `west_up`, `east_up`, `north_up`, `south_up`: front, then top). Block entity fields read back after `setblock` (`probe-26.3.json`, the same on 26.4): `name`, `target`, `pool`, `final_state`, `joint`, `selection_priority`, `placement_priority`; defaults `minecraft:empty`, `minecraft:empty`, `minecraft:empty`, `minecraft:air`, `rollable`, 0, 0. The vendored mcdoc's `target_pool` and `attachment_type` are the old names and are not written.
- **Pool element types** (registry `minecraft:worldgen/structure_pool_element`, both): `single_pool_element`, `legacy_single_pool_element`, `list_pool_element`, `feature_pool_element`, `empty_pool_element`. Projections `rigid`, `terrain_matching`; `projection` is required (`no_projection` refused on both). Weight 1 to 150 (0 and 151 refused). `override_liquid_settings` decodes.
- **A 26.4-only field:** `corner_constraint` (a list of `{density_function, acceptable_density, padding?, corners?, required_corners}`) is **parsed on 26.4** (a bad value is refused: "List is too short", "Not a json array") and **ignored on 26.3** (unknown keys are ignored there, so any value loads). Its effect was not measured: only in the game.
- **Structure** (both): `size` 0 to 20, `max_distance_from_center` an int 1 to 128 or `{horizontal: 1..128, vertical?: 1..4064}`; `start_jigsaw_name`, `project_start_to_heightmap`, `dimension_padding`, `liquid_settings`, `pool_aliases` decode. Pool alias bindings registry: `direct`, `random`, `random_group`.
- **Commands** (both): `place jigsaw <pool> <target> <max_depth 1..20> [pos]` (0: "Integer must not be less than 1"; 21: "must not be more than 20"), `place structure <structure> [pos]`, `place template <template> [pos] [rotation] [mirror] [integrity] [seed]`.
- **Confirmed by the commands** (`cmd-*.json` `asm`): `place jigsaw` and `place structure` apply the same rules as natural generation: name and target matching (`hub_match` by `place jigsaw`: only red, orange and cyan arms), depth with the fallback at the end (`place jigsaw b634:cstart b634:start 3` and `place structure b634:chain_s3`: 3 segments and one cap each, as natural generation's 5 pieces), overlap and fallback (`whub`: one wide and one narrow piece in all 12), the inside-the-parent rule (`shell`, `shell_big` placed, `shell_tall` not), list and feature elements (`misc`: both list templates and the feature's block), the lattice (`grid`: 113 pieces). `place jigsaw` puts the start piece's named jigsaw **one block below** the given position (every one of the 198 located processor placements on each version, every rotation), with a random rotation; an unknown target name fails ("Failed to generate jigsaw"). `place structure` of a size 0 structure fails ("Failed to place structure"). `place template` places at the position as the corner, keeps jigsaw blocks as jigsaw blocks (no processing, no `final_state`) and runs no processors.
- **Randomness:** `place jigsaw` and `place structure` draw fresh randomness on every call: the same position twice gave a different rotation and different pieces and processor results (`twice`, `asm_twice`). `place template ... 0.5 7` twice gave the same 256 of 256 cells, seed 8 only 128 of 256. Natural generation is fixed by the world seed and chunk: **26.3 and 26.4 gave identical assemblies at seed 634** (every fixture structure's piece counts, templates, rotations and start positions; the plains village mean 102.382 pieces on both).

The full rule list is in "Jigsaw rules for B637" below.

### 4S2 Overlap, the distance limit and depth

- **Overlap:** a piece's box may not intersect any placed piece's box (`whub`: two children 7 wide whose boxes overlap; exactly one wide piece and the fallback's narrow piece per hub, 284 of 284 and 258 of 258 starts). A piece reaching back into its parent is refused (`back`: `arm_back` extends three blocks behind its jigsaw into the hub; refused 3364 of 3364 times, the fallback placed instead).
- **Inside the parent:** a child whose box lies **entirely inside its parent's box** is placed even though it overlaps it, and even through the parent's own wall blocks (`shell`: a 3 by 3 by 3 child inside a hollow 9 by 6 by 9 room, 284 of 284; `shell_big`: a 9 by 3 by 9 child spanning the room's walls, 295 of 295). A child partly outside the parent's box is refused (`shell_tall`, 0 of 262). In vanilla's own structures every one of the overlapping box pairs is of this nested kind and none is partial (plains village 4,353 pairs in 68 starts, trial chambers 22,728 in 91, pillager outpost 806 in 66). Two children inside the same parent overlapping each other was not tested.
- **Horizontal distance:** every piece's box stays within the start piece's box centre ± D, inclusive, with the centre `(min + max) / 2` in **integer division that truncates toward zero** (`chain4_d17`, a 4-wide start: 8 pieces when the sum is ≥ 0 and the chain runs toward +, 9 when it runs toward −, and the other way round for negative sums; 91 starts split exactly by sign. `chain_d16`: the last segment ends exactly 16 from the centre; `chain_d32`, `chain2_d15`, `chain2_d16` agree).
- **Vertical distance:** relative to the **start position's y** (the start height, here the start piece's bottom + 1), ± D inclusive, not the box centre (`vchain4_d15`, `vchain4_d16`, `vchain6_d16`, `vchain6_d17`, `vchain_d16`: tops at start y + 16 allowed for D 16, + 18 refused for D 17). The int form limits both axes (`vchain_d16`: 4 pieces); `{horizontal: 116, vertical: 16}` limits up (`vchain_v16`: 4); `{horizontal: 16}` without `vertical` did not limit 100 blocks up (`vchain_h16`: 21 pieces, top 102 above the start).
- **Depth:** pieces at depth 1 to `size` come from the target pool (then its fallback); a piece **at depth `size` still fills its jigsaws, but only from the fallback pool**, and those pieces (depth `size + 1`) are not expanded (`chain_s1`: start, segment, cap; `chain_s20`: 22 pieces, depth 21; `chain_s2`, `chain_s3`, `chain_s7` the same pattern; `place jigsaw ... 3` the same). Fallback pieces at lower depths expand like any other (`fb_s5`: the start pool's only piece is too long for the distance, the fallback segment is placed and the chain continues to depth 6). `size` 0 decodes but makes no start and `place structure` fails (`chain_s0`, `s0_chain`: 0 starts).

### 4S3 Priorities and weights

- **Weights:** a weighted pick per jigsaw; `weights` (3, 1 and an `empty_pool_element` of 1) over 3,364 jigsaws gave 0.595 / 0.204 / 0.200 (seed 634) and 0.611 / 0.187 / 0.202 (seed 635) against 0.6 / 0.2 / 0.2. The empty element is a valid pick that leaves the jigsaw empty; no fallback follows it. When a picked element cannot join, the others are tried: in `match` every one of 3,364 jigsaws got one of the three joinable arms (1,088 / 1,181 / 1,095 and 1,072 / 1,156 / 1,136, about a third each), never the two that cannot join.
- **Order within a piece:** the jigsaws are shuffled, then ordered by `selection_priority`, highest first (`whub`, equal: left 149 / right 135 and 130 / 128; `whub_spl`: left 295 of 295 and 282 of 282; `whub_spr`: right 262 of 262 and 301 of 301).
- **Order between pieces:** children are expanded breadth first in placement order, ordered by the **`placement_priority` of the parent's jigsaw** that placed them, highest first (`phub_pe`: east priority 1, the east arm's child wins 92 of 92 and 105 of 105 although the arms were placed in either order; `phub_pw`: 83 of 83 twice). The **child's own** jigsaw's `placement_priority` is not used (`phub_ce`: 57 / 35 and 42 / 44, the same as `phub_eq`'s 37 / 38 and 42 / 26: the first-placed arm wins).
- **Start rotation:** uniform (200 / 217 / 214 / 210 of 841). **A set with several structures** draws the structure and the start rotation from the same random: in four worlds `proj_tm` started only as `NONE` or `CLOCKWISE_90` and `proj_rg` only as `CLOCKWISE_180` or `COUNTERCLOCKWISE_90`. Statistics need one structure per set.

### 4S4 Projection, start height, terrain adaptation

- **Start:** the start piece's corner is the start chunk's minimum corner, turned about it by a random rotation; its bottom is **start height − 1** for every start form measured: `{absolute: -50}` → bottom -51, `project_start_to_heightmap: WORLD_SURFACE_WG` with `{absolute: 0}` → -61 on a surface whose first air is -60, `{absolute: 5}` → -56, a uniform -40..-20 → bottoms -41 to -21 (`s1_abs`, `s1_proj0`, `s1_proj5`, `s1_uniform`; B547 found the same). With `start_jigsaw_name` one of the start piece's jigsaws of that name (any of the four in `s1_named`) is placed at the start position instead of the corner.
- **On a flat floor:** `terrain_matching` and `rigid` give the same result (`projf_tm`, `projf_rg`: every strip on one level, on the ground; the terrain-matching piece records `ground_level_delta` 1 against 0). **Terrain adaptation does nothing on a flat generator**: all five kinds (`none`, `beard_thin`, `beard_box`, `bury`, `encapsulate`) left the same 3-block gap under a piece floating 3 blocks up, nothing around it (`taf_*`, 15 to 39 starts each, both versions).
- **On generated land** (noise dimensions `n_proj`, `n_ta`): a `terrain_matching` 3 by 9 strip follows the surface column by column (up to 18 different heights in one strip on 26.4 seed 634, 7 on 26.3 seed 635; on land or water in 100 % of columns), a `rigid` one stays on one level (82 to 99 % of columns on land). Terrain adaptation is real there: `none` leaves a mean gap of 7.1 to 9.5 blocks under the piece; `beard_thin` and `beard_box` fill it (gap 0 to 0.3, ground raised around: 26 to 45 solid blocks in a 3-block ring); `bury` and `encapsulate` enclose the piece (the full 7 by 7 by 4 volume above it and 815 to 840 ring blocks solid).
- **So:** on a flat floor the view can show the start height, the projection's level and the pieces exactly; projection along the land and all terrain adaptation exist only on generated land (limit 4L5 covers both; reserve B648 would have to add adaptation, not only matching).

### 4S6 The jar's structure files

- **Count and size** (both): 1,511 files `data/minecraft/structure/**/*.nbt`, nothing else under that folder; 4,236,847 bytes as stored (26.4: 4,233,493; each file is itself gzipped), 2.78 MB deflated in the jar, 45.3 MB of NBT when inflated; median file 1.7 KB, largest 80 KB. No template is wider than 48 blocks; 6 are taller than 32; the largest volume is 69,312 blocks, the most non-air blocks in one template 14,331; the 104 plains village templates hold 156 non-air blocks on average (630 at most).
- **Extraction time** with the app's `unzipSync` and a filter: 67 to 144 ms warm, 139 to 326 ms cold, for all 1,511; inflating every one with `gunzipSync` 275 to 307 ms; reading and parsing the plains and common village folders (125 files) 105 to 382 ms. One village folder alone 34 to 50 ms.
- **Cache growth:** +4.2 MB and +1,511 files if kept as stored (gzipped), as the jar holds them. The JSON folders the views need (`worldgen/template_pool`, `worldgen/processor_list`, `worldgen/structure`, `worldgen/structure_set`, `tags/worldgen/structure`) are already in the cache since schema 4 (the target's `worldgen.terrainPreview.dataFolders`).
- **Verdict:** extract **in bulk** with the cache, as one new binary pattern `^data/minecraft/structure/.+\.nbt$` (not a JSON data folder), and parse on demand in the worker. This is B636's path list (cache schema 6 to 7).

### 4S8 The tolerance for B637's and B641's parity test

- **Exact** (every assembly, every seed): every join legal (rules J1 to J5), no partial box overlap, depth at most `size + 1` with only fallback pieces at `size + 1`, every box inside both distance limits, the deterministic fixtures' piece counts (`match` 5, `back` 5 with fallback 4 of 4, `chain_s1` 3, `chain_s20` 22, `chain_d16` 4, `chain_d32` 7, `chain4_d16` 8, `vchain_d16` 4, `fb_s5` 7, `shell` 2, `shell_big` 2, `shell_tall` 1, `whub` 3, `phub_*` 4, the lattice 113 and 841) and the priority winners (`whub_spl`, `whub_spr`, `phub_pe`, `phub_pw`: 100 %).
- **Statistical:** shares (weights, which jigsaw wins at equal priority, vertical rollable rotations, start rotations) compared with a two-proportion test at |z| ≤ 4; piece-count means within 4 standard errors of the game's (pooled); vanilla min and max within ±15 % of the game's range. Measured spread between seeds 634 and 635 at 841 starts: weight shares differ by at most 1.7 points (one binomial σ is 0.84 points at 3,364 draws), the village mean by 1.7 pieces (standard error about 2.5), trial chambers by 7.1 (about 4.8), the outpost by 0.1.
- **Seeds and size:** at least 200 assemblies per fixture structure on MSM's side and the game's 841 starts of one 32 by 32-chunk world at spacing 2 (one structure per set), on two world seeds (634 and 635). Because 26.3 and 26.4 assemble identically at the same seed, one recorded set serves both targets; record each version anyway so a change is caught.
- **Processors:** deterministic lists exact cell for cell; random ones (`random_block_match`, `block_rot`, `block_age`, `capped` with a range, the position predicates) by share per input block at |z| ≤ 4 over 6 placements of the sample.

### 4S10 Bigger than Try it's area, and the structure ground of B558

- **Sizes against 48 by 48 by 32:** MSM's fixtures fit or nearly (`match` 17 by 17, `grid` 75 by 75, chains up to 105 long); a plains village reaches 80 blocks from its start's centre (about 160 by 160, 13 high), trial chambers 102 out and 60 high, an outpost 24 out and 29 high. Most vanilla jigsaw structures are cut.
- **What B558 accepts:** `packages/sim/src/grounds/structure.ts` `structureGround(template, worldCorner?, keep?)` takes **one** `StructureTemplateBlocks` (`size`, `palette` of state strings, `blocks` as `[x, y, z, paletteIndex]`), centres it in x and z on the area's floor (`y` 0), drops every block outside the area and returns `cut: boolean`. It knows nothing of pieces.
- **The answer for B642:** flatten the assembly into one `StructureTemplateBlocks` (pieces in placement order, later blocks over earlier, jigsaw blocks replaced by their `final_state`, processors applied), **crop it to a 48 by 48 by 32 window around the start piece** (the start piece centred, the window's floor at the lowest piece's bottom, or at the start piece's bottom when the structure is taller than 32) before handing it over, and say "Cut at the area's edge: N of M pieces shown" (limit 4L8). `cut: boolean` cannot say N of M, so B642 adds the count beside the ground (its owner files include the ground's loader). On "My world generation" each piece's own box is placed where it lands on the generated land; pieces outside the 48 by 48 window are counted, not drawn.

## Jigsaw rules for B637

Each rule with the fixture that showed it; all on both versions and both seeds.

|---|---|---|

| J5 | Any matching jigsaw of the child may be used; the child is turned so that it faces. | `match`: `arm_two` via its side jigsaw 1,181 |

## Processor list for B638

Applied means the rule was learned exactly from the before-and-after worlds; about right means applied as observed with the view's "about right" label; named means listed, the template left unchanged for it.

| Type or test | Verdict | What the world showed (fixture, both versions) |
|---|---|---|
| `nop` | applied | nothing changes (`nop`) |
| `block_ignore` | applied | listed states are not placed; the world's block stays, air included (`ignore`: stone and air kept the glass) |

## Findings for the plan

1. **26.3 and 26.4 assemble identically at the same world seed** (J20). B639's expectations can be one measured set for both targets, still recorded per version; the only version differences found are the registry name `rule_test` / `rule_test_type` and the 26.4-only `corner_constraint`, which B638's schema walk and B635's stubs should know.
2. **Terrain adaptation does nothing on a flat floor** (4S4): 4L5 should say "On a flat floor, terrain matching and terrain adaptation are flat", and reserve B648 would need to add adaptation (beard, bury, encapsulate) as well as matching.
3. **Placement priority is the parent jigsaw's** (J15): the Template Pool Studio and the AI helper's words (B644) should describe it that way; a child's value has no effect.
4. **The distance limits differ by axis** (J12, J13): horizontal from the start box's truncated centre, vertical from the start height; `{horizontal}` without `vertical` did not limit upward. B637's tests need both, and the view's line about the limit should not call it a sphere or a cube.
5. **Size 0 makes no structure** (J11): a validator line for B637's or the structures plugin's checks (outside this plan's files: a follow-up).
6. **The budgets in ADR 0122 D10 are generous**: 100 pieces in about 10 ms in JavaScript; the cost is parsing templates (up to 250 ms for a village folder), so B636 should hand the worker parsed templates once and B637 should cache them per pool.
7. **B636's path list is one binary pattern** (`^data/minecraft/structure/.+\.nbt$`, 1,511 files, +4.2 MB, extracted in bulk in under 0.35 s), not a new data folder; the JSON folders are already cached (schema 4).
8. **4L9's 500-piece stop is above every vanilla structure** (trial chambers at most 340 measured); keep 500.
9. **B639's fixture should put one structure per structure set**, because a set's structure choice and start rotation come from the same random draw (4S3), and use `/place` only for single checks: `place jigsaw` and `place structure` are freshly random on every call and `place jigsaw` sets the named jigsaw one block below the position.
10. **4S10 needs a count in B642**: the B558 ground's `cut` is a boolean; "N of M pieces shown" needs B642 to add a count beside it (its owner files cover the ground's loader).
