# ADR 0077: Custom portal blocks

## Context

Since [ADR 0051](0051-dimension-creator-flow.md) a project can make a dimension, but the only way in is a function that runs `spreadplayers` (from a key item or a command). The coverage audit (backlog B13, row "Dimension, dimension type") asks for a real portal: players build a frame of a chosen block, light it with a chosen item or a trigger, and a portal block forms that takes them to a project dimension (or a vanilla one) and back, like the Nether portal, with its own looks (texture, particles, sounds) and travel rules (delay, cooldown, where the return portal goes, a coordinate scale such as the Nether's 8:1).

A portal is runtime work: a vanilla data or resource pack cannot add a block, and the Nether portal's machinery is hard-wired to obsidian, the Nether portal block and the Nether. This ADR covers the format, the runtime, the versions and the eject; [ADR 0078](0078-portal-flows-studio-and-tests.md) covers the Block Studio, the Creator flows, templates, examples, the AI helper and the tests. The working plan is `docs/PLAN-portals.md` (B330–B345); it holds the full fact table (F1–F20) and the limits (P1–P18).

Facts read on 2026-11-14 with `javap -protected`, `javap -c -p -constants` (JDK 25) over the Loom-cached `minecraft-merged-deobf-26.3.jar` and `minecraft-merged-deobf-26.4-snapshot-7.jar` and the Loom-cached Fabric API module jars of `fabric-api` 0.165.2+26.3 and 0.165.4+26.4 (the plan's fact table lists every signature):

- **The vanilla portal pipeline is generic.** `Portal` (`getPortalDestination(ServerLevel, Entity, BlockPos)`, default `getPortalTransitionTime(ServerLevel, Entity)` and `getLocalTransition()`), `Entity.setAsInsidePortal(Portal, BlockPos)`, `Entity.handlePortal()`, `PortalProcessor`, `TeleportTransition` (with `PLAY_PORTAL_SOUND`, `PLACE_PORTAL_TICKET` and `PostTeleportTransition.then`), `DimensionType.getTeleportationScale(DimensionType, DimensionType)`, `WorldBorder.clampToBounds(double, double, double)`, `Entity.setPortalCooldown(int)` and `Entity.canUsePortal(boolean)` are public and byte-identical on both versions. Any block that implements `Portal` and calls `setAsInsidePortal` from `entityInside` gets vanilla's delay, cooldown, passenger, chunk-ticket and dimension-change handling.
- **Detection and exit placement are not reusable.** `PortalShape` reads the `#minecraft:nether_portal_frame` tag and fills with `Blocks.NETHER_PORTAL` (private constructor; inner sizes 2 to 21 wide, 3 to 21 high); `PortalForcer` searches `PoiTypes.NETHER_PORTAL` and builds obsidian. Only the static helpers `PortalShape.getRelativePosition(FoundRectangle, Axis, Vec3, EntityDimensions)` and `PortalShape.findCollisionFreePosition(Vec3, ServerLevel, Entity, EntityDimensions)` are generic.
- **POI types are not an option on both versions.** `PoiTypes.TYPE_BY_STATE` and its `register` methods are private on both; Fabric's `PoiHelper.register` exists in `fabric-object-builder-api-v1` 24.1.13 (26.3) and is gone from 25.0.8 (26.4); 26.4 also changes `PoiTypes`' constants from `ResourceKey` to `Holder` (a new `PoiTypeIds` holds the keys) and `PoiManager`'s constructor. A POI type would need a seam with reflection or a Mixin on 26.4.
- **Fabric level attachments are persistent on both versions.** `fabric-data-attachment-api-v1` (2.2.34 on 26.3, 2.2.42 on 26.4) attaches persistent data to a `ServerLevel` (saved through Fabric's `AttachmentSavedData`), with the same `AttachmentRegistry.create` API the runtime already uses for script data ([ADR 0062](0062-persistent-script-data.md)).
- **The client effect needs no client code, but is the Nether's.** `LocalPlayer` runs its portal effect when the active portal's `getLocalTransition()` is `CONFUSION`: it closes container screens, plays `SoundEvents.PORTAL_TRIGGER` locally and raises `portalEffectIntensity` (the screen wobble); `Hud` draws the overlay from the particle sprite of `Blocks.NETHER_PORTAL`. The client calls `entityInside` for the local player itself, so a portal block that is in the content jar on both sides drives the effect with no client class. The overlay picture and the entry sound cannot be ours without client code.

## Decision

- **D1 A block type `portal`.** `msm:block` gains `type: "portal"` ([ADR 0067](0067-block-types-and-states.md) D1), with its own fields (the `msm:block_type` dispatch), not a component and not a new kind. We chose a type because the portal block is a vanilla family of its own (no collision, an `axis` state, a pane-thin shape, no item), because one element can then hold the whole rule (frame, igniter, destination, looks) for the Studio and the Creator, and because `BlockComponents` has only two Codec fields left (limit C18 of ADR 0074): type fields are a separate Codec.

  ```
  dispatch msm:block_type[portal] to struct PortalFields {
    frame: (#[id="block"] string | #[id(registry="block", tags="required")] string),  // a block id or #tag
    frame_block?: #[id="block"] string,      // the block exits are built of; default `frame` (required when `frame` is a tag)
    igniter?: (#[id="item"] string | #[id(registry="item", tags="required")] string | false),
                                             // default minecraft:flint_and_steel; false: only the light_portal action lights it
    destination: #[id="dimension"] string,   // a project or vanilla dimension
    return_to?: #[id="dimension"] string,    // default minecraft:overworld; must differ from destination
    travel?: struct PortalTravel {
      scale?: double @ 0.00001..30000000,    // the destination's scale against return_to; 8 = like the Nether;
                                             // default: from the two dimension types (DimensionType.getTeleportationScale)
      arrival?: ("portal" | "surface"),      // default portal: find or build a linked exit portal
      delay_ticks?: int @ 0..32767,          // survival players; default the gamerule (vanilla 80); creative keeps its gamerule
      cooldown_ticks?: int @ 0..32767,       // default vanilla's (Entity.getDimensionChangingDelay)
      players_only?: boolean,                // default false: items, mobs and vehicles travel too
      overlay?: boolean,                     // default true: vanilla's portal wobble, overlay and entry sound (limit P2)
    },
    sounds?: struct PortalSounds {
      ambient?: (#[id="sound_event"] string | false),   // default the target's portal ambient sound
      travel?: (#[id="sound_event"] string | false),    // default the target's portal travel sound
    },
    particles?: struct PortalParticles {
      type?: #[id="particle_type"] string,   // a particle type without options; default the target's portal particle
      color?: int @ 0..16777215,             // set: coloured dust particles of this colour (limit P3)
      count?: int @ 0..16,                   // per animation tick; default 4; 0 none
    },
    on_travel?: string,                      // event; self and other = the traveller, after arrival
  }
  ```

  The element gains the editor-only texture slot `textures.portal` (stripped in lowering). Defaults that differ from other types: no block item when `item` is absent (an explicit `item` still registers one, for creative placement), no loot table when `loot_table` is absent, unbreakable unless `msm:breakable` is given, light 11 unless `msm:light_emitter` is given, sound type `glass` unless `sound_type` is given (the Nether portal's values). Components allowed on `portal`: `msm:breakable`, `msm:light_emitter`, `msm:on_break`, `msm:on_place`, `msm:on_random_tick`, `msm:on_entity_inside`; any other is `blocks-items.component-not-for-type` and a runtime load error that drops it.
- **D2 The frame rule.** A frame is a vertical rectangle (axis x or z) whose inside is 2 to 21 blocks wide and 3 to 21 high (vanilla's sizes), with frame blocks (the `frame` block, or any block in the `frame` tag, read at use time so tags reload with `/reload`) along all four sides; corners are not needed (as vanilla). The inside may hold only air, blocks in `#minecraft:fire` and this portal's own block. We write our own detector (`registry/portal/PortalFrame`), never copying vanilla's; `PortalShape` is not called for detection.
- **D3 Lighting.** (a) **Igniter use.** A Fabric `UseBlockCallback` checks, on both sides, whether the held item matches a portal's `igniter` (item id or `#tag`) and the block next to the clicked face is the inside of an empty valid frame of that portal (both axes tried, x first); the server fills the inside with the portal block (axis set) and records the portal in the index (D5); a damageable igniter loses one durability, any other is used up one at a time, and nothing is used in creative; both sides return `SUCCESS`, so the client never predicts a fire. Portals are tried in sorted id order; two portals with the same frame and igniter are a validator warning (`blocks-items.portal-frame-clash`), and the first wins. (b) **The action `light_portal`** `{ "type": "light_portal", "portal": "<block id>" }` lights that portal at the event's block position (`EventContext.block`, else `base`) or one of its six neighbours, so a trigger (a block's `msm:on_interact`, an item's `msm:on_use_on_block`, a mob's death) can light it; it does nothing when no empty frame is there. Fire placed in a frame by any other means (lightning, fire spread, a dispenser) does not light it (limit P6).
- **D4 The portal block.** `registry/types/MsmPortalBlock extends Block implements Portal, DrivenBlock`, built by `BlockTypes.create` like the other family types: state `axis` (`BlockStateProperties.HORIZONTAL_AXIS`), a 4-pixel-thin shape along the axis, no collision, `rotate` swaps the axis; `updateShape` turns it to air when a neighbour along the axis or above or below changes and the frame (D2) is no longer complete (as vanilla); `entityInside` (on both sides, never returning early on the client) calls `canUsePortal(false)`, then, unless `players_only` stops a non-player, `setAsInsidePortal(this, pos)`; `getPortalTransitionTime` gives players `delay_ticks` (or the gamerule `PLAYERS_NETHER_PORTAL_DEFAULT_DELAY`), invulnerable (creative) players the gamerule `PLAYERS_NETHER_PORTAL_CREATIVE_DELAY`, and others 0; `getLocalTransition` is `CONFUSION` with `overlay` and `NONE` without; `animateTick` (client) spawns `count` particles (the `type`, which must be a `SimpleParticleType`, or `DustParticleOptions(color, 1.0)` when `color` is set) and plays the ambient sound locally, about once in 100 ticks; `getCloneItemStack` is empty unless the block has an item. No random tick spawning (the Nether portal's zombified piglins are not copied).
- **D5 Linking without POI types: our own index.** A persistent Fabric attachment `msm_runtime:portals` on each `ServerLevel` holds the portals of that level: `{ block, min, axis, width, height }` per portal (the inside rectangle). Lighting and exit building add an entry; a lookup checks the block at the entry and drops a stale entry; an entity that uses a portal with no entry adds it (portals placed by `/fill`, structures or other mods enter the index on first use). We chose this over a POI type because POI registration differs between the versions (Context) and over scanning blocks because a 257 by 257 column scan is too slow. Only portals of the same block id link.
- **D6 Travel.** `getPortalDestination` picks the target level: `return_to` when the portal is in `destination`, else `destination` (a portal in a third dimension also leads to `destination`). A missing level (a dimension not loaded in this world) gives no teleport and one warning per portal and level at the first attempt; the server also logs one warning per portal at start for a missing level. The target position is the entry position times the factor (with `scale` between `return_to` and `destination`: `1 / scale` going to `destination`, `scale` coming back; otherwise `DimensionType.getTeleportationScale` of the two levels), clamped to the target's world border. With `arrival: portal` it looks for the nearest indexed portal of the same block within a square radius of `clamp(round(128 × min(1, factor)), 16, 128)` blocks (the Nether's 16 and 128) and, if none, builds one with the entry's axis and a 2 by 3 inside: on solid ground within 16 blocks of the target between the level's lowest y and its logical height, else at the target with a platform of `frame_block` under it and the inside cleared (vanilla's behaviour, our own code); the traveller keeps its relative position in the portal (`PortalShape.getRelativePosition` and `findCollisionFreePosition`, the generic statics) and its rotation. With `arrival: surface` it lands on the first standing spot at the target column (from the logical height down in a level with a ceiling), building nothing; with no standing spot (a void) it falls back to `portal`. The transition carries `PLACE_PORTAL_TICKET` and, unless `sounds.travel` is `false` or a project sound, `PLAY_PORTAL_SOUND`; a project or other travel sound is played to the traveller at arrival; `cooldown_ticks` is applied to the arrived entity; then `on_travel` fires with the traveller as self and other at the exit position (as [ADR 0058](0058-event-actors-entity-commands-and-cancel-resync.md) actors: `run_function` runs as the traveller). Passengers, vehicles and the `allow_entering_nether_using_portals` gamerule (for a destination of the Nether) follow vanilla.
- **D7 Versions.** All runtime code is shared: every member used is the same on both versions (the plan's fact table). The runtime never touches `PoiTypes`, `PoiManager`, `PortalForcer` or `ServerLevel.getPortalForcer`. Plugin API 1.13.0 (additive) adds `BlockFacts.portal?: { ambientSound: string; travelSound: string; triggerSound: string; particle: string }`; both targets: `minecraft:block.portal.ambient`, `minecraft:block.portal.travel`, `minecraft:block.portal.trigger`, `minecraft:portal` (checked against the vendored registries). Built-in plugins keep `^1.0.0`.
- **D8 Lowering and validators** (`@msm/plugin-blocks-items`). The runtime definition keeps the type fields; lowering writes the blockstate (`axis=x` and `axis=z`), two generated models `<id>_ns` and `<id>_ew` whose parents are `minecraft:block/nether_portal_ns` and `_ew` with `portal` and `particle` set to `textures.portal` (default `minecraft:block/nether_portal`, referenced, never bundled; an animation sidecar `.png.mcmeta` beside a project texture is exported as today), the `block.<ns>.<id>` name, and an entry in `#minecraft:portals` (vanilla's portal block tag, which keeps dismounting riders out of portals). Validators (codes `blocks-items.*`): `portal-destination-unknown` (neither a project dimension nor a target dimension; error), `portal-same-dimension` (`destination` equals `return_to`; error), `portal-frame-unknown` (block or tag neither project nor vanilla; error), `portal-frame-block-needed` (a tag `frame` without `frame_block`; error), `portal-igniter-unknown` (error), `portal-particle-options` (`color` with a `type` other than `minecraft:dust`; error; a `type` that takes options is a runtime load error that keeps the default particle, as for leaves, because the app has no list of option-less particle types), `portal-sound-unknown` (warning; project sound keys accepted as in [ADR 0057](0057-project-sound-events-and-mob-sounds.md)), `portal-event-unknown` (`on_travel`; error), `portal-frame-clash` (warning), `light-portal-not-portal` (a `light_portal` action naming a block that is not a project portal; error), and the existing `component-not-for-type`.
- **D9 Java eject (26.3 generator).** A portal block becomes a generated `block/<Name>Block extends Block implements Portal`, with shared generated classes copied from the runtime as templates (`portal/PortalFrame`, `PortalIndex`, `PortalTravel`, `PortalLighting`), the attachment and the `UseBlockCallback` registered in the generated mod initialiser, and `light_portal` in the generated actions; the copies are compared line by line with the runtime in the target tests. Eject stays 26.3 only.
- **D10 Not in this batch (limits).** Floor portals such as the End's (a horizontal frame), a portal overlay or entry sound of our own (client code, backlog B15), particle colours other than dust (client providers, B14), lighting by fire from any source but the igniter or the action (a Mixin on fire placement), POI types and villager-style portal search, editing dimension types (ADR 0051 D1 stands: flows keep vanilla dimension types and `travel.scale` covers the 8:1 need; the `dimension_type` kind remains for power users), a script method to light portals or read links, a portal that chains more than two dimensions, and zombified-piglin-style spawning. The limits are listed in the plan (P1–P18) and move to this ADR's Findings at close.

## Consequences

- Format 1 grows additively: one block type with nested field groups, one action, one texture slot. The corpus (prefix `portal-`), the runtime Codecs, the plugin, the generator and the app move together; a block without the type registers exactly as before, and `BlockComponents` keeps its two free fields.
- Portals work with the Fabric mod jar only, on both targets, with no client class, no Mixin and no seam; the entry overlay and sound are the Nether's (or none), which the in-game check confirms because CI cannot draw (audit L16).
- Links live in the world's saved data under the runtime's id: removing the runtime from a world forgets them (new exits are built), and portals placed without lighting join the index on first use.
- Vanilla pack safety ([ADR 0066](0066-vanilla-pack-safety.md)) needs no new rule: the portal block is a mod-only id, so its `#minecraft:portals` entry becomes optional in vanilla data packs and a function naming it is kept with the usual warning; the dimension itself is vanilla data and stays.

## Status

Accepted (2026-11-14), with the defaults below; the user may still veto them. Vetoable defaults: a block type `portal` rather than a component or a kind (D1); one portal element holding frame, igniter and destination (D1); `minecraft:flint_and_steel` as the default igniter and its use rule (one durability, or one item, nothing in creative) (D3); `minecraft:overworld` as the default `return_to` (D1); the scale from the dimension types unless `travel.scale` is set (D6); `arrival: portal` with Nether-like linking and building, the search radius rule and the 16-block build search (D6); vanilla's delay and cooldown unless set (D4, D6); the overlay on (D4); the target's portal particle, ambient and travel sounds, light 11, unbreakable, no item, no loot, glass sounds (D1, D7); corners not needed and vanilla's frame sizes (D2); the action name `light_portal` and the event field `on_travel` (D3, D6); the `#minecraft:portals` tag entry (D8); our own level index instead of POI types (D5); dimension type editing left out (D10).
