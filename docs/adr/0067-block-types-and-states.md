# ADR 0067: Block types and states

## Context

`msm:block` makes one kind of block: a full cube, or since [ADR 0059](0059-block-shapes-and-see-through-blocks.md) a fixed shape that is the same in every state. The only state property is `powered` (with `msm:redstone`). ADR 0059 D5 deferred rotation, state properties, connecting shapes, stairs, slab stacking, doors and trapdoors, crops and block families; the coverage audit lists them as backlog B2 (L5). This ADR covers the building blocks; crops, saplings, trees and leaves are [ADR 0068](0068-crops-saplings-trees-and-leaves.md); the family wizard and library content are [ADR 0069](0069-block-family-flows.md).

Facts read on 2026-11-14 with `javap` (JDK 25) over the Loom-cached merged jars `minecraft-merged-deobf-26.3.jar` and `minecraft-merged-deobf-26.4-snapshot-7.jar`, the vanilla data and asset files inside them, the cached Fabric API module jars, the vendored `registries.json` of both targets and this repository:

- **Vanilla classes per family, constructors (26.3):** `StairBlock(BlockState base, Properties)` (protected), `SlabBlock(Properties)`, `WallBlock(Properties)`, `FenceBlock(Properties)`, `FenceGateBlock(WoodType, Properties)`, `DoorBlock(BlockSetType, Properties)` (protected), `TrapDoorBlock(BlockSetType, Properties)` (protected), `ButtonBlock(BlockSetType, int ticksToStayPressed, Properties)` (protected), `PressurePlateBlock(BlockSetType, Properties)` (protected), `WeightedPressurePlateBlock(int maxWeight, BlockSetType, Properties)` (protected), `IronBarsBlock(Properties)` (protected; panes and bars), `RotatedPillarBlock(Properties)`; `DirectionalBlock` and `HorizontalDirectionalBlock` are abstract. Every one of these signatures is identical on 26.4-snapshot-7. The only difference among them: `SlabBlock.canPlaceLiquid` takes a `Fluid` on 26.3 and a `FluidState` on 26.4 (we do not override it).
- **`BlockSetType` and `WoodType` are records with public constructors.** On 26.3 `BlockSetType` has a name, a `SoundType`, a private `register` into a name map (for its Codec) and constants `IRON, COPPER, GOLD, STONE, POLISHED_BLACKSTONE, OAK, SPRUCE, BIRCH, ACACIA, CHERRY, JUNGLE, DARK_OAK, PALE_OAK, POPLAR, CRIMSON, WARPED, MANGROVE, BAMBOO`. On 26.4-snapshot-7 it has no name, no map and no Codec, takes a `ResourceKey<BlockSoundSet>` (the new `block_sound_set` data registry) and its constants are `DEFAULT_WOOD, IRON, COPPER, GOLD, STONE, POLISHED_BLACKSTONE, CHERRY, CRIMSON, WARPED, BAMBOO` (the per-wood oak-like constants are gone). `WoodType` keeps its name and the same 13 constants (`OAK` to `BAMBOO`) on both, but its constructor takes `SoundType` on 26.3 and `ResourceKey<BlockSoundSet>` on 26.4, and 26.4 drops its name map and Codec. Fabric's `WoodTypeBuilder` has `register` on 26.3 and only `build` on 26.4.
- **Stripping is data driven and not mergeable.** 26.x has a `block_transformer` data registry (`data/minecraft/block_transformer/{axe,hoe,shovel}.json`, each a list of transforms with a `rule_based` block state provider) and an item component `minecraft:block_transformer` naming one entry; vanilla axes name `minecraft:axe`. A data pack can only replace `minecraft:axe` whole, which would mean shipping Mojang's list; Fabric API 0.165 has no `StrippableBlockRegistry` any more (`fabric-content-registries-v0` 15.0.7 lists `FlammableBlockRegistry`, `OxidizableBlocksRegistry`, `LandPathTypeRegistry`, `VibrationFrequencyRegistry`, `VillagerInteractionRegistries`).
- **Flammability is code**: no fire tags exist for burn and spread odds; Fabric `FlammableBlockRegistry` sets them.
- **Behaviour depends on tags**, so they are not decoration: fences connect to `#minecraft:wooden_fences` members of the same kind, walls to `#minecraft:walls`, fence gates fit walls; panes connect to panes and walls. The vanilla tags exist on both targets: `stairs`, `slabs`, `walls`, `fences`, `wooden_fences`, `fence_gates`, `doors`, `wooden_doors`, `trapdoors`, `buttons`, `pressure_plates`, `planks`, `logs`, `logs_that_burn`, `mineable/*` (block, with item counterparts where vanilla has them; the full list is checked against the vendored registries at implementation).
- **Vanilla model parents exist on both targets** (`assets/minecraft/models/block/`): `stairs`, `inner_stairs`, `outer_stairs`, `slab`, `slab_top`, `cube_column`, `cube_column_horizontal`, `fence_post`, `fence_side`, `fence_inventory`, `template_fence_gate` (four forms), `door_{bottom,top}_{left,right}[_open]`, `template_orientable_trapdoor_{bottom,top,open}`, `template_wall_post`, `template_wall_side`, `template_wall_side_tall`, `wall_inventory`, `button`, `button_pressed`, `button_inventory`, `pressure_plate_up`, `pressure_plate_down`, `template_glass_pane_{post,side,side_alt,noside,noside_alt}`, `orientable`, `orientable_vertical`. A project model naming them as parent references the user's own client jar; nothing is bundled.
- **Vanilla data shapes (identical on both targets):** blockstates use `variants` (stairs, doors, slabs) or `multipart` (fences, walls, panes); a slab's loot uses `minecraft:set_count` 2 under `minecraft:match_block` with `state: { type: double }`; a door's loot drops only from `half: lower`. Loot conditions are `condition` (singular) and functions `modifier` in the current format.
- **Doors use `DoubleHighBlockItem`** (present on both targets).
- **`MsmBlock` holds every behaviour** (events, triggers, redstone, shape, see-through) as overrides of `Block`; Java's single inheritance means a `StairBlock` cannot be an `MsmBlock`.
- `lower(element, target)` sees one element; validators see the project ([ADR 0059](0059-block-shapes-and-see-through-blocks.md) context).

## Decision

- **D1 A `type` field on `msm:block`, not new kinds.** Definition and element gain `type?: BlockType`, absent meaning `"block"` (today's block, byte-identical definition and behaviour). We chose a field over a kind per family because every type shares the registry (`block`), the block item, sound type, breakability, tool tags, loot, creative tab and the events and triggers; the Block Studio stays one Studio with a Type picker, and the wizard ([ADR 0069](0069-block-family-flows.md)) makes one ordinary `msm:block` element per family member. Types in this ADR: `block`, `pillar` (axis: logs, pillars, basalt-like), `horizontal` (four-way facing, towards the placer, like a furnace or carved pumpkin), `directional` (six-way facing, like an observer), `slab`, `stairs`, `wall`, `fence`, `fence_gate`, `door`, `trapdoor`, `button`, `pressure_plate`, `pane`. [ADR 0068](0068-crops-saplings-trees-and-leaves.md) adds `crop`, `sapling` and `leaves`.
- **D2 Per-type definition fields** (mcdoc dispatch on `type` into the top level of the definition; closed per type):
  - `stairs`: `base_block?` (a block id; default `minecraft:stone`, default, vetoable). The base must be registered before the stairs (D4).
  - `door`, `trapdoor`, `button`, `pressure_plate`: `set_type` (required), one of `wood`, `cherry`, `bamboo`, `crimson`, `warped`, `iron`, `copper`, `gold`, `stone`, `polished_blackstone`. It picks vanilla's sounds, whether hands open it (not `iron`), whether arrows press buttons and which entities press plates. `wood` is `OAK` on 26.3 and `DEFAULT_WOOD` on 26.4 (a seam, D9). Names are a target fact (D9).
  - `button`: `press_ticks?: int @ 1..200` (default 30 for the wooden set types, 20 otherwise, as vanilla).
  - `pressure_plate`: `weighted_max?: int @ 1..` (present: a weighted plate whose signal grows with the number of entities up to this count, as gold and iron plates; absent: an ordinary plate).
  - `fence_gate`: `wood_type` (required), one of `oak`, `spruce`, `birch`, `acacia`, `cherry`, `jungle`, `dark_oak`, `pale_oak`, `poplar`, `crimson`, `warped`, `mangrove`, `bamboo` (open and close sounds; the constants exist under the same names on both targets).
  - `block`, `pillar`, `horizontal`, `directional`, `slab`, `wall`, `fence`, `pane`: no extra fields.
- **D3 Components per type.** All types keep `msm:breakable`, `msm:light_emitter` and the triggers `msm:on_break`, `msm:on_place`, `msm:on_step`, `msm:on_entity_inside`, `msm:on_random_tick` (which runs after vanilla's own random tick). `msm:on_interact` fires after vanilla's own use action (a door has opened when it fires). `msm:shape` is allowed only on `block`, `pillar`, `horizontal` and `directional`; on the rotating types its boxes are written for the default orientation (north, axis `y`) and turn with the state. `msm:redstone` is allowed only on `block`, `pillar`, `horizontal` and `directional` (doors, gates, buttons and plates have vanilla's own `powered`). Two new components, allowed on every type: `msm:flammable { burn_odds: int @ 0..300, ignite_odds: int @ 0..300 }` (vanilla planks are 5 and 20, logs 5 and 5, leaves 30 and 60) through Fabric `FlammableBlockRegistry`; and `msm:strippable { into: block id }` (on `pillar`; any type is accepted and the axis is copied when both have one). A component not allowed for the type is a validator error (`blocks-items.component-not-for-type`) and a runtime load error that drops that component while the block still registers, as `while_worn` without armour does.
- **D4 Runtime.** A driver class per vanilla family in `registry/types/` (`MsmStairBlock extends StairBlock`, `MsmSlabBlock`, `MsmWallBlock`, `MsmFenceBlock`, `MsmFenceGateBlock`, `MsmDoorBlock`, `MsmTrapDoorBlock`, `MsmButtonBlock`, `MsmPressurePlateBlock`, `MsmWeightedPressurePlateBlock`, `MsmPaneBlock extends IronBarsBlock`), each delegating the shared behaviour to one `BlockBehaviourDriver` extracted from `MsmBlock` (events, triggers, cooldown maps, light). `pillar`, `horizontal` and `directional` stay `MsmBlock`, which gains an optional `AXIS` or `FACING` property chosen through the same thread-local pattern as `POWERED`, placement state, `rotate` and `mirror`, and per-state shapes (rotated boxes, precomputed). The `BlockBehaviour.Properties` of each type follow vanilla's own (`noOcclusion`, `pushReaction`, `noCollision` for buttons and plates, `forceSolidOn` for walls and fences, and so on; the executor reads them from `Blocks.<clinit>` and records them). `MsmRegistrar` registers blocks with no `base_block` dependency first, then stairs in dependency order; a base that is unknown, not yet registered (a block of another mod that registers after `msm_runtime`) or failed is a load error that skips the stairs. Doors get a `DoubleHighBlockItem`. `msm:strippable` runs through Fabric `UseBlockCallback`: a held item whose `minecraft:block_transformer` component names `minecraft:axe` (so vanilla axes, project axes and other mods' axes) strips the block, copies the axis, plays `minecraft:item.axe.strip`, damages the item by 1 and swings, as vanilla. `msm:flammable` registers once at start-up.
- **D5 Lowering per type** (in `@msm/plugin-blocks-items`): the runtime definition, the blockstate (`variants` or `multipart` in vanilla's shape for the type, written by a pure table per type), the block models, the item model definition (doors, buttons-inventory, fences-inventory and walls-inventory as vanilla), the `en_us` key, the tool and tier tags, the loot preset and the behaviour tags. Block and item tags the type always joins (D6) are written with `merge: 'tag'`. Loot `self` follows the type: slabs drop two when double; doors drop from the lower half only.
- **D6 Tags written by lowering.** `stairs` to `#minecraft:stairs`, `slab` to `#minecraft:slabs`, `wall` to `#minecraft:walls`, `fence` to `#minecraft:fences` (plus `#minecraft:wooden_fences` when `sound_type` is a wood sound, default, vetoable: an editor field `wooden?: boolean` overrides), `fence_gate` to `#minecraft:fence_gates`, `door` to `#minecraft:doors` (and `wooden_doors` for wooden set types), `trapdoor` to `#minecraft:trapdoors` (and `wooden_trapdoors`), `button` to `#minecraft:buttons` (and `wooden_buttons` or `stone_buttons`), `pressure_plate` to `#minecraft:pressure_plates` (and `wooden_pressure_plates` or `stone_pressure_plates`), each as a block tag and, where vanilla has one, the item tag. Pillars join nothing automatically (`logs` is the wizard's choice, [ADR 0069](0069-block-family-flows.md)). Tag names are checked against each target's vendored registries in the plugin tests.
- **D7 Editor-only element fields**, stripped in lowering: `textures` (per type: `all`; or `side`, `end` for pillars; `top`, `bottom`, `side` for slabs, stairs and walls; `top`, `bottom` for doors; `texture` for trapdoors, buttons, plates, fences, gates, walls; `pane` and `edge` for panes; `front`, `side`, `top` for the facing types), from which lowering writes the type's block models as `<ns>:block/<path>` plus suffixes (`_inner`, `_outer`, `_top`, `_double`, `_post`, `_side`, `_side_tall`, `_noside`, `_open`, `_pressed`, `_down`, `_inventory`, ...) parented on the vanilla templates; or `models` (a map from the type's model slot to a model id) to use the user's own models; `model` stays for `block` and is accepted for the facing types and `pillar` as the single model. A type other than `block` with neither `textures` nor `models` is a validator error (`blocks-items.type-needs-appearance`). A project model element with the id of a generated model is a validator error (`blocks-items.generated-model-clash`).
- **D8 Validators** (new file, codes `blocks-items.*`): `component-not-for-type`, `type-needs-appearance`, `generated-model-clash`, `unknown-set-type` and `unknown-wood-type` (against target facts), `stairs-base-unknown` (neither project block nor vanilla block), `stairs-base-cycle`, `strippable-target-unknown`. Existing checks (model not cube, transparent texture) learn the types: a family type never triggers `model-not-cube`.
- **D9 Versions.** Shared runtime code for all classes above. One new seam, `registry/BlockSetTypes` in `src/mc/<mc>/java` (26.3: name to `OAK`/`CHERRY`/...; 26.4: `wood` to `DEFAULT_WOOD`, the rest by name), with a GameTest seam check. `WoodType` constants are named the same on both and need no seam; we never construct a `BlockSetType` or `WoodType` (D11). Plugin API 1.10.0 (additive) adds `Target.blocks?: BlockFacts { setTypes: readonly string[]; woodTypes: readonly string[] }`; both targets list the MSM names of D2.
- **D10 Java eject (26.3 generator).** Generated block classes extend the same vanilla classes (protected constructors through a generated subclass), mirror the per-state shapes, `UseBlockCallback` stripping and `FlammableBlockRegistry` calls; stairs are emitted after their base. Eject stays 26.3 only.
- **D11 Not in this batch (limits).** Signs and hanging signs: their block entity types accept a fixed set of blocks and the client draws them from a sign material keyed by a registered `WoodType`; 26.4 removed `WoodType`'s registration map, so this needs client code and a seam (audit L3). Boats and chest boats: an entity type with a client renderer and model layer (L3). Own door and button sounds: a custom `BlockSetType` takes `SoundType` on 26.3 and a `block_sound_set` key on 26.4; deferred, so set types are vanilla presets. Waterlogging for `block` and the facing types (the vanilla family classes keep their own waterlogging). Copper weathering and waxing (`block_transformer` plus Fabric `OxidizableBlocksRegistry`). Stripping through vanilla data (D4 explains why the runtime does it). Ladders, torches, lanterns, chains, carpets as a type (the `carpet` shape preset stays), flower pots and potted plants, coloured glass panes beyond a texture.

## Consequences

- Format 1 grows additively: one field with per-type fields, two components. The corpus (prefix `block-type-`), the Codecs, the plugin, the generator and the app move together. A block without `type` lowers, registers and ejects exactly as before.
- One `msm:block` element per family member keeps Studios, Raw JSON, references and the AI helper unchanged in shape; a family is a group of elements, not a container.
- Vanilla-dependent behaviour (connections, fire, villager and mob behaviour) works through the same tags vanilla uses; all of them are data and reload.
- `msm_runtime` gains its first `UseBlockCallback` and its first content registry calls (flammability).
- Vanilla pack safety ([ADR 0066](0066-vanilla-pack-safety.md)) needs no new rule: family blocks are mod-only ids, so their recipes and loot are left out of vanilla data packs and their tag entries (including the behaviour tags of D6) become `required: false`.
- A project with types needs the runtime release that ships this.
