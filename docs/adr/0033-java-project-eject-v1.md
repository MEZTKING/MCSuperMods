# ADR 0033: Java project eject v1 (`java-project` exporter)

## Context

Tier 2 ([Scripting and Escape Hatches](../DESIGN.md#12-scripting-and-escape-hatches)) is "Export as Fabric Java project": a one-way, deterministic, documented Gradle project with generated Java that mirrors what `msm_runtime` would have done, with no dependency on `msm_runtime` ([Targets and Exporters](../DESIGN.md#9-targets-and-exporters), exporter `java-project`). The ROADMAP asks for a CI check that the ejected kitchen-sink project builds with Gradle and for behaviour-parity GameTests against both the runtime jar and the ejected build. Facts (verified 2026-11-05 in the phase plan, deleted at phase close; it survives in git history): Gradle 9.8.2 is current and is the engine-mod wrapper (wrapper jar SHA-256 `3b8a2577…8e98`); Loom 1.19.3 is the latest 1.19 release (1.20 is alpha); Fabric Loader 0.20.1 and Fabric API 0.165.2+26.3 are the latest for 26.3; Loom 1.19.3 has the `include` configuration and `NestableJarGenerationTask`; Fabric API's gametest module runs tests on a production dedicated server when the JVM property `fabric-api.gametest` is set (`fabric-api.gametest.report-file`, `.filter`, `.verify` exist in 4.0.36). The generated Java names Mojang classes of one Minecraft version (`Identifier`, `BlockBehaviour.Properties.setId`, `FabricEntityType.Builder.createMob`), which are version facts.

## Decision

**D1. Scope of v0.6.** The eject covers everything `msm_runtime` v1 registers: `msm:block` (every component: `msm:breakable`, `msm:light_emitter`, `msm:on_interact`, `msm:on_step`, `msm:redstone`; block items and creative tabs; loot table override), `msm:item` (`msm:food`, `msm:tool`, `msm:durability`, `msm:on_use`), `msm:entity` (attributes, the six goal types including the runtime's `FollowTypesGoal` copied into the project, triggers, spawn egg, natural spawn, the GeckoLib bridge and client renderer) and every action (`run_function`, `spawn_particle`, `set_block_state`, `give_item`, `play_sound`, `trigger_event`, `play_animation`). **Scripts are not ejected**: `msm:script` elements and `run_script` actions are left out with one `export.scripts-not-ejected` warning per script naming it, and the generated README says so (a follow-up may copy the runtime's `scripting/` sources and nest Rhino). `assets/` and `data/` files are copied unchanged; `msm/` definitions do not appear in the output.

**D2. Layout of the generated project** (`<mod_id>/`, package `<java package>` = the mod id with `-` as `_`, prefixed `mod_` when it starts with a digit or is a Java keyword):

```
settings.gradle.kts, build.gradle.kts, gradle.properties, .gitignore, README.md, LICENSE-NOTES.md
gradlew, gradlew.bat, gradle/wrapper/gradle-wrapper.jar, gradle/wrapper/gradle-wrapper.properties
src/main/resources/fabric.mod.json, assets/**, data/**
src/main/java/<pkg>/<ModClass>.java            // ModInitializer: registers blocks, items, entities, tabs, spawns
src/main/java/<pkg>/ModBlocks.java, ModItems.java, ModEntities.java
src/main/java/<pkg>/block/<Name>Block.java      // one class per block with events or redstone state
src/main/java/<pkg>/item/<Name>Item.java        // one class per item with msm:on_use
src/main/java/<pkg>/entity/<Name>Entity.java    // PathfinderMob + GeoEntity, goals, triggers, controllers
src/main/java/<pkg>/entity/FollowTypesGoal.java // copied from the runtime when a follow goal exists
src/main/java/<pkg>/client/<ModClass>Client.java, entity/<Name>Model.java   // ClientModInitializer, GeoModel
src/main/java/<pkg>/Actions.java                // the six action helpers, straight-line Java with depth guard 16
msm.export.json
```

Gradle facts come from the target: `Target.fabric` (`loom`, `loader`, `api`, `minecraftDependency`, new `gradle`) and `Target.geckolib` (`implementation` and `include` of `maven.modrinth:geckolib:<modrinthVersionId>` from the Modrinth Maven, only when the project has entities). `fabric.mod.json` is the lowered one without the `msm_runtime` dependency, plus `entrypoints` `main` and `client`, with GeckoLib under `depends` when nested. The wrapper jar and scripts come from the host (`createJavaProjectExporter({ loadGradleWrapper })`, which the app serves from `engine-mod/gradle/wrapper/` in development and from the packaged `resources/runtime/gradle-wrapper/` staged by `stage-runtime.mjs`); without them the project is still written and `export.gradle-wrapper-missing` (info) tells the user to run `gradle wrapper`.

**D3. Where the Java generation lives.** The Java source generator is a target fact: `packages/targets/mc-26.3/src/java-project/` implements `Target.javaProject: JavaProjectGenerator` ([ADR 0034](0034-plugin-api-0.8.md)) and names every Mojang and Fabric class and member for 26.3 (the runtime's registrar, driver classes and GeckoLib bridge are the reference implementation and compile against the same jar). `@msm/exporters` `java-project/` owns the version-independent parts: reading the definitions from the `msm` layer, the Gradle files, the README, resource copying, the manifest, determinism and problems; it calls the target's generator with the parsed definitions. A target without `javaProject` reports `export.no-java-project-target`. The next target copies the generator folder and adjusts names, as it does with folder facts.

**D4. Determinism and one-way.** Files are written in sorted path order; content depends only on the project, the target and the MSM version in the manifest (no timestamps, no absolute paths). The app writes into `<picked folder>/<mod_id>/`, which must not exist or must be empty (`export.folder-not-empty` blocks otherwise), through a new main-process `exports.writeTree` that accepts a checked tree of relative paths (segments `[A-Za-z0-9_.-]+`, no `.`/`..`, depth at most 16, at most 4096 files). Edits to the generated project never flow back; the README says so and names the MSM version that produced it.

**D5. CI and parity.** The `engine-mod` CI job exports `fixtures/sample-mod/` and `fixtures/sample-mob/` as Java projects (the golden tests write them with `MSM_SAMPLE_MOD_JAVA_OUT` and `MSM_SAMPLE_MOB_JAVA_OUT`) and builds each with its own `./gradlew build --no-daemon` (the shared Gradle cache holds the 26.3 artefacts). Behaviour parity: `engine-mod/parity/` is a separate Gradle build (`cd engine-mod && ./gradlew -p parity build`) producing `msm_parity_tests.jar`, a GameTest mod written against the sample mods' public behaviour through vanilla APIs only (registry entries, block properties, interactions with a mock player, entity attributes and goals, spawn eggs, drops; no runtime classes). `tools/run-fabric-server --gametest <jar> --report <file>` runs a production dedicated server with `-Dfabric-api.gametest=true` and the report file; CI runs it twice per sample: with the content jar (runtime nested) and with the ejected build's jar. The same tests passing on both is the phase's exit-criterion proxy.

## Consequences

- A user who outgrows MSM gets a conventional Fabric project (Loom, Mojang names, Java 25) that builds as it stands and reads like hand-written code.
- The generator doubles the places a component's semantics are written (runtime Java and generated Java); the parity GameTests keep them equal, and every new component in later phases lands in both or is reported as not ejectable.
- CI grows by two Gradle builds and two server runs (estimated five minutes).
- Scripts remain runtime-only in v0.6.

## Status

Accepted (2026-11-05, Phase 6 close, B141). Implemented by B131 (spike, `engine-mod/parity/` skeleton, `run-fabric-server --gametest`), B136 (exporter and the 26.3 generator), B137a (`exports.writeTree`, the served wrapper, File > "Export Java Project…"), B137b (dialog), B139 (parity tests and CI) and B140 (e2e `eject-path`). Findings at close:

- The mod class is the mod id in Pascal case plus `Mod` unless it already ends so (`MsmSampleMod`, `MsmSampleMobMod`); the client entrypoint and `client/` exist only with entities.
- One parity jar holds both samples' tests (`SampleModParityTest`, 11 tests; `SampleMobParityTest`, 7 tests); each run selects its sample with `--gametest-filter`. The functions' effects are observed through `ServerMessageEvents.COMMAND_MESSAGE` (both sample functions `say` a line); sounds and particles stay unobserved.
- CI runs the four parity runs (content and ejected jar of each sample) in one `fabric-server-parity` folder; locally, warm, the added steps took about 4.5 minutes.
- `export.folder-not-empty` is a blocking problem built from `writeTree`'s `folder-not-empty` result, not a thrown error.

Findings of B131 (2026-11-05, eject and parity spike; Loom 1.19.3, Gradle 9.8.2, Fabric API 0.165.2+26.3, JDK 25.0.5):

- **GeckoLib nesting (D2).** In the non-remapping Loom, plain `implementation("maven.modrinth:geckolib:kSxHvs99")` plus `include(...)` of the same coordinates compiles against GeckoLib and nests it; no `mod*`-style configuration is needed or exists. The nested file is `META-INF/jars/geckolib-kSxHvs99.jar` (artefact id and Modrinth version id, not `geckolib-fabric-26.3-5.5.7.jar`), byte-identical to the Modrinth Maven artefact (it keeps its own `fabric.mod.json`, id `geckolib` 5.5.7, so Loom generates no metadata for it), and Loom adds `"jars": [{"file": "META-INF/jars/geckolib-kSxHvs99.jar"}]` to the built `fabric.mod.json`. `processIncludeJars` prints `(kSxHvs99) is not valid semver for dependency maven.modrinth:geckolib:kSxHvs99`, which is harmless (the version comes from the nested jar's own metadata); generated READMEs should mention it so users do not chase it. Fabric Loader resolves `msm_minimal 1.0.0 \-- geckolib 5.5.7` and a `"geckolib": ">=5.5.7"` entry under `depends` is satisfied by the nested copy. The hand-built project (one block through `BlockBehaviour.Properties.of().setId(key)`, one `PathfinderMob implements GeoEntity` through `FabricEntityType.Builder.createMob`, a `GeoEntityRenderer` registered through `EntityRenderers.register` in the client entrypoint) built and started a dedicated server to `Done (` with `tools/run-fabric-server --no-runtime`.
- **Build times** (`./gradlew build --no-daemon`, warm `~/.gradle` holding the 26.3 artefacts and GeckoLib, configuration cache on): first build of the new project 20.4 s; with the project's `.gradle/` cleared 12.3 s and 12.8 s; with `.gradle/` and `build/` cleared 12.7 s. A cold `~/.gradle` could not be measured: Maven Central answered 429 for Loom's own dependencies twice in the session container. The parity build (`./gradlew -p parity build --no-daemon`) took 24 s the first time and 9 s up to date; its jar is 2.7 kB.
- **Production-server GameTests (D5).** The `fabric-api` jar does not nest `fabric-gametest-api-v1` (its POM lists the module as a dependency, so development runs have it): a production server with the parity jar fails mod resolution until the module is in `mods/`. `tools/run-fabric-server --gametest` therefore downloads the module at the version Fabric API's POM names (4.0.36+3434d6d95d for 0.165.2+26.3), checked against its `.sha1`. With `-Dfabric-api.gametest=true` Fabric API's `MainMixin` replaces the dedicated server with Minecraft's `GameTestServer` (EULA check skipped, fresh `world/`); every registered test runs, Minecraft's `minecraft:always_pass` included; the server never logs `Done (`, stops by itself and exits with `MultipleTestTracker.getFailedRequiredCount()` (`GameTestServer.onServerExit`), -1 when no test is selected or the vanilla data pack fails, 1 on a crash; Fabric's `exitOnError` also exits -1. Measured: exit 0 with everything passing, exit 1 with one failed required test. `fabric-api.gametest.report-file` holds JUnit-like XML: `<testsuite><testsuite time timestamp>` with `<testcase classname="fabric-gametest-api-v1:empty" name="msm_parity_tests:sample_mod_parity_test_ruby_ore_is_registered" time>` and a `<failure message="(x, y, z) <assertion message> on tick 0"/>` child on failure. The runtime's `[msm_runtime] registered ...` lines appear before the tests, so the registration checks still apply to content jars.
- **Parity runs.** `engine-mod/parity/` (id `msm_parity_tests`, one test `rubyOreIsRegistered`) passed against the `fixtures/sample-mod` content jar with the real runtime (2 tests passed, 25 s) and failed, naming the test and its message, against the minimal ejected jar with `--no-runtime` (exit 1, 28 s). Server stack frames read `at knot//<class>`, so the tool's runtime-frame rule now accepts that prefix and leaves the parity tests' own frames to the report.
- **CI estimate for B139** (warm Gradle cache): parity build about 25 s, two ejected builds about 15 to 25 s each, four GameTest runs about 30 s each with one shared `--work` folder (each new folder downloads the game server again): about four minutes on this container, five to six on a GitHub runner, within the five minutes estimated above.
- Nothing in D2 needs to change for Loom; the generator should name the nested GeckoLib by coordinates, not by file name.
