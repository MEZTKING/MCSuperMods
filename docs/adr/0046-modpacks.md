# ADR 0046: Modpacks (collections of projects, exported and tested together)

## Context

One MSM project is one mod ([DESIGN §4](../DESIGN.md#4-core-project-model-ir)). The user asked (2026-11-06) for "modpack support, so everything you make can be organised", and chose both readings: collections that organise their projects, and a collection that can be exported or tested as a real Minecraft modpack. Until now each project was exported and tested on its own; Test in Minecraft installs one content jar (plus Fabric API) into one game location ([ADR 0026](0026-fabric-content-jar.md) D5), and nothing groups projects.

Facts checked on 2026-11-06:

- The Modrinth modpack format (`.mrpack`) as Prism Launcher reads it (`launcher/modplatform/modrinth/ModrinthInstanceCreationTask.cpp`, `develop`): a zip with `modrinth.index.json` (`formatVersion` 1 required, `game` `"minecraft"` required, `versionId`, `name`, `files[]` with `path`, `hashes.sha512` required, optional `env.client` `required | optional | unsupported`, `downloads[]`, plus `dependencies` with `minecraft` and `fabric-loader`), then `overrides/` and `client-overrides/` copied into the instance. Prism asks the user to trust any file whose download host is not Modrinth's CDN and any jar under `overrides/mods/`. The Modrinth support article and docs pages refused automated fetches; `hashes.sha1` and `fileSize` are written as Modrinth's own packs carry them (verify at implementation against an exported pack imported into Prism and the Modrinth app).
- Fabric API is Modrinth project `P7dR8mSH` (Apache-2.0); the 26.3 target's Fabric API `0.165.2+26.3` is version `nJlcvFfj`, `https://cdn.modrinth.com/data/P7dR8mSH/versions/nJlcvFfj/fabric-api-0.165.2%2B26.3.jar` (Modrinth API, 2026-11-06).

## Decision

- **D1 Modpack file.** A modpack is a folder holding `msm.modpack.json` (JSON, 2-space, sorted keys, like project files): `formatVersion` 1, `name`, `version` (free text, default `1.0.0`), `summary` (optional), `targetId`, `projects` (each `{ path }`: a project folder relative to the modpack folder with `/` separators, or absolute when on another drive) and `mods` (extra mods, each a pinned Modrinth file: `projectId`, `versionId`, `title`, `fileName`, `url`, `sha1`, `sha512`, `size`). Projects are referenced, never copied: one project can be in several modpacks, and editing it changes every modpack it is in. Parsing and writing live in `@msm/core` (`modpack.ts`), pure and validated (unknown keys kept out, safe relative paths, unique members).
- **D2 Organising.** The app remembers modpacks in `settings.json` (`modpacks`, like `recentProjects`, main only). **File → Modpacks…** opens the Modpacks dialog: the list of modpacks (create one in a new folder, add an existing one, forget one), and for the selected modpack its member projects with their state (found, Minecraft version, mod id, error count when last checked), **Add project…** (the open project, a recent one or a folder), **Remove**, **Open** (opens the project in the window), its details (name, version, summary, Minecraft version) and its extra mods. Opening a member project is the normal Open; the modpack stays in the list.
- **D3 Building.** A modpack build loads each member into a separate, read-only `ProjectSession` in the renderer (the same plugins and targets, no UI), runs the content-jar pipeline into memory with the default options (runtime and GeckoLib nested, as for one project), and disposes it. Members must use the modpack's target (`modpack.target-mismatch`, with Upgrade project target as the fix) and distinct mod ids (`modpack.duplicate-mod-id`); a member with errors, or one that is missing, blocks (`modpack.member-errors`, `modpack.member-missing`). Problems name the member project.
- **D4 Export as `.mrpack`.** **Export modpack (.mrpack)…** writes `<name>-<version>.mrpack`: `modrinth.index.json` with `formatVersion` 1, `game` `minecraft`, `versionId` (the modpack version), `name`, `summary`, `dependencies` `{ minecraft: target.mcVersion, fabric-loader: target.fabric.loader }`, and `files` for Fabric API (from the new target fact `fabric.apiModrinth`) and every extra mod, each with `path` `mods/<fileName>`, `hashes` (`sha1`, `sha512`), `env` `{ client: required, server: required }`, `downloads` `[url]` and `fileSize`; each member's jar goes to `overrides/mods/<mod id>.jar`. Output is deterministic (sorted entries, fixed timestamps). The exporter is a pure function in `@msm/exporters` (`modpack/mrpack.ts`); it does not download anything.
- **D5 Testing.** **Test modpack in Minecraft…** uses the Test in Minecraft dialog and location rules ([ADR 0026](0026-fabric-content-jar.md) D5) with every member jar: it installs them as `<mod id>.jar`, ensures Fabric API, downloads each extra mod once into the download cache (SHA-512 checked against the pinned value, like GeckoLib) and installs it, removes content jars and extra mods the app installed earlier that are not in this modpack (only files recorded in `mods/.msm-installed.json`, new role `extra`), then launches as before. The test instance stays **MCSuperMods Test (<version>)**.
- **D6 Extra mods.** **Add mod from Modrinth…** takes a Modrinth project slug, id or URL; main asks the Modrinth API for the newest version with loader `fabric` and the modpack's Minecraft version and pins its primary file (D1). The request carries the app's generic user agent, never personal data. Changing the modpack's Minecraft version marks pinned mods for another lookup (**Update mods**). The app never adds a mod's own dependencies by itself: the dialog lists the required dependencies Modrinth reports so the user can add them.
- **D7 Target facts.** `TargetFacts.fabric` gains the optional `apiModrinth` (`versionId`, `fileName`, `url`, `sha1`, `sha512`, `size`), verified per target like the GeckoLib facts. Plugin API 1.3.0, additive ([ADR 0036](0036-plugin-api-1.0-and-compatibility-policy.md) D1). A target without it cannot export a `.mrpack` (`modpack.no-fabric-api-file`); testing still works through the Fabric Maven download.
- **D8 Out of scope for 1.1.** CurseForge modpack export (needs an API key and their file ids), server packs, config files in overrides, local jar files that MSM did not build, and automatic updates of extra mods.

## Consequences

- Everything the user makes can be grouped, and a group is one file they can share or version with the projects.
- A modpack built from several MSM mods nests the runtime in each jar; Fabric's jar-in-jar keeps one copy at run time, so the cost is download size only.
- Importing an exported `.mrpack` in Prism or the Modrinth app shows their "untrusted files" prompt for the member jars, because those are not hosted on Modrinth. The guide says so; publishing the mods on Modrinth (later) removes it.
- Main gains Modrinth API calls (metadata and file downloads only); tests inject the downloader as elsewhere.

## Status

Accepted (2026-11-06) by the user's request; implementation planned for 1.1.0 (`docs/MODPACKS-PLAN.md`).
