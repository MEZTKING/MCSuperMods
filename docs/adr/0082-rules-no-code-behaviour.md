# ADR 0082: Rules, behaviour without code

## Context

The user asked (2026-11-14) for "an easy to use, very easy to use mode ... something like blueprints ... like Scratch ... anyone can build anything", then clarified: "it doesn't have to be scratch style. Do your own style. Just something where coding isn't necessary. Just an option for people that don't want to code." This ADR decides that style and how it fits the existing model. [ADR 0083](0083-very-easy-mode.md) decides the Very easy mode around it and [ADR 0084](0084-one-click-play-and-reload.md) the one-click test. Facts (F1–F24) and limits (R1–R22) are in this ADR's findings (the batch's plan, `PLAN-blocks-and-play.md`, was deleted at close).

What MSM has today:

- **Tier 0, events and actions** ([ADR 0025](0025-msm-definition-format-v1.md), [ADR 0028](0028-entity-definition-format-v1.md), [ADR 0061](0061-more-triggers.md)): trigger components on blocks, items, mobs, effects, containers, machines and portals name one event each; an event is a flat, ordered list of actions (`play_sound`, `spawn_particle`, `run_function`, `set_block_state`, `give_item`, `trigger_event`, `run_script`, `apply_effect`, `launch`, `damage`, `heal`, `play_animation`, `light_portal`). There are no conditions, loops, variables or waits. The shared `EventsEditor` edits them as forms with ids and option lists.
- **Tier 1, scripts** ([ADR 0031](0031-rhino-runtime-and-typescript-es5-scripts.md), [ADR 0032](0032-script-api-v1-and-typings.md), [ADR 0062](0062-persistent-script-data.md), [ADR 0065](0065-script-api-1-1.md), [ADR 0076](0076-container-and-machine-flows-studio-and-script-api.md), Script API 1.3 from [ADR 0080](0080-custom-particle-types.md)): TypeScript with logic, saved data per player, mob and world, 19 game events, and the `run_script` bridge from any definition event. Scripts reload on `/reload`; the Java eject leaves them out.
- **The Creator** ([ADR 0043](0043-creator-guided-flows.md)) makes whole things from questions, but behaviour beyond the flows' fixed choices needs the events editor or code.

The options weighed for a no-code behaviour editor:

| Style | For | Against |
|---|---|---|
| Stacked blocks (Scratch, Google Blockly 13.4.0, Apache-2.0) | Familiar to children; logic is visible | Drag precision and a canvas to manage; a whole second visual language beside the Studios; Blockly is a large dependency (17.6 MB unpacked on npm, roughly 1 MB minified with messages and media) for a 32 MB asar at 26.9 MB; its keyboard and screen-reader support is a separate plugin; the user said it need not be Scratch |
| Node graphs ("blueprints", for example React Flow 12.12.1, MIT) | Good for data flow and big systems | Wires, layout and zoom are hard for beginners; sequences ("do this, then that") read badly; poor keyboard and screen-reader story; one more dependency |
| Plain forms (today's `EventsEditor`) | Already built, exact | Field-centric and id-centric, no logic, reads like a file format |
| **Sentence cards** ("When a player right-clicks Ruby Block, if they are sneaking, give them 2 Rubies and play Chime") | Reads like the guide; every blank is a picked choice with a picture; linear like a recipe; works with keyboard and screen readers as ordinary buttons and lists; maps one to one onto triggers and actions and, where needed, onto generated script code; small, in-house, no new dependency | Deep nesting is less visual than blocks (capped on purpose) |

## Decision

- **D1 Style and name.** MSM's no-code behaviour editor is **Rules**: a list of **rule cards**, each a plain-language sentence in three parts, **When** (one trigger), **Only if** (optional conditions, "all of these" or "any of these", each can be turned into "not"), and **Do** (an ordered list of steps). Every blank in a sentence is a chip that opens a picker with pictures and words (project things first, then vanilla things by category, with search); numbers are steppers with words ("2 seconds", "25% of the time"); text is typed only where text is the point (a message or a title). Logic steps nest: "If ... then ... otherwise ...", "Repeat N times", "For each player nearby", "Wait N seconds"; nesting is at most 3 levels deep and a rule has at most 50 steps (the editor stops adding past these, and the validator reports hand-edited files). Rules are an option beside the existing editors, never a replacement: the events editor, scripts and Raw JSON stay as they are in every mode. Stacked blocks and node graphs are not built (Context); the vetoable default is the name "Rules" (cards "Rule", the element's editor "Rule book").
- **D2 Storage: a new kind `msm:rules`.** A rule book is an ordinary element of kind `msm:rules` (folder `rules`, no registry), owned by a new built-in plugin `@msm/plugin-rules` (plugin id `msm.rules`, made with `tools/new-plugin`), saved as JSON with sorted keys like every element. Shape (MSM mcdoc `::msm::rules::RuleBook`, `packages/schemas/mcdoc/msm/rules.mcdoc`):
  ```json
  {
    "counters": [{ "name": "clicks", "scope": "player", "start": 0 }],
    "format": 1,
    "rules": [{
      "do": [
        { "count": 2, "item": "mymod:ruby", "step": "give_item", "who": "player" },
        { "sound": "minecraft:block.note_block.chime", "step": "play_sound", "where": "here" }
      ],
      "key": "ruby_gift",
      "name": "Ruby gift",
      "only_if": { "conditions": [{ "condition": "player_sneaking" }], "match": "all" },
      "when": { "subject": "mymod:ruby_block", "trigger": "block_used" }
    }]
  }
  ```
  `key` is stable (`[a-z0-9_]{1,32}`, unique in the book) and names generated ids; `enabled: false` keeps a rule without effect. A number slot takes a number or a value object (`{ "value": "random", "min", "max" }`, `{ "value": "counter", "counter", "scope" }`, `{ "value": "player_health" }` and the other readings of D4, `{ "value": "math", "op": "+|-|*|/", "a", "b" }` at most two deep); a text slot takes a list of strings and value objects. A project has as many rule books as it likes; the Studios' Rules sections (D7) add to `<namespace>:rules`, created on first use.
- **D3 Compilation, done at lowering time, never stored twice.** The rule book is the only source. The plugin's **compiler** (`compileRuleBook(book, elements, target)`, pure) produces two things:
  1. **Patches to the subjects' definitions**, applied to a copy of each subject element before it is lowered, validated or ejected, through a new plugin API contribution `contributes.projectExpanders` (plugin API 1.15.0; D9). For each subject and definition trigger used by enabled rules the patch adds one event `<subject id>_rules_<trigger>` and sets the trigger component to it. When every enabled rule on that subject and trigger is **plain** (no conditions, every step one of the format's actions with a matching target), the event holds those actions in rule order; otherwise it holds one `run_script` action whose handler is `<namespace>:rules/<book path>/<subject path>/<trigger>`. When the subject already has a hand-made event on that trigger, the generated event starts with `trigger_event` to it, so hand-made behaviour keeps running first. Trigger options (interval, cooldown, chance, hand) are one per subject and trigger: the subject's own component values win, else the first rule's (R16).
  2. **One generated TypeScript script** per book that needs one, lowered by the rules plugin itself as `msm/<ns>/script/rules/<book path>.ts` (`language: 'typescript'`, so the content jar exporter transpiles it like any script): `msm.actions.define` handlers for the `run_script` bridges, and `msm.events.on(...)` for script-only triggers (D4). The code is readable: a header ("Made by Rules from <book id>; edit the rules, not this file"), one comment per rule with its sentence, and a `// rule:<key>` marker per statement so runtime script errors (logged with id and line) map back to a rule.
  The alternative, writing the compiled events and a script element into the project on every edit (as the Creator writes ordinary elements), is rejected: it stores everything twice, needs drift checks on hand edits and a choke point on every changeset. Consequence: the Events editor does not show rule events as editable; it lists them read-only under "From rules" with a link (D7).
- **D4 Triggers.** Definition triggers (subject is a project block, item, mob, effect, container or machine block, or portal): block used, stepped on, broken, placed, random tick, entity inside, powered, unpowered, opened, closed, machine starts, machine finishes, portal travel; item used, used on a block, hits a mob, held (every N seconds, hand), worn, thrown item hits a mob, hits a block; mob hurt, dies, used, attacks, every N seconds, spawns; effect starts, every N seconds, ends. Script-only triggers: a player joins, leaves, respawns, chats (with "message contains"), changes dimension, every N seconds for each player; the world starts; every N seconds; and **vanilla subjects** ("a player breaks any Stone", "a player right-clicks a vanilla block or uses a vanilla item", "any Zombie is hurt or dies") through `block.break`, `block.interact`, `item.use`, `entity.damaged`, `entity.death` and `entity.interact` filtered by id. A trigger offers only the actors it has (a random tick has no player): the pickers hide what a trigger lacks, and the compiler reports `rules.no-such-actor` on a hand-edited file.
- **D5 Steps, conditions and values (version 1 catalogue).** Grouped as the picker shows them; "(A)" marks a step that compiles to a format action when its target matches, the others compile to script.
  - **Players:** give item (A), take item, heal (A), hurt (A), feed, give experience points or levels, set game mode, teleport to a place, launch (A), show a chat message, show a title, show action bar text, give an effect (A), remove an effect.
  - **World:** place a block (A: `set_block_state`), remove a block, spawn a mob, drop an item, make an explosion, set the weather, run a function (A), run a command (hidden in Very easy), light a portal (A).
  - **Sounds and particles:** play a sound (A), spawn particles (A; project particles first, dust colour through ADR 0080's options objects).
  - **Mobs:** play an animation (A, own mobs), hurt, heal or remove the mob, show or update a boss bar.
  - **Logic:** if / otherwise, repeat N times (at most 100), for each player nearby (radius at most 64) or every player, wait N seconds, stop the normal action (only on cancellable script events: block use and break, item use, mob use and hurt, chat).
  - **Counters:** set, add to, take from a named counter for the player, the mob or the world (saved through the Script API data stores, so they survive a restart, ADR 0062).
  - **Conditions:** the player is sneaking, is in creative, holds an item, has at least N of an item, health, food or level compared with a number; a chance in percent; day or night; raining or thundering; the block at a place is a block; the other entity is a kind of mob; the dimension is; a counter compared with a number or another counter.
  - **Places and who:** here, above here, at the player, at the mob, where the player looks (up to N blocks), and an offset (hidden in Very easy); the player, the mob, the other, every player, every player nearby.
  - **Values:** a number, a random number between two, a counter, the player's health, food, level or position part, the number of players, the time of day, and one level of + − × ÷.
  Steps the Script API cannot do yet are added as **Script API 1.4** (runtime version at implementation): `World.isRaining`, `World.isThundering`, `World.dayTime`, `World.setWeather(kind, seconds?)`, `World.explode(pos, power, options?)`, `World.dropItem(pos, item)`. Nothing compiles to `runCommand` except the "run a command" step.
- **D6 Problems on the card.** The rules plugin's validators (`msm.rules.*`, codes `rules.<check>`) check a book against the project: unknown subject or picked id, a trigger the subject's kind does not have, an actor the trigger lacks, an unknown step, condition or value (`rules.unknown-step`, from a newer MSM: kept, shown as "Unknown step", blocks export), too deep or too long, duplicate keys, a generated event id that clashes with an existing one, counters used but not declared (warning; declared on first use by the editor), a book whose rules need a script on a target without one. Problems carry `elementId` plus an RFC 6901 pointer (`/rules/2/do/1/item`), so the card highlights the chip and shows the plain-language text ([ADR 0083](0083-very-easy-mode.md) D5). Problems found while lowering a patched subject (schema or `run_script` checks) carry the patch's origin and point at the rule, not at the subject.
- **D7 Where Rules appear.** (a) `msm:rules` elements open the **Rule book** (a lazy Studio in `app/src/renderer/src/studios/rules/`), with "Add a rule", reorder, turn off, duplicate, and a "What this becomes" drawer in Advanced mode showing the generated events and script read-only. (b) The Block, Item, Mob and Effect Studios gain a **Rules** section listing the rules whose subject is this element, with "Add a rule" (the When chip pre-filled). (c) The events editor shows the subject's rule events read-only under "From rules" and offers **"Turn into rules"** on a hand-made event whose actions all map to steps (one undo step: the rules are added, the event removed, the trigger left to the rules). (d) Advanced mode offers **"Copy as my own script"** on a book (one undo step: a normal `msm:script` with the generated code; the book is turned off). The shared **ThingPicker** (pictures of project things from the existing thumbnails, vanilla items, blocks and spawn eggs from the extracted client jar, ADR 0011; a generic icon and the name without it) is a separate component reused by [ADR 0083](0083-very-easy-mode.md). Every edit is one undoable command; text typing coalesces as in the forms.
- **D8 Versions.** `format: 1` for the book; the step, condition, trigger and value ids are the format, each new id is additive within format 1, and a removed or changed meaning is a format 2 with a migration in `@msm/core`'s migration chain. Rules work on both targets; the catalogue names no version fact (picked ids come from the target's registries and the project).
- **D9 Plugin API 1.15.0.** New optional contribution `projectExpanders?: ProjectExpander[]` with `ProjectExpander { id: string; kinds: readonly string[]; expand(input: { elements: readonly Element[]; target: TargetFacts }): MaybePromise<ExpansionResult> }` and `ExpansionResult { patches: ElementPatch[]; problems: Problem[] }`, `ElementPatch { elementId: string; path: readonly (string | number)[]; value: Json; origin: { elementId: string; pointer: string } }`. `@msm/core` applies patches (later patches on the same path are a `core.expansion-conflict` error) to copies of the elements before lowering, validation, export and eject, never to the saved project. Plus `TargetFacts.dev?: DevFacts` for [ADR 0084](0084-one-click-play-and-reload.md). Built-in plugins still declare `^1.0.0`.
- **D10 Java eject, vanilla packs, AI helper.** The eject receives the expanded project, so plain rules eject as events; rules that need a script are not ejected (scripts are left out of the eject), and the Export Java project dialog lists them (`rules.not-in-eject`, warning). Vanilla packs carry no rules (they need the Fabric mod jar, R8); exporting a vanilla pack from a project with rules shows `rules.needs-jar` (info). The AI helper writes rule books like any element (`create_elements` with kind `msm:rules`; its schema summary lists the catalogue ids); its system prompt prefers rules over scripts for beginner requests and over hand-made events when logic is needed; `run_checks` lowers the expanded scratch project.
- **D11 Library.** Templates in the rules plugin (category "Rules"): "Welcome message", "Jump pad", "Lucky block", "Healing spring", "Click counter", "Mob drops a reward". Examples in the library: "Rules: a lucky block" (block, item and a book with chance, random reward and a counter) and "Rules: a guard mob" (mob with every-N-seconds and for-each-player-nearby). Both create with zero problems on both targets.

## Consequences

- Beginners get logic (if, repeat, wait, counters, maths) without code; power users can read the generated script and take it over.
- Rule edits on an existing trigger can be reloaded in a running test game ([ADR 0084](0084-one-click-play-and-reload.md) D6); a rule that adds a trigger to a thing needs a restart (R2).
- One new plugin, one new kind, plugin API 1.15.0 and Script API 1.4; no new runtime format and no runtime change for rules themselves: the runtime sees ordinary events and scripts.
- The expander is a general mechanism other plugins may use; its patches are invisible in saved files by design.

- **Format** (D2, D4, D5, D8; B363). `packages/schemas/mcdoc/msm/rules.mcdoc`, module `::msm::rules`: `RuleBook { format: 1, rules, counters? }`, `Counter { name, scope player|mob|world, start? }`, `Rule { key, name?, enabled?, when, only_if?, do }`, `When { trigger, subject?, options? }`, `Conditions { match, conditions }`; dispatchers `msm:rule_trigger`, `msm:rule_condition`, `msm:rule_value`, `msm:rule_step`, `msm:rule_logic_step`, `msm:rule_logic_step_nested`. Version 1 has 43 triggers (definition triggers require `subject`, player and world triggers take none, `any_*` take an optional one), 36 steps, 16 conditions and 9 values; logic steps (`if { match, conditions, do, else? }`, `repeat { times 1..100, do }`, `for_each_player { radius?, do }`) only at levels 1 and 2, level 3 plain steps only, lists up to 50; 362 exported mcdoc types; an editor-only kind with no runtime corpus. The `if` step uses `do`, not `then` (an object with `then` is a thenable). Trigger option `chance` is 0..1, the condition `chance` uses `percent`. `MSM_SCHEMA_REFS.rules` is `msm:rules`.
- **Catalogue and compiler** (D3–D5; B365, B368). `@msm/plugin-rules` exports the catalogue (`TRIGGERS`, `STEPS`, `CONDITIONS`, `VALUES`, `PLACES`, `WHO`, `CATALOGUE_IDS`; each entry with `label`, `sentence`, `slots`, `actors`, `actorLabels`, `veryEasy`, `cancellable`), the caps `MAX_DEPTH` 3, `MAX_STEPS` 50, `MAX_REPEAT` 100, `MAX_RADIUS` 64, `MAX_EXPLOSION_POWER` 10, `MAX_DROP_COUNT` 64, `MAX_WEATHER_SECONDS` 1000000, and `compileRuleBooks(books, elements, target) -> { patches, scripts, problems }`. Books compile together in id order: books sharing a subject and trigger share one event (a hand-made event first, then each book's part in id order). Generated ids are `<subject id>_rules_<trigger>` (event) and `<book ns>:rules/<book path>/<subject path>/<trigger>` (handler); patch origins are `/rules/<first rule index>`. Generated scripts type-check against `msm-runtime.d.ts` and transpile to ES5; 116 compiler goldens. Runtime choices: counters `rules.counter.<name>` in `player.data`, `mob.data` or `msm.storage`; boss bars `rules_<bar>`; night is day time 13000–23000; each rule runs in try/catch and logs `Rules <book>, rule <key>: <error>`; after a wait a rule stops when its player or mob is gone.
- **Deviations from D4 and D5.** `any_mob_hurt` compiles to the cancellable `entity.hurt`, not `entity.damaged` as D4 said, so "Stop the normal action" works on it. "Remove the mob" compiles to Script API 1.4's `Entity.remove()` (no loot, experience or death events; mobs only, players are skipped) and "Remove a block" to `world.breakBlock(pos, { drops })`; Script API 1.4 grew `Entity.remove()` and `breakBlock` beyond D5's six members for this (orchestrator decision during B365), so no "drops not supported" warning remains. Explosion power is clamped to 0..10, also when computed; "Light a portal" needs a plain rule.
- **Kind, expander, lowering and validators** (D2, D3, D6; B368). Kind `msm:rules` (folder `rules`, default `{ counters: [], format: 1, rules: [] }`, `hiddenPaths ['/generated_script']`); the expander `msm.rules.expand` (kinds `msm:rules`, `msm:block`, `msm:effect`, `msm:entity`, `msm:item`) writes each book's script to its expanded copy at `generated_script`, and `lowerRuleBook` writes `msm/<ns>/script/rules/<book path>.ts` (layer `msm`, `language: 'typescript'`; the content jar transpiles it, F24 confirmed). Validator `msm.rules.book` (kinds `msm:rules`, `msm:script`): errors `rules.duplicate-key`, `bad-counter-name`, `duplicate-counter`, `unknown-subject` (for `any_` triggers, against the `block`, `item` and `entity_type` registries), warnings `rules.undeclared-counter` and `script-path-clash`; with the compile codes `RULES_PROBLEM_CODES` holds 22 codes. Six templates in category "Rules" (`msm_rules_welcome_message`, `jump_pad`, `lucky_block`, `healing_spring`, `click_counter`, `mob_reward`). The plugin declares `^1.0.0` like every built-in.
- **Plugin API 1.15.0 and core** (D9; B364, B367). `PluginContributions.projectExpanders` as decided, plus the rules documented in the API: missing parents are created, an empty path replaces `data`, the same path twice is an error. `@msm/core` `expandProject` (async) and `expandProjectSync`, `expansionOriginKey(elementId, pointer)` (`<id>#<pointer>`), `originForProblem` (deepest covering patch), `mapProblemsToOrigins`; `LowerProjectOptions.plugins`; codes `core.expansion-conflict` (the first value is kept), `core.expansion-failed` (one error per element of the expander's kinds), `core.expansion-invalid-patch`. Every expander sees the saved elements; patched elements are deep copies.
- **The app session** (D3, D6, D10; B371). `project-session.ts` expands once per path (live validation, `checkProject` and the AI's `run_checks`, every export, Test in Minecraft, modpacks, plugin exporters, the eject), cached per project state and target; problems are mapped to origins after hidden paths are filtered, so `/generated_script` never shows. Generated scripts are checked live and their diagnostics land on the book at `/rules/<i>` through the `// rule:<key>` markers ("The script Rules made for <book>, line N: ..."). `rules.*` compile codes and `core.expansion-*` block exports that package the `msm` layer, not vanilla packs. Session codes `rules.needs-jar` (info, on both vanilla packs) and `rules.not-in-eject` (warning, per enabled rule that needs a script). `session.rulesView` gives rules and rule events per subject.
- **Editors** (D1, D7; B372, B375). The Rule book Studio (`studios/rules/`, lazy, 54.6 kB) with chips as buttons named "<slot>: <words>", custom cards for `if`, `repeat` and `for_each_player`, "all"/"any" conditions with "Not", counters declared on first use, Alt+Up and Alt+Down to move, one undo step per edit with typing coalesced, and "What this becomes" (Advanced). The shared `ThingPicker` (`components/thing-picker/`, sorts item, block, mob, sound, particle, effect, function, dimension; 48 tiles per section). The Rules section in the Block, Item, Mob and Effect Studios (lazy, above Events; the default book `<ns>:rules` is made in the same undo step), the read-only "From rules" list and "Turn into rules" in the events editor (offered only when the event round-trips), and the Export Java dialog's list of rules not in the eject. **"Copy as my own script" (D7 d) is not built**; the guide calls it planned and points at "What this becomes".
- **Library** (D11; B377). Examples `example_msm_rules` "Rules: a lucky block" and `example_msm_rules_guard_mob` "Rules: a guard mob" (category "Rules", Fabric only), mirrored in `examples/rules/`; `library.test.ts` expands every project with all plugins and checks the generated scripts and the jar's events. 134 examples in all.
- **AI helper** (D10; B382). The system prompt's "Rules" paragraph lists the catalogue by hand; `RULES_PROMPT_IDS`, `RULES_PROMPT_PLAIN_STEPS` (11), `RULES_PROMPT_CANCELLABLE` (6) and `RULES_PROMPT_TEMPLATES` (6) are pinned against the catalogue by `app/test/ai-rules.test.ts`, with a build-mode scenario "a lucky block made with rules". ### Limits

| # | Limit | Why | What users see | Mitigation |
|---|---|---|---|---|
| R1 | **New things need a game restart.** | Registries freeze at start (DESIGN §10). | Reload says "Restart needed" with the reason. | One-click Restart (ADR 0084 D5). |
| R2 | **A rule that adds a trigger to a thing needs a restart; changes inside an existing trigger reload.** | Components and triggers are part of the frozen definition; only event action lists and scripts are swapped in dev mode. | The first rule on "when broken" restarts; later edits reload. | Generated event ids are stable per subject and trigger. |
| R3 | **World data needs the world reopened; terrain changes show only in new chunks.** | Registries loaded with the world (`TargetFacts.dev.worldDataFolders`, 53 on 26.3, 54 on 26.4). | The world is reopened instead of reloaded. | Automatic reopen; a reopen also refills the chests. |
| R4 | **Removing a file needs a restart.** | An overlay cannot remove what the installed jar holds. | Restart needed with the reason. | One click. |
| R5 | **The client side of Play is checked in CI, the launcher and Windows are not.** | `MsmDevClientGameTest` covers the hooks (F23); Prism, sign-in, the jar lock and the restart round trip need Windows. | Launcher and lock problems reach the user first. | e2e with a stub launcher; the `fixtures/sample-rules` README checklist. |
| R6 | **Play needs Prism Launcher signed in to a Microsoft account.** | MSM cannot sign in; the official launcher and CurseForge cannot be told to start an instance. | A one-time setup panel. | "Find Prism"; Test in Minecraft stays for others. |
| R7 | **Play while the game runs restarts it; an unresponsive game must be closed by hand.** | The running game locks its jar on Windows (F19). | "Close Minecraft, then press Play again." | Quit request with a 30-second wait. |
| R8 | **Rules need the Fabric mod jar.** | They compile to runtime events and scripts. | Vanilla packs carry no rules (`rules.needs-jar`). | Info line on export. |
| R9 | **Rules with logic are not in the Java eject.** | Scripts are left out of the eject (F22). | The eject dialog lists them (`rules.not-in-eject`). | Plain rules eject as events; "Copy as my own script" is planned, "What this becomes" shows the code today. |
| R10 | **Some moments have no trigger.** | No event for crafting, picking up, eating, sleeping, advancements, keys or the HUD (client side is backlog B15). | Not offered in the When picker. | Recorded for later triggers. |
| R11 | **Script limits apply to logic rules.** | 2000 ms per call, waits in server ticks, data store size; the caps of D1 and D5. | Very long repeats are stopped by the editor. | Caps and validator codes. |
| R12 | **Pictures of vanilla things need the client jar.** | Mojang assets are never bundled (ADR 0011). | Names with a generic icon. | A line pointing at Settings, Game locations. |
| R13 | **Vanilla sounds cannot be previewed.** | Sound files are not in the client jar. | Vanilla sounds show a name only. | None. |

| R17 | **Quick play cannot create a world.** | F2. | None. | The runtime's title screen hook creates the world. |
