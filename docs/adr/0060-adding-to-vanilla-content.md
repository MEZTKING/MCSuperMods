# ADR 0060: Adding to vanilla content

## Context

A project can only add new things today. It cannot put its ore into vanilla biomes, add a drop to a vanilla mob, make an item burn or compost, or offer a trade to a vanilla villager, except by replacing whole vanilla files (coverage audit backlog B3, and the data half of B9). Facts read on 2026-11-13 (the plan with the full fact table was deleted at close and its findings live in this ADR; sources: `javap` over the Loom-cached merged jars for 26.3 and 26.4-snapshot-7, `javap` over the pinned Fabric API module jars, data files in the 26.3 game jar, the vendored mcdoc, this repository):

- Fabric `BiomeModifications` (`addFeature`, `addSpawn`, `addCarver`; `BiomeSelectors.tag`, `includeByKey`, `foundInOverworld`) has the same API on 26.3 and 26.4. Modifications are applied when a server starts, so they are fixed per world load and never reload. The runtime already uses it for natural spawns of project mobs.
- `LootTableEvents.MODIFY` (`modifyLootTable(ResourceKey<LootTable>, LootTable.Builder, LootTableSource, HolderLookup.Provider)`) is identical on both. It fires on every data pack load, so additions are reloadable. A data pack alone can only replace a whole table.
- Fuel and composting are item data components in 26.3 (`minecraft:cooking_fuel`, `minecraft:compostable`, `minecraft:brewing_fuel`), not code registries. Their values may be a constant or a key of a `context_int_provider`. Same on 26.4.
- Fabric API has no fuel, compost or trade helper in these builds, and `fabric-content-registries-v0` is absent from the 26.4 build.
- Trades are data: registries `villager_trade` and `trade_set`, and tags `minecraft:<profession>/level_<1..5>` and `wandering_trader/{buying,common,uncommon}`. A tag file with `replace: false` adds a trade to a vanilla villager with no code. A trade set draws `amount` trades from its tag, so an added trade is a candidate, not a certainty. Same folders on 26.4.
- The Custom ore starter makes a block, a gem, a loot table, recipes, a tag and advancements, but no `worldgen/feature` and no `worldgen/placed_feature`, although the worldgen plugin has both kinds.

## Decision

- **D1 Route per addition, chosen by the facts above.** Features and spawns into vanilla biomes: a runtime kind over `BiomeModifications`. Extra drops: a runtime kind over `LootTableEvents.MODIFY`. Fuel and composting: vanilla components on the project's own items, no runtime code. Trades: vanilla data kinds and a tag, no runtime code, valid in vanilla packs. No mixin anywhere.
- **D2 `msm:biome_addition`** (kind in `@msm/plugin-blocks-items`, folder `biome_addition`, lowered to `msm/<ns>/biome_addition/<path>.json`): `{ format: 1, biomes: [#[id(registry="worldgen/biome", tags="allowed")] string] @ 1.., features?: [{ feature: #[id="worldgen/placed_feature"] string, step }], spawns?: [{ entity: #[id="entity_type"] string, category: MobCategory, weight: int @ 1.., min_group, max_group: int @ 1.. }] }`, where `step` is one of the eleven generation steps in lower case. At least one of `features` and `spawns` is required. The runtime registers one `BiomeModifications` call per entry at initialisation, with the selector code that natural spawns use today moved into a shared helper. An unknown biome, tag, placed feature or entity type is a late warning after start, as for spawns today. The result is frozen per world load, and only new chunks get the features; the guide says so.
- **D3 `msm:loot_addition`** (same plugin, folder `loot_addition`): `{ format: 1, tables: [#[id="loot_table"] string] @ 1.., pools: [<vanilla loot pool>] @ 1.. }`. The runtime keeps each pool as JSON and decodes it with `LootPool.CODEC` over the `HolderLookup.Provider` of every `MODIFY` call, so project items, enchantments and predicates resolve and additions survive `/reload` without doubling. They apply when `source.isBuiltin()`: a world data pack that replaces the table wins, as Fabric recommends (default, vetoable). A pool that fails to decode is one logged error per load and is skipped.
- **D4 Fuel and composting.** Element-only fields on `msm:item` and on the block's `item`: `fuel?: { burn_seconds: float @ 0.05.. }` and `compost?: ("30%" | "50%" | "65%" | "85%" | "100%")`, lowered to `minecraft:cooking_fuel { burn_time: ticks }` and `minecraft:compostable { layers: <provider id> }` inside `msm:components` (the editor-only pattern of [ADR 0059](0059-block-shapes-and-see-through-blocks.md) D2). The chance-to-provider table is a target fact: the five provider files are read at implementation (verify at implementation). The definition gains `BlockItem.components?` with the same passthrough as items. That the two components decode at initialisation, without the delayed list of `ComponentPassthrough`, is to be proven by a GameTest (fallback: add both to `DELAYED`). There is no friendly field for `brewing_fuel` (passthrough only).
- **D5 Trades.** `@msm/plugin-datapack` gains the generic kinds `minecraft:villager_trade` and `minecraft:trade_set` and the tag registry `villager_trade`; both targets gain the two data folders. "Add to a villager" is a tag element `minecraft:<profession>/level_<n>` (or `wandering_trader/common`); the existing tag merge keeps `replace: false`. The guide states the limit (a candidate among `amount`), and that a guaranteed trade means a project `trade_set` override, which replaces vanilla's. The Creator flow "Villager trade" (profession, level, price, product) goes in the existing `worlds` Creator group (decided 2026-11-13; no new group).
- **D6 Custom ore generates.** The Custom ore and Scripted ore starters add a `worldgen/feature` (ore, targets `#minecraft:stone_ore_replaceables` and `#minecraft:deepslate_ore_replaceables`), a `worldgen/placed_feature` and an `msm:biome_addition` for `#minecraft:is_overworld`, step `underground_ores`. A new wizard step "World" offers generate (on by default, vetoable), vein size, veins per chunk, lowest and highest Y. With "generate" off the output equals today's byte for byte; existing projects are unchanged until the flow is reopened. A second flow, "Extra drop" (mob, block or chest table; item, count, chance, player kill only), writes an `msm:loot_addition`.
- **D7 Vanilla packs.** The two `msm:` kinds lower only into the jar's `msm/` layer, as blocks and items do; the starter text and the guide say that world generation and extra drops need the Fabric mod export. Trades and the feature files are plain data and stay in the data pack.
- **D8 Plugin API 1.8.0 (additive).** `DataFolderKey` gains `villager_trade` and `trade_set`; `JavaProjectInput.biomeAdditions?` and `lootAdditions?: DefinitionInput[]` ("Since 1.8.0", absent means empty); `TargetFacts.items.compostProviders?: Record<string, string>`.
- **D9 Java eject (26.3).** `ModWorldgen.java` makes the same `BiomeModifications` calls and `ModLoot.java` embeds the pools as JSON text decoded in a `MODIFY` listener, with the same source rule. Fuel and compost need nothing (components).
- **D10 Versions.** Shared runtime code only; no seam. Nothing uses `fabric-content-registries-v0`.
- **D11 Deferred, stated so nobody expects them:** flammable blocks, strip, wax and oxidise pairs (the Fabric module is missing on 26.4: needs a seam or a mixin), fuel or compost values on vanilla items (`DefaultItemComponentEvents`), custom compost chances (a `context_int_provider` kind, audit B11), removing vanilla features or spawns, carvers, new professions and POI types, a bespoke Loot Studio.

## Consequences

- Format 1 grows additively: two definition kinds, `BlockItem.components`, two element-only fields. The corpus (prefixes `biome-addition-`, `loot-addition-`, `block-item-components-`), the Codecs and the eject generator move together.
- Plugin API goes from 1.7.0 to 1.8.0, additive.
- Generated features reach new chunks only, and a world data pack that replaces a loot table hides the extra drop. A new trade is a candidate, not a guarantee. All three are documented in the guide.
- The world-generation and loot additions need the Fabric mod export; vanilla pack export carries trades only.
- Existing projects and the Custom ore output with "generate" off do not change.

## Status

Accepted (2026-11-14). Defaults the user may veto: additions never override a world data pack; a new trade is a candidate, not a guarantee; Custom ore generates by default in new projects; the kind names `msm:biome_addition` and `msm:loot_addition` and the Studio labels "World addition" and "Extra drops".

Runtime findings (B234, 2026-11-14; 151 GameTests on 26.3, 26.3 without GeckoLib and 26.4):

- `minecraft:cooking_fuel` (with the required `speed_multiplier`, lowered as 1) and `minecraft:compostable` (a provider key) decode at initialisation through the `msm:components` passthrough; neither needs `DELAYED`.
- Fabric's `BiomeModifications` throws for an unregistered placed feature and would stop the server, so the runtime adds each feature through `BiomeModifications.create(id).add(ADDITIONS, …)` after looking the key up in `selection.getRegistryAccess()`; a missing feature, biome, tag, entity type or loot table is a warning after start-up.
- Loot additions decode each pool with `LootPool.CODEC` on every `LootTableEvents.MODIFY` and only change built-in tables; a pool that fails to decode is one error per load and changes nothing. A pool naming an unknown key in a registry loaded with loot tables (for example a made-up `rolls` provider) stops the data pack load, as it does in vanilla; the editor's full pool check (the `pools` type is substituted with vanilla `LootPool` per target) reports these before export.
- Block item settings and addition files are closed structs: unknown keys are errors.

Implementation notes (close, 2026-11-14):

- The ore starters use `block_match` on stone and deepslate rather than the replaceable tags (D6), because the schema validator does not read implicit tag ids yet (follow-up in the ROADMAP; the targets move to the replaceable tags once it does).
- The sample data pack trade is now checked in CI on a vanilla server (`tools/run-fabric-server/vanilla-datapack.ts`), no longer by hand only.
