# ADR 0072: A vanilla model renderer for mobs (GeckoLib optional, mobs on 26.4)

## Context

Every `msm:entity` renders through GeckoLib ([ADR 0028](0028-entity-definition-format-v1.md) D5, [ADR 0029](0029-model-animation-pipeline.md) D1): `msm:animated_model` is required, a runtime without GeckoLib registers no entity, and a content jar with entities nests GeckoLib. GeckoLib has no build for any 26.4 snapshot (Modrinth checked again on 2026-11-14: the newest Fabric builds are 5.5.7 and 5.5.6 for 26.3), so on `mc-26.4` the content jar export refuses entities (`export.no-geckolib-target`) and the library hides every mob starter and example (`supports: hasGeckolib`; coverage audit L8, L9). DESIGN §17 risk 6 kept "an own minimal renderer" as the documented, unbuilt fallback. The user asked whether a renderer built from vanilla's own entity model classes, fed by the project's GeckoLib geometry, is feasible on the client; otherwise a fixed set of vanilla model shapes.

Facts read on 2026-11-14 with `javap` over both merged jars and the cached GeckoLib 5.5.7 jar (fact table F12, F13, F15 in the Findings of [ADR 0070](0070-mob-bodies-movement-and-ranged-attacks.md)):

- **The client model API is the same on 26.3 and 26.4-snapshot-7** (one addition on 26.4, `PartDefinition.transformCubes`): `ModelPart(List<Cube>, Map<String, ModelPart>)`; `ModelPart.Cube` has a public constructor taking box UV `(int u, int v, x, y, z, w, h, d, growX, growY, growZ, boolean mirror, float texW, float texH, Set<Direction>)` and a **public final `Polygon[] polygons`** whose elements can be replaced; `Polygon(Vertex[], ...)` and `Vertex(x, y, z, u, v)` are public records; `CubeListBuilder`, `MeshDefinition`, `PartDefinition`, `PartPose`, `CubeDeformation`, `LayerDefinition.create(...).bakeRoot()`.
- **Renderers:** `MobRenderer(Context, M, float shadow)`, `LivingEntityRenderer.getTextureLocation(S)`, `extractRenderState`, `scale`; `EntityModel(ModelPart)` (protected) with `setupAnim(S)`; `LivingEntityRenderState` carries `walkAnimationPos`, `walkAnimationSpeed`, `scale`, `ageScale`, `isBaby`. `EntityRendererProvider.Context.getResourceManager()` gives the client's resources when renderers are (re)built on resource reload.
- **Keyframe animation is vanilla's own:** `AnimationDefinition.Builder.withLength(float).looping().addAnimation(bone, AnimationChannel)`, `AnimationChannel(Target, Keyframe...)` with targets `POSITION`, `ROTATION`, `SCALE`, `Keyframe(float, Vector3fc[, Vector3fc], Interpolation)` with `LINEAR` and `CATMULLROM`, `AnimationDefinition.bake(ModelPart)` to a `KeyframeAnimation` with `apply(AnimationState, float)` and `applyWalk(...)`; `AnimationState.start`, `stop`, `animateWhen` (the warden, frog and camel use these).
- **Renderer registration** already has a version seam, `client/EntityRendererRegistration` (26.3 `EntityRenderers.register(type, provider)`, 26.4 the client registry form), and the thrown item renderer registers through it on every client.
- **GeckoLib hooks** for this batch: `GeoModel.getTextureResource(GeoRenderState)`, `GeoModel.addAdditionalStateData(T, Object, GeoRenderState)`, `DataTicket.create(String, Class)`, `GeoRenderState.addGeckolibData`/`getOrDefaultGeckolibData`, `GeoRenderer.adjustModelBonesForRender(RenderPassInfo, BoneSnapshots)`, `GeoEntityRenderer.scaleModelForRender(RenderPassInfo, float, float)`; `GeoEntityRenderer` extends `EntityRenderer`, not `LivingEntityRenderer`.
- The app's WebGL preview already bakes the same Bedrock geometry with Blockbench's conventions (recorded in `app/src/renderer/src/preview/geo/geometry.ts`), so there is a reference for the sign and pivot rules.
- Nothing on the client can be drawn in CI (no OpenGL or Vulkan backend in the container; audit L16).

## Decision

- **D1 Our own renderer over vanilla model classes, fed by the project's geo files.** The runtime gains `client/vanilla/`: `GeoMeshReader` (pure Java, no client classes: reads a Bedrock geometry file into bones and cubes in Java model space, applying the Blockbench conventions of ADR 0029 Status), `GeoModelBaker` (builds a `ModelPart` tree: one part per bone at its pivot with its rest rotation; box-UV cubes through the `Cube` constructor; per-face UV cubes by replacing the cube's polygons with remapped UVs; a cube with its own rotation becomes a child part about its pivot; `inflate` as growth; `mirror`), `GeoAnimationReader` (Bedrock animation 1.8.0 keyframes to `AnimationDefinition`s: numbers only, `linear` and `catmullrom`, `pre`/`post` keyframes, loop modes), `MsmVanillaModel extends EntityModel` and `MsmVanillaRenderer extends MobRenderer`. The renderer provider reads the geo and animation files named by `msm:animated_model` (`assets/<ns>/geckolib/models/...` and `.../animations/...`, the paths GeckoLib uses, so the same project files serve both renderers) from `Context.getResourceManager()`, so a resource pack reload rebuilds them. We chose this over a fixed set of vanilla shapes (humanoid, quadruped) because the user's own Blockbench model then looks the same in both renderers and in the app preview, and vanilla shape classes would force vanilla's texture layouts; the library ships original preset models instead ([ADR 0073](0073-mob-flows-templates-and-presets.md)).
- **D2 What the vanilla renderer plays.** `idle` loops always (its own `AnimationState`), `walk` through `applyWalk` with the render state's walk position and speed, the state animations of [ADR 0071](0071-tameable-breedable-rideable-mobs-variants-and-boss-bars.md) D6 (`sit`, `fly`, `swim`) from synched state, and triggered animations (`attack`, `shoot`, `play_animation`) through one runtime synched int `DATA_ANIM` (an 8-bit counter and the animation's index in the definition's triggerable list): the client starts that animation's `AnimationState` when the value changes. Babies draw at `ageScale` through the vanilla render state; the variant's texture comes from `DATA_VARIANT` (ADR 0071 D4); `saddle_bone` is hidden unless saddled. Hurt flash, death tilt, shadows and name tags are vanilla's.
- **D3 What the vanilla renderer does not do** (validator `entities.vanilla-renderer-subset`, a warning naming each): Molang expressions (evaluated as 0, as the app preview does), `bezier` and other easings (played as linear), sound, particle and instruction keyframes, bone-level render layers and glow, animations on the `msm_triggered` controller of other names than the definition lists. GeckoLib remains the full-fidelity renderer.
- **D4 `renderer` field.** `msm:animated_model` gains `renderer?: "auto" | "geckolib" | "vanilla"`, absent meaning `auto`. Server side: `geckolib` registers only with GeckoLib loaded (today's rule and error); `auto` registers the GeckoLib subclass when GeckoLib is loaded and the plain class otherwise; `vanilla` never touches GeckoLib. Client side: GeckoLib renderer for GeckoLib subclasses, the vanilla renderer for the rest. The GeckoLib subclasses add no synched data of their own, so a client and server that disagree about GeckoLib still agree on the entity's data (confirmed: GeckoLib 5.5.7's `GeoEntity` defines none).
- **D5 Export.** The content jar nests and depends on GeckoLib when an entity is `geckolib`, or `auto` on a target with GeckoLib facts (so every existing project exports exactly as today on 26.3). On a target without GeckoLib (26.4) `auto` entities export without GeckoLib (info `export.entity-vanilla-renderer`) and `geckolib` entities stop the export (`export.no-geckolib-target`, as today). A project whose entities are all `vanilla` never nests GeckoLib. "Separate runtime and GeckoLib (for modpacks)" keeps its meaning.
- **D6 Mobs on 26.4.** With D4 and D5, entities export, register and render on 26.4. The library's mob starters, flows and examples use `auto` and change their gate from `hasGeckolib` to `hasFabric` (a content jar is possible), except examples that need GeckoLib-only features (Molang), which keep `hasGeckolib`. The 26.4 runtime runs the entity GameTests it skipped before, and CI exports and serves the mob samples on 26.4 too.
- **D7 Testing without a screen.** `GeoMeshReader` and `GeoAnimationReader` are pure and covered by JUnit. A shared golden (`fixtures/geo-parity/`) holds the world-space vertex positions and UVs of two models (the sample mob's biped and a model with per-face UV and cube rotation) as computed by the app's preview baker; a new app test writes or checks it from `geometry.ts`, and a JUnit test bakes the same files through `GeoModelBaker` into real `ModelPart`s (the client classes are on the test classpath; nothing is drawn) and compares the transformed vertices, so the two bakers cannot drift apart. Drawing, animation feel and textures stay an in-game check, listed in the sample's README.
- **D8 Java eject.** The eject is 26.3-only and 26.3 has GeckoLib, so ejected projects render every entity through GeckoLib, including `vanilla` ones (info `export.eject-uses-geckolib`, default, vetoable). Copying the vanilla renderer into ejected projects is a follow-up if users ask.
- **D9 Seams.** The renderer code uses only the API listed above, identical on both versions, so it is shared; registration keeps the existing `EntityRendererRegistration` seam. If an implementation detail differs, it goes behind a new seam in `src/mc/<mc>/java/.../client/` with a compile check on both versions.

## Consequences

- Mobs no longer need GeckoLib: offline first exports of `vanilla` mobs work (audit L8), and mobs reach 26.4 (L9).
- The runtime gains its first real client code beyond registrations (audit L3): about six classes in `client/vanilla/`, compiled on both versions and tested as far as JUnit can go.
- `auto` keeps every existing project's export unchanged on 26.3; the same project exported for 26.4 renders with the vanilla renderer, with fewer animation features (D3).
- DESIGN §17 risk 6 changes from "documented, unbuilt" to "built as the fallback renderer".

## Findings

Recorded at close (2026-11-14) from B285, B286, B288, B295, B296 and B302:

- **GeckoLib never applies `getAgeScale`.** `GeoEntityRenderer` is not a `LivingEntityRenderer`, so GeckoLib 5.5.7 drew babies adult-sized; the runtime's `GeckolibRenderers.MsmGeoRenderer` scales by the age scale and hides the saddle bone and its children in `adjustModelBonesForRender`, fed by the tickets `MsmGeoModel.TEXTURE`, `HIDDEN_BONE` and `AGE_SCALE` set in `addAdditionalStateData` (limit M14 fixed). Renderer generics use `R extends EntityRenderState & GeoRenderState`, because Loom's interface injection is absent without GeckoLib and on 26.4.
- **`GeoEntity` has no synched data** (D4 confirmed), so a client and a server that disagree about GeckoLib agree on the entity's data; `triggerAnim` still sends GeckoLib's own packets, so limit M17 stands (ship GeckoLib to both sides or neither).
- **The renderer reads GeckoLib's paths** (`assets/<ns>/geckolib/models/...` and `.../animations/...`) through `MsmVanillaRenderer.provider(typeId, definition)`; broken or missing files draw nothing and log once. Every non-GeckoLib type registers through `EntityRendererRegistration` ("registered N vanilla entity renderer(s)").
- **Vanilla's `root` lookup.** `ModelPart.createPartLookup()` puts the root part first as `root` (`putIfAbsent`), so `AnimationDefinition.bake(root)` cannot reach a bone named `root`. `GeoAnimationBaker` binds channels under private keys `#msm<i>` and bakes against `Baked.bones()` instead; presets avoid the name.
- **Model space** (B285, `javap -c`, the same on both versions): a Bedrock point `(x, y, z)` is `(x, 24 - y, z)` in Java model space with sizes unchanged; rest and animation rotations keep the file's degrees (Blockbench and GeckoLib negate x and y, vanilla's `scale(-1, -1, 1)` negates them back); animation positions are `(x, -y, z)` pixels; scales become `offsetScale` = factor - 1. Box UV with whole-number offsets uses vanilla's `Cube` constructor (its layout and `mirror` equal Blockbench's); fractional offsets and per-face UV replace the polygons (Bedrock east, west, up and down are vanilla WEST, EAST, DOWN and UP). Rotated cubes are child parts `<bone>#cube<n>`. Vanilla and GeckoLib do not floor box UV sizes; Blockbench's own preview floors and insets 1/64 px.
- **The vertex golden** (`fixtures/geo-parity/`): the app's preview baker and `GeoModelBaker` over real `ModelPart`s agree within 1e-4 on two models (`GeoParityTest`, `app/test/preview/geo-parity.test.ts`); client classes load in plain JUnit. The Gradle build does not yet declare the folder as a test input (follow-up).
- **What the vanilla renderer plays.** `MsmVanillaModel` loops `idle`, plays `walk` through `applyWalk(pos, speed, 1.0, 2.5)` and the state animations by the same rule as `GeoControllers.loop` (`sit`, then while moving `swim` in water, `fly` off the ground in mode fly, `walk`, else `idle`); triggered animations are one per controller at a time, and the first value seen after the entity appears is not replayed (limit M3: one per tick). Babies draw at `def.scale` times the age scale. Head look is not drawn yet (follow-up). Both renderers keep their own copy of the state rule; a GeckoLib-free `registry/mob/MobStates` with one definition of moving is a follow-up.
- **Drawing is in-game only** (limit M5): the sample creatures' README holds the checklist for both renderers on 26.3 and 26.4 (`fixtures/sample-creatures/README.md`).
- **Export.** `entityRenderers(files)` and `needsGeckolib(files, { geckolib? })` in `@msm/exporters` decide nesting; info `export.entity-vanilla-renderer` per `auto` entity on a target without GeckoLib and `export.eject-uses-geckolib` per `vanilla` entity; `export.no-geckolib-target` for `geckolib` entities in a jar for 26.4. The sample mob and sample creatures export, load and pass parity on 26.4 without GeckoLib.

## Status

Accepted (2026-11-14). Defaults the user may veto: `auto` as the default renderer and GeckoLib preferred where the target has it (D4, D5); the renderer reading GeckoLib's resource paths rather than its own (D1); ejected projects using GeckoLib for every entity (D8).
