# ADR 0029: Model and animation pipeline: GeckoLib, Blockbench import, geo and animation kinds, preview

## Context

Phase 5 needs a way to get a Blockbench model with animations into the game and onto a custom mob ([Interop](../DESIGN.md#13-interop-blockbench-nbt-minecraft-installation), [Editors and UX](../DESIGN.md#8-editors-and-ux)). DESIGN §13 planned GeckoLib geo and animation JSON with the original `.bbmodel` kept as an asset, and §17 risk 6 named an own minimal renderer as the fallback if GeckoLib lagged the target.

Verified on 2026-11-05 (sources in the Phase 5 plan's facts table, a working document removed at phase close; it stays in git history and `DEVLOG.md` records its sources):

- **GeckoLib 5.5.7 is available for Fabric 26.3** (Modrinth, MIT, `environment` `*`, depends on Fabric API `>=0.160.5+26.3`), so the fallback renderer is not needed. The official Maven is unreachable through the session proxy; the Modrinth Maven (`https://api.modrinth.com/maven`, `maven.modrinth:geckolib:kSxHvs99`) and the Modrinth CDN (`geckolib-fabric-26.3-5.5.7.jar`, SHA-512 recorded in the plan) work.
- GeckoLib 5 reads Bedrock geometry (`format_version` `1.12.0` and later, `minecraft:geometry[]` with `description` and `bones`) from `assets/<ns>/geckolib/models/**.geo.json` and Bedrock animations (`format_version` `1.8.0`, `animations{}`) from `assets/<ns>/geckolib/animations/**.animation.json`; it warns on unknown and refuses unsupported geometry format versions. Its Java API is `com.geckolib.*`: `GeoEntity`, `AnimationController`, `RawAnimation`, `GeoModel`, `GeoEntityRenderer`.
- Blockbench 5.2.2 saves projects with `meta.format_version` `"5.0"` (4.x wrote `"4.10"`); cubes, groups, textures and animations keep documented fields, and its Bedrock export applies known sign conventions (cube origin x = -(from.x + size.x), pivot x negated, rotation x and y negated, per-face UV with the up and down faces flipped, animations with `loop`, `animation_length`, `catmullrom`). Blockbench can also export the `.geo.json` and `.animation.json` files itself.
- The app's preview uses deepslate for Java models and structures ([ADR 0010](0010-preview-with-deepslate.md), [ADR 0023](0023-structure-and-climate-previews.md)); deepslate cannot draw Bedrock geometry. DESIGN §8 allows three.js "only if a phase needs it".

## Decision

**D1. GeckoLib 5.5.7 is the animated-model backend for 26.3.** Every `msm:entity` renders through GeckoLib (`msm:animated_model` is required, [ADR 0028](0028-entity-definition-format-v1.md) D2). The target carries the facts (`Target.geckolib: GeckolibFacts`, [ADR 0030](0030-plugin-api-0.7.md)): version, mod id, the dependency range written into `fabric.mod.json`, the jar's file name, download URL and SHA-512, and the Modrinth version id. GeckoLib's Java API is isolated in the runtime's bridge classes and the version-specific strings in the target, so a GeckoLib or Minecraft bump touches those two places only. The own-renderer fallback of DESIGN §17 risk 6 stays documented, unbuilt.

**D2. Two element kinds in `@msm/plugin-models-anim` (`msm.models-anim`).** `msm:geo_model` (kind folder `geo_model`, schema `msm:geo_model`, an mcdoc subset of Bedrock geometry 1.12.0: description, bones with pivot and rotation, cubes with box or per-face UV, inflate, mirror, locators) and `msm:animation` (folder `animation`, schema `msm:animation`: animations with loop modes, length, bone channels with vector or keyframe values, Molang strings accepted). Elements hold the JSON as GeckoLib reads it, so the Raw JSON tab edits the real file and hand-written files import unchanged. Lowering writes `assets/<ns>/geckolib/models/<path>.geo.json` and `assets/<ns>/geckolib/animations/<path>.animation.json` (layer `resourcepack`, validated by the gate). Ids follow the convention `<ns>:entity/<name>` for the model and `<ns>:entity/<name>_animations` for its animation set, because element ids are unique across kinds. Validators (`models-anim.*`) check UVs against the texture size, duplicate and orphan bones, animation bones against the project's models and flag Molang as unsupported in the preview.

**D3. Blockbench import lives in `@msm/interop` `blockbench/` and is registered by the app as a host importer.** `convertBbmodel` is a pure function over the documented `.bbmodel` fields (format `4.x` and `5.x`, warning on others; cubes only; embedded textures; rotation, position and scale channels) applying Blockbench's own Bedrock export conventions, producing one geometry file, one animation file and the texture PNGs. `.geo.json` and `.animation.json` files pass through after a format check. The `Importer` object (`id` `blockbench`) yields an `msm:geo_model`, an `msm:animation` when the file has animations, `textures/entity/<name>.png` assets and the original `.bbmodel` kept as the asset `blockbench/<name>.bbmodel`, which the exporters already skip. Plugins may only depend on `@msm/plugin-api` and `@msm/schemas`, and DESIGN §13 places Blockbench in `@msm/interop`, so the app's `collectImporters` accepts host importers next to plugin importers; third-party plugins can still contribute their own importers through the same interface. Java block `.bbmodel` files are not converted in v0.5 (Blockbench exports those itself); the importer says so.

**D4. GeckoLib is nested only when the project has entities.** The content jar exporter ([ADR 0026](0026-fabric-content-jar.md)) adds `"geckolib": "<dependency>"` to `depends` and, unless the existing `separateRuntime` option is on (relabelled "Separate runtime and GeckoLib (for modpacks)"), nests `META-INF/jars/<fileName>` with bytes from `loadGeckolibJar`. The app's main process supplies them from `<userData>/downloads/geckolib/`, downloading the jar once from the target's URL with a SHA-512 check (the same downloader and atomic write as the Fabric API download of ADR 0026 D5). Without a cached jar and without network the export fails with `export.geckolib-missing` and a message saying a one-off download is needed. CI downloads the jar the same way for the headless server check. The installer does not ship GeckoLib in v0.5.

**D5. The preview renderer is the app's own, raw WebGL with `gl-matrix`, no three.js.** `preview/geo/` bakes geometry into buffers (cubes, inflate, box and per-face UV, mirror), applies the bone hierarchy about pivots with the rotation order and signs of Blockbench's Bedrock renderer (verified at implementation and recorded in the module header), textures from project assets, an orbit camera and grid; playback evaluates keyframes (linear; `catmullrom` as linear with a notice; Molang strings as 0 with a notice), loop modes and transport controls. Subjects: `geo_model`, `animation` (played on the matching model) and `entity` (the referenced model, texture and idle animation at the definition's scale). Three.js would add about 600 kB for cubes and keyframes we can draw in a few hundred lines, and deepslate's WebGL helpers already set the pattern.

**D6. GeckoLib on the runtime's build.** `engine-mod` compiles against GeckoLib from the Modrinth Maven and runs it on the GameTest server, but the built `msm_runtime` jar neither contains GeckoLib nor hard-depends on it (`suggests`), so a runtime without GeckoLib still serves blocks and items. The exact Gradle configuration is settled by the spike (B110) and recorded in the Status below.

## Consequences

- Users import a `.bbmodel` or Blockbench's own geo and animation exports, pick them in the Entity Studio and see the model animate in the app before testing in the game.
- GeckoLib's resource layout is fixed by GeckoLib; MSM's path conventions in `@msm/plugin-models-anim` `paths.ts` follow it and change only when GeckoLib does.
- Exporting an entity jar needs the GeckoLib jar once; the app caches it. A modpack maker can leave both GeckoLib and the runtime out.
- The preview is a subset: no Molang, no particle or sound keyframes, no catmullrom; the game remains the reference, and the guide says so.
- Risk 9 of DESIGN §17 (Blockbench drift) is mitigated by reading only documented fields, checking `meta.format_version` and keeping the pass-through path.

## Status

Accepted (2026-11-05, Phase 5 close, B122). Implemented by B110 and B113 (runtime and Gradle), B111 (target facts and content jar nesting), B112 (geometry and animation mcdoc), B114 (`@msm/plugin-models-anim`), B116 (Blockbench import), B117 (preview), B118 (app wiring and the GeckoLib download), B120 (CI headless check) and B121 (e2e). Findings at close:

- **Licence.** GeckoLib is MIT: its Modrinth page and the `LICENSE.txt` and `modLicense=MIT` inside the 5.5.7 jar (checked 2026-11-05). The README's Licence section credits it; nesting it in user jars is allowed, and the installer does not ship it in v0.5.
- **CI headless check (B120).** The `engine-mod` job exports `fixtures/sample-mob/` (`msm_sample_mob`: one entity with every component, all six goal types, `play_animation`, natural spawns and a spawn egg) with the real `msm_runtime` jar and the real GeckoLib 5.5.7 jar nested (`META-INF/jars/`, downloaded from `Target.geckolib.url` and SHA-512 checked), and starts a headless 26.3 Fabric server with Fabric API. It passes when the mod list shows both nested jars, the runtime logs `registered 0 block(s) and 1 item(s) from 1 definition file(s); 0 error(s), 0 warning(s)` and then `registered 1 entity type(s)`, and no GeckoLib warning, error or stack frame appears; the sample-mod check pins `registered 0 entity type(s)` the same way. GeckoLib logs nothing at all on the dedicated server. `tools/run-fabric-server --separate-geckolib` covers jars exported with "Separate runtime and GeckoLib (for modpacks)".
- **Blockbench 5.0 layout and keyframes (B116).** Blockbench 5.0 (`bbmodel.js` at v5.0.0) moved group fields into a top-level `groups` array, with the outliner holding `{ uuid, isOpen, children }` nodes, and stores keyframes in Blockbench's own orientation: position x and rotation x and y are inverted relative to 4.x files (the 4.x-to-5.0 upgrade inverts them, and the Bedrock export inverts them back). `convertBbmodel` reads both layouts, negates those channels for `5.x` (and unversioned or newer) files and writes `4.x` keyframes as they are; a test proves a 4.10 rewrite of the fixture converts to the same output. Loose cubes go under a `root` bone; bezier keyframes are written as linear with a warning; sound, particle and timeline channels are reported as info and left out.
- **Preview rotation convention (B117).** Read from Blockbench 4.12.4 (`bedrock.js`, `canvas.js`, `cube.js`, `timeline_animators.js`) and recorded in the header of `app/src/renderer/src/preview/geo/geometry.ts`: Bedrock geometry is drawn with x mirrored (cube `from = [-(origin.x + size.x), origin.y, origin.z]`, pivots x negated, rest rotations x and y negated), Euler order `ZYX` (x applied first), bones at `pivot - parent.pivot`; animation rotation is added with x and y negated, position with x negated, scale multiplied about the pivot. The preview reads the Bedrock and GeckoLib values as written; the 5.0 keyframe orientation is the converter's concern only. The e2e spec mounts the WebGL preview under xvfb with SwiftShader (`--use-angle=swiftshader`); pixels are not asserted.
- **GeckoLib download (B118).** The app caches the jar at `<userData>/downloads/geckolib/<fileName>`, checked by SHA-512 on every use, downloaded once with the Fabric API downloader and written atomically; without it and without network, the export fails with `export.geckolib-missing` and a message naming the one-off download.

Spike findings (B110, 2026-11-05):

- **Gradle (Loom 1.19.3, non-remapping).** There are no `mod*` configurations (`modImplementation`, `modLocalRuntime` do not exist); a plain jar with a `fabric.mod.json` on the run classpath is discovered by Fabric Loader as a mod. `engine-mod/build.gradle.kts` uses `compileOnly` and `gametestCompileOnly` for compilation and `localRuntime` for `runGameTest`, `runServer` and `runClient`; `-PwithoutGeckolib` leaves the runtime one off. The Modrinth Maven is declared as an `exclusiveContent` repository for group `maven.modrinth` (otherwise Gradle asks Maven Central first and hits 429s). The built `msm_runtime-0.4.0.jar` contains no `com/geckolib` class and its `fabric.mod.json` only `suggests` `geckolib >=5.5.7`. The jar resolved from the Modrinth Maven has the SHA-1 recorded in the plan (`064ad66e...925c`).
- **GeckoLib on the GameTest server and the dedicated server.** GeckoLib 5.5.7 loads in `runGameTest` (mod list, common Mixins, class tweaker) with no warning. A production headless server (`tools/run-fabric-server` with the runtime jar, the GeckoLib jar and a hand-made content jar holding the spike entity and its GeckoLib assets) starts cleanly: `Done`, 0 errors, 0 warnings.
- **Resource lookup keys.** `GeckoLibResources.stripPrefixAndSuffix` turns `ns:geckolib/models/entity/x.geo.json` into `ns:entity/x` and `ns:geckolib/animations/entity/x_animations.animation.json` into `ns:entity/x_animations` (asserted in a GameTest). The definition's `model` and `animations` ids are the lookup keys unchanged; the texture id `ns:entity/x` maps to `ns:textures/entity/x.png`. GeckoLib's own `DefaultedEntityGeoModel` would add an `entity/` prefix itself, so the runtime uses a plain `GeoModel` subclass.
- **Triggerable animations.** `AnimationController.triggerableAnim(String name, RawAnimation)` registers a name (the `triggerableAnimations` supplier is filled by it); `receiveTriggeredAnimations()` also exists (not used by the spike; its exact semantics: verify at implementation). `GeoEntity.triggerAnim("msm_triggered", "attack")` on the server does not throw, also for a name the controller does not know.
- `GeoEntityRenderer<T, R extends EntityRenderState>` is created with `new GeoEntityRenderer<MsmGeoEntity, EntityRenderState>(ctx, model)` from the client entrypoint and registered with Fabric's `EntityRendererRegistry.register`, which is `@Deprecated` in fabric-rendering-v1 27.2.0 but works (vanilla `EntityRenderers.register` is private; replacement: verify at implementation). Settled by B113: the runtime calls vanilla `EntityRenderers.register`, which Fabric API's transitive access wideners make public, with `withScale(scale)` ([ADR 0028](0028-entity-definition-format-v1.md) Status). In `runClient` under `xvfb-run` GeckoLib loads and the client entrypoint runs, but the game cannot create a render backend in the container (OpenGL: no matching GLX visual; Vulkan: no `VK_KHR_surface`), so client rendering is not checked by the spike and reserve brief B123 cannot run in this container; the user's in-game check carries rendering.
