# ADR 0096: Commands, creative tabs, place and explosion events, and the small script and Rules gaps

## Context

[ADR 0065](0065-script-api-1-1.md) D11 deferred `block.place` ("no event without a mixin"), `msm.commands.register` ("the command tree and reload order need a spike"), a custom creative tab ("a definition feature, not script") and dropped items in `entitiesNear`. The research report (`popular-mods.md` section 3, rank 13) adds `entity.vehicle` and `passengers`, an explosion event that can keep blocks safe (anti creeper grief) and a "facing" reading for Rules (the conveyor belt example). Commands, creative tabs and game rules are vanilla systems; under the user's rule of 2026-11-14 they belong in the app.

Facts ([ADR 0101](0101-vanilla-parity-2-flows-studios-try-it-and-tests.md#fact-table-f1-to-f36-moved-from-the-plan-at-b485) F15–F18): Fabric's `CommandRegistrationCallback.EVENT` (`register(CommandDispatcher, CommandBuildContext, Commands.CommandSelection)`) and `FabricCreativeModeTab.builder()` are the same on both versions; Fabric API 0.165.2 and 0.165.4 have no block placement or explosion event in any module (all module jars searched); `BlockItem.place(BlockPlaceContext)` is public and `ServerExplosion.explode()` public with a private `interactWithBlocks(List<BlockPos>)`, both identical on 26.3 and 26.4. DESIGN §10 "Mixin policy" allows a Mixin where no event exists, with a justification comment and a GameTest. The runtime has no Mixin yet (audit L3).

## Decision

- **D1 Kind `msm:command`** (definition, frozen at start like other definitions; re-registered on every `/reload` if S8 confirms Fabric fires the callback again):

  ```
  struct Command {
    name: string,                    // the literal, lower case [a-z0-9_]; refused if vanilla or another project command has it
    aliases?: [string] @ 0..4,
    permission?: int @ 0..4,         // default 0: every player; 2 = operators, as vanilla's cheat commands
    arguments?: [Argument] @ 0..8,   // optional arguments only at the end
    function?: #[id="function"] string,   // run as and at the player or source, with the arguments as macro values
    event?: string,                  // an action list in the definition (ADR 0061 actions), context self = source entity
    feedback?: string,               // a lang key shown to the source on success
  }
  struct Argument { name: string, type: "integer" | "number" | "word" | "text" | "boolean" | "player" | "players" | "entity" | "position" | "block_position" | "item" | "block", min?: number, max?: number, optional?: boolean }
  ```

  A function receives the arguments as macro values (`$(name)`); scripts receive a `command` event with `name`, `source` and an `args` object. A command with neither `function` nor `event` is a validator error unless a script subscribes to it (a warning then). Permission 0 commands that run a function are an author's choice, like a data pack's `/trigger`; the validator gives an info line (`commands.runs-as-player`).
- **D2 Kind `msm:creative_tab`** (frozen): `icon: item id`, `title` (a lang key written by lowering from the editor's name), `order?: "as_listed" | "by_name"` (default `as_listed`). Items and blocks join by naming its id in their existing `creative_tab` field (today an unknown tab only warns, `MsmRegistrar`); the tab registers before blocks and items through `FabricCreativeModeTab.builder()` into the vanilla registry. A new project made by the Creator offers "Give my mod its own tab" (ADR 0101 D2).
- **D3 The first two Mixins.** In `engine-mod/src/main/java/.../mixin/` with `msm_runtime.mixins.json` (server side, `required: true`), each with a justification comment and GameTests on both versions:
  - `BlockItemPlaceMixin` at the head of `BlockItem.place(BlockPlaceContext)` when the context has a server player: fires the script event `block.place` (cancellable; `pos` is the placement position, `block` the item's block id, `item`, `player`) and the Rules trigger "When a player places a block". A cancel returns `FAIL` and resyncs the held slot and the position (ADR 0058's resync). Placement by dispensers, endermen and commands is not seen (limit Q17).
  - `ServerExplosionMixin` at the head of `explode()` fires `world.explosion` (`pos`, `radius`, `source` entity or null, `cause`: the direct source's type id or `"block"`); `cancel()` stops the explosion; `keepBlocks()` cancels the head of `interactWithBlocks`, so entities still take damage and knockback but no block breaks or drops. Rules: "When something explodes" with steps "Stop the explosion" and "Keep the blocks safe" and the condition "caused by <mob or block>".
  We chose Mixins because neither event exists in Fabric API and both are what the research's anti-grief and building-rule ideas need; both targets are public or private methods with identical signatures (F15, F16). The spike (S7) proves the Loom setup on both versions before any brief writes one.
- **D4 Script API 1.6** (vehicles take 1.5; renumbered at merge if needed): `Entity.vehicle` (`Entity | null`), `Entity.passengers` (`Entity[]`), `Entity.ride(entity)` and `Entity.dismount()` (refused for players riding players); `World.itemsNear(pos, radius)` returning `DroppedItem` objects (`item: ItemRef`, `pos`, `age`, `remove()`, `setItem(spec)`, `owner` uuid or null), while `entitiesNear` keeps living entities only; `ItemRef.contents` ([ADR 0095](0095-item-inventories.md) D5); events `block.place`, `world.explosion` and `command`. Members are labelled with the release that ships them at close.
- **D5 Rules additions** (catalogue and compile, [ADR 0082](0082-rules-no-code-behaviour.md)): the value **Facing** (of the player, of a mob, or of the block "here": its `facing` or `axis` property, as north, east, south, west, up or down), the condition **is facing**, the place **in front of here** (one block along the block's facing), the triggers **When a player places a block**, **When something explodes** and **When a player uses the command /…** (which makes the `msm:command` element for the user), and the steps **Stop the placing**, **Stop the explosion**, **Keep the blocks safe** and the condition **is riding** (a mob or vehicle, from `Entity.vehicle`). Compilation prefers plain events (the command's `event`, the explosion through the script bridge only when a step needs `cancel` or `keepBlocks`).
- **D6 Versions and eject.** No seam expected (F15–F18 identical). Plugin API 1.17.0 adds `TargetFacts.commands?: { vanillaNames: readonly string[]; argumentTypes: Readonly<Record<string, { parser: string; properties?: Readonly<Record<string, string>> }>> }` (a map from MSM's twelve argument names, because `player`, `players` and `entity` share one parser; amended at B444) (vanilla command literals from the vendored `commands.json`, for the clash check) and `ItemFacts.creativeTabs` is already the vanilla tab list. The 26.3 generator emits commands (a generated `ModCommands` with Brigadier builders) and creative tabs; the two events are script-only, and scripts are not ejected (L10), so the Mixins are not ejected.
- **D7 Not in this batch.** Client-side commands, custom argument types and suggestions beyond the listed types, changing explosion radius or knockback, placement events for non-players, `block.break` by non-players, cancelling vanilla commands, game rules of our own (ADR 0082 R10 lists them for a later batch).

## Consequences

- `msm_runtime` gains its first Mixin configuration; DESIGN §10's policy applies, and every later Mixin follows these two in package, naming and test shape.
- Commands make Rules and scripts reachable by players directly; the guide warns that permission 0 commands are for everyone.
- Two kinds (99 with vehicles' three) and one Script API minor.

- **Spike answers** (B440). S7: `msm_runtime.mixins.json` with `required: true`, `minVersion` 0.8, `compatibilityLevel` `JAVA_25`, `injectors.defaultRequire` 1 and no refmap works with Mojang names on GameTest, integrated and dedicated servers on both versions. S8: `CommandRegistrationCallback` runs at each start and on every `/reload`, on a worker thread; the client's tree updates only after `server.getCommands().sendCommands(player)`; functions run with `withPermission(LevelBasedPermissionSet.GAMEMASTER)`, not `withMaximumPermission`; arguments reach macros through command storage (`function <id> with storage <ns>:args`); macro text is raw. S9: a tab from `FabricCreativeModeTab.builder()` registered into `BuiltInRegistries.CREATIVE_MODE_TAB` keeps its items in listed order; extra tabs go to Fabric's second page.
- **D1 as built** (B443, B454, B456, B464a). Names, aliases and argument names are `[a-z0-9_]+`; the element field `feedback_text` is lowered to the lang key `command.<ns>.<path>.feedback` (`/` as `.`) and `feedback` names it. The kind lives in `@msm/plugin-scripting` (folder `command`, default `/hello` with the event `greet` and "Hello!"). `MsmCommands` registers at each start and on `/reload` and resends every player's tree at `END_DATA_PACK_RELOAD`; a run reads the arguments, runs `function <id> with storage <mod id>:args` at GAMEMASTER, fires `event` (self and other the source entity), fires the script `command` event, then sends the feedback. A literal taken by an earlier project command, vanilla or another mod is a load error and is not registered under that name. Macro values: integer `5`, number `2.5`, boolean `1`, position `1.5 64.0 -2.25`, block position `3 70 -4`, item and block their ids, `entity` the UUID and, **by decision at B464a**, `player` the player's name and `players` names separated by spaces (vanilla `give` refuses a UUID for a player; the sample's `/kit` failed before the change); runtime and eject changed together. No macro escaping: `commands.raw-text` (info) stays. The runtime runs both `function` and `event` when both are set while the eject refuses; `commands.function-and-event` refuses it first, so no user sees the difference. The runtime always reads the arguments, so an event-only command whose selector matches nobody fails as vanilla's would. Validator codes (`COMMAND_PROBLEM_CODES`, plain words in the app): `bad-name`, `name-clash` (against `TargetFacts.commands.vanillaNames` and the project), `optional-not-last`, `text-not-last`, `range-not-number`, `min-above-max`, `function-and-event`, `unknown-event`, `nothing-to-run` (an error, or a warning when a script handles the name), `runs-as-player` (info) and `raw-text` (info). A dev-mode overlay of a command reloads its events. GameTests `MsmCommandGameTest` (13, plus one manual real `/reload`), JUnit `CommandParserTest` (10).
- **D2 as built** (B454, B456, B460). The kind lives in `@msm/plugin-blocks-items` (folder `creative_tab`, registry `creative_mode_tab`, default icon `minecraft:diamond`, `display_name` "My mod"); the title key is `itemGroup.<ns>.<path>`. `MsmCreativeTabs.register` runs before the registrar so items resolve it. **`as_listed` is registration order** (block items, then items, then spawn eggs, each by mod id and then file path), not the project's element order as the Creative tab Studio first assumed (B460's note, corrected by B454); the guide says so, and the Studio's list is a guide to it. **Decision (B460):** no hand ordering of a tab's items in this batch (D2 of ADR 0101 said "drag to order"). `by_name` is a stable sort by hover name in the phase `msm_runtime:sort_creative_tab`. A new tab needs a restart (no overlay). A tab with an unknown icon shows no picture. Codes `blocks-items.creative-tab-unknown` and `creative-tab-icon-unknown`. GameTests `MsmCreativeTabGameTest` (5), JUnit `CreativeTabParserTest` (3).
- **D3 as built** (B441, B455). The first two Mixins, in `dev.mcsupermods.runtime.mixin`, each with the DESIGN section 10 justification comment. `BlockItemPlaceMixin` at the head of `BlockItem.place` skips the client, non-`ServerPlayer`s and `!canPlace()`; a cancel returns `FAIL` and resyncs the inventory, the position and its six neighbours. `ServerExplosionMixin` at the head of `explode()` returns 0 on `cancel()`; `keepBlocks()` cancels the heads of `interactWithBlocks` **and `createFire`** (D3 named only the first), so entities are hurt and pushed but no block breaks, drops or burns. The event fires for every `ServerExplosion` (TNT, creepers, fireballs, wind charges, beds, respawn anchors, `World.explode`, the vehicle `explode` action). `ServerExplosionMixin` applies only at the first explosion, so `fixtures/sample-vanilla-blocks` explodes once at `server.started` and CI forbids the lines `Mixin apply` and `MixinTransformerError` on production jars through `tools/run-fabric-server --forbid-line` on both versions. `block.place` can fire for a placement that then fails; a cancelled explosion may still show smoke and sound. GameTests `MsmMixinEventGameTest` (8).
- **D4 amendments** (B455, B464a). `Entity.vehicle` and `Entity.passengers` had already shipped in Script API 1.5 (vehicles, ADR 0090 D11), so Script API 1.6 ("Since runtime 1.5.1", snapshot `script-api-v1-1.9.0.json`) adds `Entity.ride(vehicle)` and `dismount()` (vanilla boarding rules and cooldown; nothing rides a player), `World.itemsNear(pos, radius)` returning `DroppedItem` (`item`, `pos`, `age`, `owner`, `remove()`, `setItem()`; `owner` is undefined once the thrower is unloaded), `ItemRef.contents` (read-only) and the events `block.place` (cancellable), `world.explosion` (cancellable; `cancel` wins over `keepBlocks`; `cause` the direct source's type id or `"block"`) and `command` (`id`, `name`, `source`, `args`; runs after the command's function and event and before its message back). In `args` a `player` stays a UUID (scripts can look it up) while the macro value is the name (B464a). `CommandEvent.name` is the command's own name also when an alias was typed (B462b). GameTests `MsmScriptApi16GameTest` (8).
- **D5 as built** (B458, B458a). Triggers `any_block_placed` and `explosion` (both cancellable through the script bridge), `command_used` ("When a player types the command", subject a project `msm:command`), and two not in D5, `player_mounted` and `player_dismounted` (polled from `player.tick` every 5 ticks, since no event exists); steps `stop_placing`, `stop_explosion`, `keep_blocks_safe`, `ride` and `dismount`; conditions `is_riding`, `is_facing` (`of`, `direction`) and `caused_by` (an entity type or "a block"; explosions only); the value `facing` (words, offered in text slots only); the place `in_front_of_here`; slot type and subject sort `command`; codes `rules.not-for-trigger` and `rules.not-a-number`. The catalogue is 56 triggers, 44 steps, 19 conditions, 13 values and 7 places. **Differs from D5:** the command trigger picks an existing command rather than creating one (the Command Studio and the Custom command flow make it; the Rules section appears in the Command Studio). **Compilation:** plain rules on a command become the command's `event`: the generated `<id>_rules_command_used` takes the `event` field and starts with `trigger_event` of the hand-made event, so the hand-made actions run first and the rules' steps after (B462b's golden pins `/greet`'s `wave`, then the cookie; Try it logs `Ran /greet's event "wave" too.`). Script rules go through `run_script` in that event; a command that runs a function cannot also run an event, so its rules listen to the script `command` event filtered by `e.id`, and they do not run from the console or a command block. Entity facing is horizontal only; getting on and off is noticed up to a quarter of a second late, for players only.

## Status

Accepted with findings at close B468 (2026-11-15; unreleased, awaiting the user's in-game checks), with the defaults below; the user may still veto them. B440's S7 answer came before any Mixin was written. Vetoable defaults as built: commands as a kind with permission 0 by default, functions at level 2 whatever the player's level (D1); macro arguments into functions, players passed as names and entities as UUIDs (D1); creative tabs as a kind, items joining through `creative_tab`, `as_listed` as registration order, no hand ordering (D2); Mixins for the two events, `block.place` cancellable at the head and placements by players only, `keepBlocks` also stopping fire (D3); `itemsNear` as a new method rather than a flag on `entitiesNear` (D4); the Rules wording, the command trigger picking an existing command, plain command rules after the hand-made event (D5).
