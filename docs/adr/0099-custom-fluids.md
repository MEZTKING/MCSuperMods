# ADR 0099: Custom fluids

## Context

The research report ranks fluids eleventh ("a project fluid with a bucket, flowing rules and a texture": fuel and oil for vehicles, magic water, honey-like liquids); the coverage audit rates them L ("runtime + client rendering, probably a mixin"). Vanilla has them (water, lava), so the user's rule of 2026-11-14 applies.

Facts ([ADR 0101](0101-vanilla-parity-2-flows-studios-try-it-and-tests.md#fact-table-f1-to-f36-moved-from-the-plan-at-b485) F27–F30): the fluid API differs between the two targets more than anything the runtime has met.

- **26.3:** `Fluid()` has a no-argument protected constructor; `getBucket()` returns an `Item`; `FlowingFluid` has the `FALLING` and `LEVEL` properties and abstract `getFlowing()` and `getSource()`; a liquid is two registered fluids (the registry lists `water`, `flowing_water`, `lava`, `flowing_lava`, `empty`).
- **26.4-snapshot-7:** `Fluid(Fluid.Properties)` with `Properties.of()`, `bucketItem(ResourceKey<Item>)`, `soundEvent`, `dripParticle`, `explosionResistance`, `randomTicking`, `drag`, `fogType`, `fallDistanceMultiplier`; `getBucket()` returns a `ResourceKey<Item>`; `FlowingFluid` has `SOURCE` instead of `FALLING`, `getFlowing(int)`, `getSource()`, `isSource`, `isFalling`; a liquid is one registered fluid (`water`, `lava`, `empty`).
- **Both:** `LiquidBlock(FlowingFluid, Properties)` (protected), `BucketItem(Fluid, Item.Properties)`, Fabric's client `FluidRenderingRegistry.register(Fluid still, Fluid flowing, FluidModel.Unbaked)` and `FluidModel.Unbaked(Material still, Material flowing, Material overlay, BlockTintSource)` (rendering-fluids 6.0.6 and 6.0.10).
- **Entity behaviour:** Fabric's `EntityFluidInteractionRegistry` and `FluidBehavior` (swimming, drowning, boats) are in `fabric-content-registries-v0`, present for 26.3 only. Vanilla treats fluids in `#minecraft:water` and `#minecraft:lava` as water and lava for most entity rules (to be confirmed per version, S14).

## Decision

- **D1 Kind `msm:fluid`** (frozen):

  ```
  struct Fluid {
    behaves_like?: "water" | "lava" | "none",   // default "water": joins the fluid tag, so entities swim, drown and are put out
    flow?: { tick_delay?: int @ 1..100, slope_distance?: int @ 1..8, drop_off?: int @ 1..4, infinite?: boolean },
                                               // defaults water's 5, 4, 1, true; "lava" defaults 30, 2, 2, false
    light?: int @ 0..15,                       // default 0 (lava-like 15)
    tint?: int,                                // an RGB colour multiplied over the textures; default none
    explosion_resistance?: float,              // default 100, as water
    on_entity_inside?: string,                 // event while an entity is in it (cooldown 10 ticks, ADR 0061)
  }
  ```

  One element registers the fluid (one or two registry entries by target), its `LiquidBlock` under the element id and its bucket `<path>_bucket` (a `BucketItem`; a generated id, `blocks-items.generated-item-clash` on conflict). Editor-only `textures` (`still`, `flowing`, optional `overlay`; animated with `.png.mcmeta` as water's) and the bucket picture lower to assets; lang for the block, fluid and bucket; the fluid tag of `behaves_like`.
- **D2 The runtime behind a seam.** `registry/fluid/` holds the shared registration and the definition reader; the fluid classes live in `src/mc/26.3/java/.../fluid/MsmFluid.java` (a source and a flowing subclass) and `src/mc/26.4/java/.../fluid/MsmFluid.java` (one class over `Fluid.Properties`), both reading the same `FluidDefinition`. Flow numbers, infinite sources and the bucket are vanilla's `FlowingFluid` and `BucketItem` behaviour over our numbers; nothing is transcribed from `WaterFluid` or `LavaFluid`. The client registers one `FluidModel.Unbaked` per fluid in `MsmRuntimeClient` (shared; F29).
- **D3 Spike first.** B470 proves on both versions: registration and sync to a client on a dedicated server; flowing, sources and draining; bucket fill and empty (and dispensers); drawing through `FluidRenderingRegistry` (a client GameTest screenshot); swimming and drowning through the tag; fog. If 26.4 is a no-go, the reserve B486 makes fluids a 26.3-only feature (`export.not-on-target` on 26.4, the pattern of `renderer: geckolib`), vetoable.
- **D4 Versions and eject.** Plugin API 1.18.0 adds `BlockFacts.fluidModel?: "two_fluids" | "one_fluid"` (informational, for the Studio's wording) and `fluidTags`. The 26.3 generator warns `export.not-in-eject` (a follow-up).
- **D5 Not in this batch (limits).** Mixing rules (a fluid meeting water or lava making a block), cauldrons, bottles and potions of a fluid, fluids in pipes or tanks (Fabric transfer API), custom fog colours on 26.3, buoyancy and swim speed other than water's, boats on project fluids, fluid-specific drowning or burning damage, waterlogging by a project fluid (`SimpleWaterloggedBlock` is water only), and world generation of lakes of a project fluid beyond the existing lake feature with its block.

## Consequences

- The largest version seam the runtime has; both implementations are tested by the same GameTests on both versions.
- Vehicles' fuel and magic liquids gain a vanilla-looking source; Try it shows still and flowing pictures without simulating flow (ADR 0101 D5).

## Amendment after the spike (B470, 2026-11-15)

- **D3 answered: go on both versions.** 26.3 registers two fluids per liquid (`<id>` and `<ns>:flowing_<path>`); 26.4 one `FlowingFluid(Fluid.Properties)`. Flow, falling, draining, infinite sources, buckets, dispensers (vanilla's water bucket behaviour object, registered after vanilla's bootstrap), drawing through `FluidRenderingRegistry` with our textures and a plain RGB tint, and dedicated-server sync behave the same on both. Reserve B486 is not needed.
- **26.4 needs one Mixin** (accepted under ADR 0096's Mixin rules): `EntityFluidMixin` injects at the head of `Entity.isInWater` and `isInLava` and returns true when the entity's fluid height for that tag is above 0. Without it a water-like project fluid drowns entities but nobody swims or floats in it. The server's `isUnderWater` may need its own injection (verify at implementation). 26.4 copies `drag`, `fallDistanceMultiplier` and `fogType` from vanilla water or lava by `behaves_like`; fog on 26.4 comes from `fogType`, on 26.3 from the tag.
- **D1 corrected:** putting out fire and lava burning come from the fluid's own `entityInside` effects (`EXTINGUISH`; `LAVA_IGNITE` and `Entity::lavaHurt`), not from the tag; with them the damage numbers match vanilla. Swimming needs `#minecraft:swimmable` on 26.4. `behaves_like: none` is air-like on 26.3 and slow with no fall damage on 26.4 (a limit).
- **D4:** `fluidModel` is `two_fluids` on 26.3 and `one_fluid` on 26.4; `fluidTags` adds `swimmable` on 26.4; lowering writes the `flowing_` id into tags on 26.3 only.
- **D5 corrected:** on 26.3 a lava-like project fluid mixes with water by vanilla's rule (obsidian or cobblestone); on 26.4 only vanilla lava does. Recorded as a limit that differs per version.

## Findings at close (B485)

Recorded 2026-11-21 at the close of vanilla parity 2 batch 2 (B485) from the code on the session branch at 9bbbc65 and the plan's notes: B470 (1f7f25e, the spike), B472 (06fb4f2), B473 (f3f892b), B475 (15d219d), B477 (f131d47), B478 (090bc3f), B480 (ddae6de), B481 (083647c), B482 (724416f), B483 (9f8e915) and B484 (382e0f3, f16c4d4), and the validator added at the close. The facts are F27 to F30 and F34 and the limits Q25, Q26, Q28 and Q29 of [ADR 0101](0101-vanilla-parity-2-flows-studios-try-it-and-tests.md)'s fact table and limits. Unreleased; awaiting the user's in-game checks.

- **D1 as built** (B473, B475, B477). The kind `msm:fluid` lives in `@msm/plugin-blocks-items` (folder and registry `fluid`). Format gap fills: the fluid's events sit in its own `events` map, `tint` 0 to 16777215, `explosion_resistance` at least 0. The runtime's `loader/FluidParser` is closed, with defaults by `behaves_like`: water 5, 4, 1 and infinite; lava 30, 2, 2, not infinite and light 15 (as D1; the mcdoc `light` comment still says 0); `none` takes water's flow; no tint unless one is set, while the kind's default element writes water's `0x3f76e4`. `on_entity_inside` and `trigger_event` must name the fluid's own events (the runtime refuses the fluid; since B485 the app reports `blocks-items.fluid-unknown-event`). Lowering writes the definition without the editor fields, a single-variant block state naming `<ns>:block/<path>` whose element-less model carries the texture variables `still`, `flowing`, optional `overlay` and `particle`, a flat bucket model `<ns>:item/<path>_bucket`, the keys `block.<ns>.<path>` and `item.<ns>.<path>_bucket` (no fluid key: vanilla has none), no `.png.mcmeta` (an animated picture brings its own) and the tags of `BlockFacts.fluidTags`; missing pictures fall back to vanilla water's or lava's. Codes `blocks-items.generated-item-clash` (error), `fluid-flow-range` (warning; a fluid spreads `floor(7 / drop_off)` blocks), `fluid-texture-missing` and `fluid-no-fog` (warnings) and `fluid-unknown-event` (error).
- **D2 as built** (B475). `registry/fluid/MsmFluids` registers per definition the fluid (26.3: `MsmFluid` as the source and `MsmFlowingFluid` as `<ns>:flowing_<last segment>`; 26.4: one `MsmFluid` over `Fluid.Properties` with `drag`, `fallDistanceMultiplier` and `fogType` copied from vanilla water or lava), `MsmLiquidBlock` under the same id and the `BucketItem` `<ns>:<path>_bucket` (stack 1, a bucket left, in vanilla's Tools and Utilities tab); a taken id is an error and the fluid is skipped. Dispensers use vanilla's water bucket behaviour object, looked up in `onInitialize` after vanilla's bootstrap; the pickup sound is a 26.3 override and the 26.4 `soundEvent` property. Both versions apply the fluid's own `entityInside` effects by `behaves_like` (B470). `on_entity_inside` fires on the server only, at most every 10 ticks per entity whatever number of the fluid's blocks it touches, under the shared tick cap. Measured: the first spread after `tick_delay`, reach `ceil(8 / drop_off) - 1`, a hole found up to `slope_distance + 1` away. Logs `registered N fluid(s)`.
- **Fluid pictures** (B475, differs from D1 and from B477's decision). `client/fluid/FluidClient` registers one `FluidModel.Unbaked` per fluid, reading `still`, `flowing` and `overlay` from the liquid block's model inside the mod that shipped the definition, at client start, because `FluidRenderingRegistry` takes its materials before resources load. **A resource pack cannot change a fluid's pictures** (a limit in the guide); the tint is a plain RGB `BlockTintSource`.
- **D3 as built: the 26.4 Mixin** (B470, B472, B475). `mixin/EntityFluidMixin` (26.4 only, under ADR 0096's Mixin rules) has **three head injections**: `Entity.isInWater` and `isInLava` (true when the `#minecraft:water` or `#minecraft:lava` fluid height is above 0) and `isUnderWater` (eyes in `#minecraft:water`; the server needed it). One shared Mixin config cannot list a class that exists on one version, so `mixin/MsmMixinPlugin` adds it when the seam `mixin/MixinVersions` says so; a GameTest fails when the plugin leaves it out. Reserve B486 was not needed.
- **D4 as built** (B473, B478). `BlockFacts.fluidModel` (`two_fluids` on 26.3, `one_fluid` on 26.4) and `fluidTags` (26.4 adds `minecraft:swimmable`); lowering writes the `flowing_` id into tags on two-fluid targets only. Vanilla packs treat the fluid, its `flowing_` id, the liquid block and the bucket as mod-only, write fluid tag entries `required: false` and leave out recipes using a project bucket. The eject warns once per fluid.
- **D5 and the limits as found.** On top of D5: no fire spread, lava particles or random ticks for lava-like fluids; mixing differs by version (26.3 lava-like fluids make obsidian and cobblestone, 26.4 only vanilla lava does); `behaves_like: none` is air-like on 26.3 and slow with no fall damage and no fog on 26.4; Try it shows still and flowing pictures without flow (Q29). The Fluid flow's lakes are a `minecraft:lake` feature with MSM's own block predicates; vanilla's lava lake numbers were not checked (verify at implementation).
- **Tests** (B475, B477, B482). `MsmFluidGameTest` (22), `MsmFluidClientGameTest` (still and flowing pictures with the tint by `assertScreenshotContains`), JUnit `FluidParserTest`; goldens for water-like, lava-like, untagged and minimal fluids on both targets; `fixtures/sample-villagers-and-fluids` with `brine` (water-like, glowing inside) and `molten_amber` (lava-like, light 12), pinned in CI as `registered 2 fluid(s)`.
- **Open follow-ups.** Make `MsmRegistrar.checkEvents` public so fluid events get the block event checks; correct the mcdoc `light` comment (lava-like defaults to 15); sim-parity scenarios for `on_entity_inside`; in-game checks of lakes of a project fluid, swimming, burning and mixing; the D5 limits (mixing rules, cauldrons, bottles, pipes, boats, buoyancy, fog colours on 26.3, waterlogging by a project fluid); the eject.
- **Later (B544, 2026-11-22).** Vanilla parity 3 batch 2 closed most of these: mixing rules, cauldrons and bottles are in [ADR 0108](0108-fluids-2-mixing-cauldrons-and-bottles.md) (with `mixing` set, 26.3 and 26.4 behave alike); `MsmRegistrar.checkEvents` is public and checks fluid events; the mcdoc `light` comment now says a lava-like fluid defaults to 15; vanilla and project boats float on water-like fluids; the 26.3 eject writes fluids ([ADR 0112](0112-vanilla-parity-3-flows-studios-eject-try-it-and-tests.md) D3). Still open: fog colours on 26.3 (the client batch), fluid events in dev-mode overlays, sim-parity scenarios for `on_entity_inside`; pipes, tanks, other buoyancies and waterlogging by a project fluid are dropped as not vanilla.

## Correction (B525, 2026-11-22)

The limit "a resource pack cannot change a fluid's pictures" is wrong: a resource pack replacing the PNGs at the fluid's texture paths repaints it on both versions. Only re-pointing the liquid block's model in a pack has no effect, because `FluidClient` reads the model from the mod jar at client start. The guide says so.

## Status

Accepted with findings at close B485 (2026-11-21; unreleased, awaiting the user's in-game checks), with the defaults below; the user has not yet been shown them and may still veto them. B470 answered D3 with a go on both versions and one 26.4 Mixin. Vetoable defaults as built: `behaves_like: water` by default through the vanilla fluid tag, water's flow numbers by default, lava-like light 15 (D1); a fluid's pictures from the mod's own block model, not from resource packs (D2); the 26.4 `EntityFluidMixin` with three injections (D3); no eject for fluids yet (D4).
