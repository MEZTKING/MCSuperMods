# ADR 0085: Try it, an in-app test area

## Context

The user asked (2026-11-14) for a way to test what they build inside MSM: "Test inside the app — a built-in test view in MCSuperMods where you can walk around, place your blocks, see mobs and particles, without launching Minecraft at all."

The agreed real-game path is [ADR 0084](0084-one-click-play-and-reload.md): **Play** builds the jar, starts the managed Prism instance and opens a flat test world; **Reload** swaps data, scripts, event lists and pictures in place; a new block, item or mob still needs a restart, because registries freeze at start (DESIGN §10). Play needs Prism Launcher, a Microsoft account, Java and tens of seconds per start. An in-app view can be instant and needs none of those, but it cannot be Minecraft.

What the app already draws (facts T1–T14 in `docs/PLAN-test-world.md`): block and item models and structure templates with deepslate 0.27.2 (`StructureRenderer`, which rebuilds single chunks through `updateStructureBuffers(chunkPositions)`), mobs with the app's own raw WebGL 1 geo renderer (bones, keyframes, the same baker the runtime's vanilla renderer is checked against through `fixtures/geo-parity`), and particles with `particle-sim.ts`, the TypeScript twin of the runtime's `ParticleLook`, tied to it by `fixtures/particle-look/golden.json`. All three are lazy chunks of about 18 to 20 kB on top of the shared deepslate code. The e2e suite already runs WebGL under SwiftShader.

What the app does not have: any Java discovery (Prism runs Java for Play), any server download (only Fabric API is downloaded; the Fabric and vanilla server downloads live in the dev tool `tools/run-fabric-server`), any Minecraft network protocol code, and any model of the game's rules. Behaviour lives in the runtime mod: vanilla block classes per block type (ADR 0067), vanilla mob goals (ADR 0070), triggers and actions (`events/EventRunner.java`), scripts on Rhino (ADR 0031) and Rules compiled to events and scripts ([ADR 0082](0082-rules-no-code-behaviour.md)).

## Decision

- **D1 What it is.** MSM gains **Try it**: a small flat test area drawn inside the app, where the user walks or flies, places and breaks the project's blocks, sees their models and states, and (in later slices) spawns the project's mobs, sees particles, uses items and watches their Rules and events run. It is a **preview**. It runs MSM's own small simulation of what MSM's own definitions say; it does not run Minecraft, Fabric, the runtime mod or any Mojang code. Play (ADR 0084) stays the real check and is one click away from inside the view at all times.
- **D2 Approach: the existing renderers plus our own simulation, in the renderer process.** The view reuses deepslate's `StructureRenderer` over a mutable world for blocks, the geo renderer for mobs and `particle-sim.ts` for particles, in one new lazy chunk (`app/src/renderer/src/tryit/`; the name `sandbox` already means the plugin sandbox). The rules of the test area live in a new pure package `@msm/sim` (`packages/sim/`, no DOM, no Node, no Electron; depends on `@msm/plugin-api` and `@msm/core` types only): a world of block states, a player controller, a block catalogue, entities, and an interpreter for triggers and actions. No new runtime dependency is added.
- **D3 The simulation reads lowered files, not elements.** The view lowers the expanded project (ADR 0082 D3, B371) for the current target and gives `@msm/sim` the output files the game would get: `msm/<ns>/<kind>/<path>.json` definitions, blockstates, models, item definitions and lang. So Try it shows what the export holds, Rules that compile to plain events work without special cases, and a lowering bug is visible here too. Editor-only fields never reach the simulation.
- **D4 Live.** The area updates as the user edits: a change to an element re-lowers that element (debounced), swaps its definitions, models and textures, and keeps the world. A new block, item or mob appears at once; there is no restart in Try it. A block state the edited definition no longer has falls back to the block's default state; a removed thing is taken out of the world with a line in the log.
- **D5 Fidelity levels.** Every behaviour belongs to exactly one level, and the level decides how it is shown:
  - **Shown as in the game (checked by tests against the runtime where a test can check it):** block models, block states and item models from the lowered files; placement orientation of the block types (pillar axis, horizontal and directional facing, slab halves and doubling, stairs facing and half, door halves and hinge, trapdoor half, fence, wall and pane connections to neighbours); opening doors, trapdoors and gates by hand where the set type allows it; a button's press time; pressure plates under the player; crop and sapling ages stepping through their stages; `lit` and `open` pictures; `msm:shape` boxes for walking and picking; mob model, texture, scale and the `idle` and `walk` animations as the app's geo preview plays them; particle looks by `particle-sim.ts`; which trigger fires and which actions run, in order, with cooldown and chance.
  - **Approximate, and labelled so:** walking, jumping and flying (Minecraft-like numbers, our own collision code; no sprint-jump tricks, ladders, water, slime or ice); mobs "wander" (a random walk on the floor, or hovering for flyers; no targets, no pathfinding, no attacks, no breeding or taming); growth uses a "Grow" tool and a fast clock instead of vanilla's random tick odds; container and machine screens are plain mock-ups from the definition (title, rows, slots; no Mojang GUI art, no item movement rules, no smelting); portals show their look and their particles, and stepping in logs "would travel to <dimension>".
  - **Not simulated, and always said out loud:** `run_function` and every command; scripts and logic Rules until slice 4 (D9); redstone beyond the block's own `powered` picture toggled by a "Power" tool; light levels and shadows; liquids; survival (health, hunger, damage numbers, armour, tools' mining speed and durability, drops and loot); status effects beyond a chip naming the effect; mob AI, spawning rules, variants by biome, boss fights; world generation, structures, dimensions and travel; vanilla blocks' behaviour (a vanilla block from the picker is a prop: drawn, solid, breakable, nothing more); other mods; multiplayer; the client's HUD and sounds of vanilla (R13 of the Rules plan: vanilla sound files are not in the client jar).
  Whenever the simulation meets something of the third level it writes one plain line to the log ("Only in Minecraft: run function mymod:greet") instead of doing nothing. Silence is the failure mode this ADR forbids.
- **D6 No survival numbers.** Try it has no health bar, hunger, damage or loot. Balance cannot be judged in a simulation that does not run the game's combat and mining code, so the view offers nothing that invites it. `damage`, `heal` and `apply_effect` actions appear in the log and as a short chip ("Poison for 5 seconds"), not as a changing number.
- **D7 Labelling.** The view carries a permanent strip, not dismissible: **"Preview, not the real game."** with **Play in Minecraft** beside it (ADR 0084 D1; "Test in Minecraft…" where Play is unavailable). The floor is MSM's own drawn grid, on purpose not a Minecraft landscape, so a screenshot cannot pass for the game. The first time the view opens, a three-line card says what is real here (looks, states, which rule runs), what is rough (movement, mobs) and what is not here (commands, redstone, survival), with a link to the guide page's limits list. Approximate things carry their label where they appear (the mob's name plate reads "wanders only in the preview"). Very easy mode uses the same words.
- **D8 "What happened".** A side panel lists, newest first, what the simulation did and why, in words and by display name: "You used Ruby Block. Rule 'Ruby gift' ran. Gave you 2 Ruby. Played sound Chime." and the "Only in Minecraft" lines of D5. Each line links to the rule card, the event or the Studio field it came from. This is the part where Try it is better than the game, not only faster: it explains.
- **D9 Slices.** Built in four slices, each shippable alone (briefs in `docs/PLAN-test-world.md`):
  1. **Look and place** (B385–B392): the area, walking and flying, placing and breaking project blocks and vanilla props, block types and their states, growth with the Grow tool, live update, the strip and the first-run card. Gated by a measurement brief (B385, D11).
  2. **Mobs and particles** (B393–B395): spawn eggs, models with idle and walk, wandering, ambient particles, portal looks.
  3. **Things happen** (B396–B399): triggers and actions, "What happened", project sounds, effect chips, item use, container mock-ups, and the shared parity fixture (D10).
  4. **Scripts and logic Rules** (B400–B401): the project's transpiled scripts in a Web Worker against a Script API shim backed by `@msm/sim`. Started only after slice 3 has been used by the user and the Rules batch is closed; it is the largest slice and the one most likely to diverge from Rhino and the real API, so every unsupported call logs "Only in Minecraft".
- **D10 Keeping it honest: shared scenarios.** In the style of `fixtures/particle-look` and `fixtures/geo-parity`, a new `fixtures/sim-parity/scenarios.json` holds small scripted scenarios over a fixture project (place this block looking north, use it, step on it, wait 30 ticks) with the expected block states, fired triggers and action order. A runtime GameTest plays each scenario in the real server and checks or regenerates the expected values; a Vitest test plays the same file through `@msm/sim`. A behaviour of D5's first level without a scenario is refused at review; a behaviour that cannot be put in a scenario belongs to the second or third level.
- **D11 Size and speed.** No new dependency; the new lazy chunks are budgeted at 0.4 MB of `app.asar` in all (measured per brief; stop and report above 31 MB as in the Rules plan). The area is 48 by 48 blocks and 32 high, meshed in 8-block chunks so one placed block rebuilds one small chunk. B385 measures before anything is built: frame rate and rebuild time under SwiftShader (the worst case) and on a hardware GPU when the machine has one, sharing one WebGL context between deepslate and the geo renderer. Go threshold: 20 frames a second under SwiftShader at 640 by 360 with 2,000 placed blocks, and a single-block rebuild under 16 ms. If the context cannot be shared, mobs draw on a second stacked canvas; if the frame rate fails, the area shrinks or the slice stops and this ADR is revisited. The view renders only while visible and focused, at a capped 60 frames a second, with a "Smaller picture" option that halves the resolution.
- **D12 Without WebGL, offline, Windows.** Without a WebGL context the view shows the existing "WebGL is not available" message and the Play button; nothing else in the app changes. Try it needs no network, no Java, no launcher and no account. Vanilla props and vanilla parent models need the user's client jar (ADR 0011) exactly as the preview panel does; without it project blocks on MSM's fallback parents still draw and vanilla props are left out of the picker. Mouse look uses pointer lock (Esc releases it, as everywhere); every action also has a key, so the view is usable and testable without the mouse. Nothing in it is Windows-specific.
- **D13 Where it sits.** A **Try it** button next to Play in the toolbar (all three modes), View > Try it, the palette, and `F6`. It opens as a view in the editor area, like Home, and keeps its state while the user switches to a Studio and back; closing the project or pressing "Clear the area" resets it. The area is not saved (a test area that outlives a session invites building in it). The hotbar and a picker list the project's blocks, items and spawn eggs first.
- **D14 One boundary for a later live source.** The view talks to the simulation only through a `WorldSource` interface (block changes, entity snapshots, effects and log lines out; player actions in). `@msm/sim` is the only implementation now. The interface is what a later "watch the real game" source would implement (D15); nothing else is built for it.
- **D15 Not chosen now: mirroring a headless real server.** See Alternatives. Deferred, not rejected: it is revisited if users report that Try it misleads them about behaviour and Play is still too slow or unavailable for them, and only after the Play batch has been checked on Windows.
- **D16 No plugin API in this ADR.** Third-party kinds are drawn only if they lower to files the simulation already understands (models, blockstates, `msm` definitions of built-in kinds). A contribution point for plugin-defined simulation is not added until a plugin asks.

## Alternatives considered

- **(a) Extend the deepslate preview into an interactive view, with our own rules (chosen, D2).** Smallest step from what exists; no download, no Java; live editing without restarts. Its cost is honesty: everything that is not looks must be either rebuilt and tested against the runtime (D10) or labelled (D5, D7).
- **(b) A separate lightweight engine** (three.js or a voxel engine library). Adds a renderer the app does not have (three.js is about 600 kB, ADR 0010) and a second model pipeline that must again be made to agree with deepslate's and with the game's. deepslate already reads blockstates, multipart, models, tints and atlases the way the game does. Rejected; `@msm/sim` is our own, but only for rules, not for drawing.
- **(c) Embedding the real game.** Rejected. The client cannot be redistributed or bundled (Mojang's licence; golden rule "never bundle Mojang assets"); starting it legitimately needs the user's account and a launcher, which is exactly Play; it draws in its own native window, which cannot be placed inside an Electron view except by fragile window re-parenting; it needs Java 25 and the full game files; and it would still restart for every new block. It would be Play with a worse window.
- **(d) Hybrid: a local headless Fabric server running the user's jar, mirrored into the app's own renderer.** Assessed in detail because it promises real behaviour:
  - *What it gives:* the real server side: block classes, redstone, mob AI, loot, commands, functions, events, scripts on Rhino, Rules as shipped. It runs on Linux too, so CI could test all of it.
  - *What it does not give:* anything the client does. Models, animations, particles spawned on the client (ambient particles, break and step effects), sounds, screens and the HUD are not on a server; our renderer would still approximate them. And **movement is the client's job in Minecraft**: the server only checks what the client reports, so our own walking code is needed in this option as well.
  - *The "you" problem:* mobs react to players in the level's player list. Fabric's `FakePlayer` (present in `fabric-events-interaction-v0`) is deliberately not in that list and its connection drops every packet, so it can place and use blocks but mobs do not see it and nothing is sent to it. Being a real player means either speaking the vanilla network protocol from the app (login, registry sync, chunk and entity packets, all version-specific and changed in most snapshots; no protocol code exists in MSM; third-party JavaScript libraries trail releases, 26.x support verify at implementation) or adding Mixins to fake a connection, against the Mixin policy (DESIGN §10).
  - *Capturing effects:* particles and sounds the server sends exist only as packets to nearby players, so a bridge mod must either own a real connection or intercept the level's send methods.
  - *What the user's machine needs:* Java 25 found or downloaded (the app has no Java discovery today; Prism brings its own for Play), the Fabric server launcher and Mojang's server jar downloaded on first use (tens of MB, from Mojang's servers by the user's machine), the user's one-time agreement to the Minecraft EULA (the app must not accept it silently), 1.5 to 2.5 GB of memory beside Electron, a first start of 20 to 60 seconds and the same restart for every new block, item or mob as Play (the registry freeze does not go away). A child server process must be supervised and bound to loopback only.
  - *Effort and risk:* about 25 to 35 briefs against about 17 for (a) through slice 3: Java discovery or download, server install and supervision, EULA flow, a viewer bridge in the runtime (state out, actions in, dev mode only), a real-player strategy, a renderer for a full vanilla world, per-version upkeep of whichever protocol is chosen. High risk on the player and effects problems; medium on Windows process handling.
  - *Verdict:* for a slower start than Try it and the same restart rule as Play, it delivers server truth drawn by an approximate client, while Play delivers the whole real game in one click. It does not earn its cost now. D14 keeps the door open at the price of one interface.
- **A recorded tour of the real game** (CI or the user's Play session records states and the app replays them). Not interactive; rejected for this request, though D10's scenarios are a small, testable form of the same idea.
- **Only improve Play.** Play already is the real check, and nothing here replaces it. But it cannot be instant, cannot explain which rule ran, and needs a launcher and an account before a first-time user sees their block. Try it covers that gap.

## Consequences

- A first-time user sees and walks around their block seconds after making it, with no launcher. Play remains the only place where behaviour, feel and balance are true, and the view says so permanently.
- MSM takes on a second, partial implementation of its own behaviour model in TypeScript. It can drift from the runtime; D3 (lowered files), D10 (shared scenarios) and D5's "say it out loud" rule bound the drift, and each new runtime behaviour must now be given a level (shown, approximate or not simulated). Reviews of runtime briefs gain one question: "what does Try it say about this?"
- New package `@msm/sim` and one line in `tools/check-deps/layers.json`; new app folder `tryit/`; a new fixture and one GameTest class; a guide page with the limits list. `app.asar` grows by an estimated 0.4 MB.
- The toolbar gains a third test button (Try it, Play, Reload). ADR 0083 D4's Very easy toolbar list gains **Try it** before Play.
- Risk: users take a pass in Try it for a pass in the game. Mitigations are D5 to D8; the residual risk is accepted and listed as limit T1 in the plan.
- DESIGN §8 (a "Try it" subsection after "Test in Minecraft"), §14 (no new dependency; the chunk), §15 (the package), §16 (the parity fixture) and the ROADMAP change when this ADR is accepted; they are not changed while it is Proposed.

## Status

Accepted (2026-11-14), with the defaults below; the user may still veto them. Vetoable defaults: building the in-app view at all rather than only Play; our own simulation rather than the headless-server mirror (D15 deferred); the name "Try it" and the wording "Preview, not the real game."; `F6`; the strip that cannot be dismissed; MSM's drawn grid floor rather than a Minecraft-looking one; the area of 48 by 48 by 32 and that it is not saved; no health, hunger, damage numbers or loot (D6); mobs that only wander, with the label; vanilla blocks as props only; container screens as mock-ups without Mojang art; the "Grow" and "Power" tools instead of random ticks and redstone; "What happened" as a side panel; scripts and logic Rules left to slice 4 and started only after the user has tried slice 3; the go thresholds of D11; Try it in the Very easy toolbar; no plugin contribution point.
