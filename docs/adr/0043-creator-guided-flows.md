# ADR 0043: The Creator (guided no-code flows with a live preview)

## Context

The user asked (2026-11-05) for "a workflow system for beginners that shows in realtime what you want to make, with almost no coding required; you should be able to make entire gears, and also have the option to manually adjust anything", planned together with the AI helper ([ADR 0041](0041-ai-helper.md)) so both share one changeset, preview and single-undo Apply. What exists:

- Starters with parameters ([ADR 0040](0040-wizards-as-parameterised-starters.md), B156): `ProjectStarter.parameters` describes friendly fields (string, number with min/max/step, boolean, colour, choice), `build(context)` reads `context.values` and returns a content bundle (elements plus generated placeholder assets); the host renders a multi-step New project dialog. The Custom ore, Custom sword and Custom mob starters have parameters; the library also builds bundles into an existing project (`session.addBundle`, "Copy into my project", one undo step). Generators are pure: the same values on the same target give the same bundle, byte for byte (the `examples/` mirror test relies on it).
- The AI helper plan ([AI-HELPER-PLAN.md](../AI-HELPER-PLAN.md), B172) adds the pending changeset: change items with before/after views, conflicts, per-item accept, `checkProject` over a scratch project, and `applyChangeset` as one undo step.
- Previews: deepslate renders block and item models from project assets and the vanilla cache (`preview/`, [ADR 0010](0010-preview-with-deepslate.md)); the geo preview renders Bedrock geometry with a texture ([ADR 0029](0029-model-animation-pipeline.md) D5); the Recipe Studio draws crafting grids.
- Armour and custom tool materials are added by [ADR 0042](0042-armour-and-custom-tool-materials.md).
- `Element.meta` holds `notes` and `tags`; assets have no meta.

## Decision

**D1. Creator flows are starters.** No new contribution point. A flow is a `ProjectStarter` with `parameters` and the additive `creator?: { group: 'gear' | 'blocks' | 'food' | 'mobs' | 'scripts'; blurb: string }` field (plugin API 1.x). The Creator lists every starter that has `creator`, grouped; a starter without `creator` stays a New-project starter only. Flows build bundles through the same `build(context)` as before, so the library's tests, the `examples/` mirror and the AI helper's `add_starter` tool cover them unchanged, and a third-party plugin can contribute a flow. New parameter type `set` (`type: 'set'`, `choices`, `default: string[]`, optional `min`) for "which pieces"; the New project wizard renders it as a checkbox list.

**D2. The flows.** In `@msm/plugin-library`:

- **Gear set** (`gear-set`, group `gear`): `material_name` (string, default "Ruby"), `colour` (colour), `material_source` (choice: `ore` makes an ore block, its loot table and a storage block as the Custom ore starter does; `item` makes only the material item), `tier` (choice: a vanilla tool tier, or `custom`), with the custom tier's `durability`, `speed`, `attack_damage_bonus`, `enchantment_value` and `mines_like` (choice of vanilla levels for `incorrect_blocks_for_drops`), `armor_base` (choice: a vanilla armour material to copy stats from, or `custom` with `durability`, `defense` sliders per slot, `toughness`, `knockback_resistance`), `pieces` (set: sword, pickaxe, axe, shovel, hoe, helmet, chestplate, leggings, boots; all by default). It builds the material item (`msm:item`, `ingot` or `gem` texture), the optional ore and storage block with their recipes and loot tables, each tool as an `msm:item` with `msm:tool` and the shaped vanilla recipe (`minecraft:item/handheld` model, silhouette texture tinted from `colour`), each armour piece with `msm:armor` and its recipe, one `minecraft:equipment` element and the two layer textures, lang keys for everything, the `minecraft:tag/item` entries vanilla expects (`swords`, `pickaxes`, `axes`, `shovels`, `hoes`, `head_armor`, `chest_armor`, `leg_armor`, `foot_armor`, plus the `enchantable/*` tags; verify the list against the target's vendored item tags) and the `msm:mod` element. Ids derive from `material_name` (`ruby`, `ruby_sword`, `ruby_helmet`, equipment `ruby`).
- **Ore and block set**: the existing Custom ore starter gains `creator: { group: 'blocks' }`.
- **Simple block** (`simple-block`, group `blocks`): name, colour, pattern, hardness, tool and tier, light level, whether it drops itself, an optional recipe from a chosen vanilla ingredient.
- **Food** (`food`, group `food`): name, colour, nutrition and saturation sliders, "can always eat", an optional recipe.
- **Mob**: the existing Custom mob starter gains `creator: { group: 'mobs' }`.
- **Scripted behaviour** (`scripted-item`, group `scripts`): an item whose `msm:on_use` runs a generated `msm:script` chosen from a few behaviours (heal, launch upward, strike lightning at the looked-at block, give an effect) with their numbers as parameters; the script's lines are generated from a template so the user can open it in the Script Studio and edit.

Every flow's defaults validate with zero problems on every supported target and export (the library test); flows that need kinds a target lacks declare `supports`.

**D3. The Creator UI.** A full-size dialog (`CreatorDialog`) opened from the toolbar ("Create…"), File > "Create…", the palette ("Create with the Creator…") and the empty-project welcome: a flow picker (groups, blurbs), then the flow's fields on the left (rendered from `parameters` by the wizard's `ParameterField`, all on one page, grouped by `group`), and on the right a **live preview** that rebuilds the bundle on every change (debounced 150 ms, in the renderer; `build` is pure and fast; an async `build` from an external plugin is awaited with the latest values winning): tabs *Items* (every item model rendered by the deepslate preview over a bundle-backed asset source, with the generated textures as `data:` images), *Blocks* (block models), *Recipes* (crafting grids from the Recipe Studio's grid component), *Armour* (the layer textures on a hand-written humanoid preview geometry in the geo renderer, preview only), *Stats* (tool and armour numbers, food values, block hardness, in words), *Elements* (the list of elements and assets that will be created, with conflicts against the open project). No apply is needed to see anything; "Create" turns the bundle into change items ([ADR 0041](0041-ai-helper.md) D5) and applies them as one undo step ("Create <flow title>"); conflicts (an id that exists) are shown before and skipped unless the Creator is editing that very set (D4).

**D4. Manual adjustment and reopening.** Everything the Creator makes is ordinary elements: "Open in Studio" and Raw JSON work on every piece; the Creator writes `meta.creator = { flowId, setId, values }` on each element it creates (`setId` a UUID per Create; `ElementMeta.creator` is additive in `@msm/core`). "Edit in Creator" on any such element reopens the flow with the stored values. On Create from a reopened set, for each element the flow generates now: the element is **untouched** when its current data equals the data the flow produces for the *stored* values on the project's target (generators are pure, so the previous output is recomputed, not stored); an untouched element is replaced; a hand-edited element is **kept** and listed under "Kept your edits" with a per-element "Overwrite" toggle; an element of the set the new values no longer produce (a piece unticked) is removed when untouched, otherwise kept and listed; new pieces are created; assets follow the same rule by bytes. The whole edit is one changeset and one undo step. Elements the user renamed keep their `meta.creator` through the rename command, so they still count as part of the set under their new id (matched by the stored output id in `meta.creator.generatedId`).

**D5. The AI helper drives the same flows.** The helper's `list_starters` tool reports `creator` groups and parameters, and `add_starter` runs any flow with values ("make a sapphire gear set" becomes one `add_starter` call with `material_name: 'Sapphire'`); the resulting change items carry `meta.creator`, so the user can reopen them in the Creator afterwards. One generator layer, two front ends.

**D6. Rejected.** *A separate "creator flow" contribution point:* duplicates starters and splits the library tests. *Preview by applying to the project and undoing:* pollutes the undo stack and the validation pass; the bundle is previewed from memory. *Storing hashes of generated data in meta:* recomputing from the stored values is simpler and survives generator fixes (a fix changes what "untouched" means for an old set only when the output changed, and the user then sees a diff in the review). *A free-form visual editor of textures and models:* out of scope; the Creator makes placeholders the user replaces in the Studios or Blockbench.

## Consequences

- Plugin API 1.x gains `ProjectStarter.creator` and the `set` parameter type (additive); `ElementMeta.creator` in core; four new starters (Gear set, Simple block, Food, Scripted behaviour) and `creator` on two existing ones; the `examples/` mirror and the library counts grow.
- The Creator depends on [ADR 0042](0042-armour-and-custom-tool-materials.md) (armour) and on the AI helper's changeset (B172); it is the second front end of the same generator and apply machinery.
- The preview gains a bundle-backed asset source and a humanoid armour geometry (preview only, written from scratch).
- Ships in 0.7.0 with the AI helper when the Creator briefs finish in time; otherwise 0.7.0 ships the AI helper and armour, and the Creator follows as 0.8.0 (the plan says which).

## Status

Proposed (2026-11-05). Implemented by B183 (library flows, API additions), B184 (Creator UI, preview, reopen rule) and B185 (tests, e2e, guide); accepted with the release that ships it.
