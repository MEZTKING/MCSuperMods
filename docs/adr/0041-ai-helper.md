# ADR 0041: The AI helper (Claude assistant in the app)

## Context

[DESIGN §18](../DESIGN.md#18-open-questions) question 14 and the ROADMAP's "Post-1.0 Ideas" record the user's request for optional AI help through the Claude API with their own key, "may be pulled ahead of 1.0 if the user asks". On 2026-11-05 the user asked: the helper goes ahead of the remaining Phase 7 briefs (B160–B162), and it must be able to **build whole content from one prompt** ("make a ruby tools mod with ore, blocks, items, recipes, a mob"), one-shot or step by step, not only answer questions and suggest edits.

Facts checked on 2026-11-05 (the claude-api skill, the npm registry, the repository):

- The official SDK is `@anthropic-ai/sdk`; `1.6.0` was published 2026-11-05, `1.5.0` on 2026-11-04 (peer `zod ^3.25.0 || ^4.0.0`, optional; the catalog has zod 4.6.7). Bundled with esbuild for Node, minified, the SDK is **414 kB** (1.3 MB unminified); with `helpers/beta/zod` and zod external, 414 kB. `app.asar` is 29.3 MB of its 32 MB budget after B153, so a lazy, minified main chunk fits without a budget change.
- Models: `claude-opus-5-5` (the default; thinking always on, `thinking: { type: 'disabled' }` or `budget_tokens` return 400, effort default `medium`, forced `tool_choice` `any`/`tool` return 400, no assistant prefill), `claude-sonnet-5-5` and `claude-haiku-5-5` (same rules; Haiku has no server-side refusal fallback). Exact ids, no date suffixes. Effort is `output_config.effort`. Thinking summaries need `thinking: { type: 'adaptive', display: 'summarized' }`; thinking blocks are bound to the model and the conversation and must be passed back unchanged, with history kept append-only. Refusal fallback: beta `server-side-fallback-2026-07-01` with `fallbacks: 'default'` on the beta messages endpoint. Task budgets: beta `task-budgets-2026-03-13`, `output_config.task_budget: { type: 'tokens', total }`, minimum 20,000, supported on the three models. Streaming: `client.beta.messages.stream(...)` and `finalMessage()`, `max_tokens` about 64,000; client tools take `eager_input_streaming: true`, so the client validates every tool input itself. Prompt caching is a prefix match: a stable system prompt and a deterministic tool list first, `cache_control: { type: 'ephemeral' }`, volatile content after. Typed errors (`Anthropic.AuthenticationError`, `RateLimitError`, `APIError`). Prices (first-party, per million tokens): Opus 5.5 $4 in, $20 out; Sonnet 5.5 $2, $10; Haiku 5.5 $0.10, $0.50 (verify at implementation).
- The app: project state lives in the renderer's `ProjectSession` ([ADR 0007](0007-renderer-hosted-core-and-platform-adapter.md)); every edit is a `ProjectCommand` on the command stack; `addBundle` already applies many elements and assets as one undo step (`bundleCommand`); schema validation (`validateJson`), plugin validators, mcfunction and TypeScript checks run in the session; the library (templates, starters with parameters after [ADR 0040](0040-wizards-as-parameterised-starters.md), examples) and the placeholder texture generator (`placeholderPng`, `@msm/plugin-library`) exist; the renderer's `Markdown.tsx` renders a safe subset; settings live in `<msmHome>/settings.json` (main); IPC is zod-validated and versioned (`msm:v1:<domain>:<op>`); `electron-updater` is a lazy main chunk behind `AutoUpdaterLike`; the renderer is served from `msm-app://` with CSP `connect-src 'self'` ([ADR 0035](0035-plugin-sandbox-and-capability-manifest.md) D1a), so the renderer cannot call the API even by mistake.
- Third-party plugins have no network, no editors and no commands (ADR 0035), so the helper cannot be a plugin; it is host code that reaches plugin content only through the session, which makes every kind, template, starter and validator (built-in or external) available to it with no per-plugin work.

## Decision

**D1. Bring your own key; the key never leaves main.** The user pastes an Anthropic API key in Settings > "AI helper". Main encrypts it with Electron `safeStorage` and stores the bytes in `<msmHome>/ai-key.bin` (never in `settings.json`); the renderer receives only `{ set: boolean; tail: string | null }` (the last four characters). "Test key" makes one tiny request and reports the typed error class on failure. "Clear key" deletes the file. When `safeStorage.isEncryptionAvailable()` is false (Linux without a keyring, CI) the store refuses to save and the dialog says so; releases are Windows only, and tests use the scripted client of D9. No other credential sources (environment variables, profiles, proxies, base URLs) in v1. Nothing is sent to Anthropic until the user opens the helper and sends a message; the Settings section and the panel's first screen state what is sent (D7).

**D2. The SDK runs only in main, as a lazy chunk; the logic is a package.** New workspace package `packages/ai/` (`@msm/ai`, layer `["@msm/plugin-api"]`, types only) holds everything that does not need Electron: the protocol types, the tool catalogue (zod schemas and the JSON Schema sent to the API, descriptions), the run loop over a `ModelClient` interface, the budget accounting, the system prompt, the model table with prices and the `ScriptedModelClient` for tests. Its second entry point `@msm/ai/sdk` holds the only import of `@anthropic-ai/sdk` (`createAnthropicModelClient`); main loads it with a dynamic `import()` so electron-vite emits a separate chunk (`ai-client-*.js`), minified like `scripting-engine` (the vite plugin `minifyScriptingChunk` gains the prefix). Biome forbids `@anthropic-ai/sdk` and `@msm/ai/sdk` in the renderer and the preload. The SDK version is pinned in the catalog (`1.5.0` or newer; verify at implementation: at least two weeks old at the time). CSP and the renderer's origin do not change.

**D3. A manual agent loop in main; tools execute in the renderer.** `runAssistant(...)` in `@msm/ai` drives one *run* (one user message until `end_turn`): it streams a request, forwards text and thinking-summary deltas as events, collects the final message, checks `stop_reason` (`refusal` with `stop_details` and `max_tokens` end the run before any tool runs), validates every `tool_use` input against the tool's zod schema (a failure becomes a `tool_result` with `is_error: true` and the raw input, never an executed tool), sends the tool requests to the host, and appends **all** results of a turn as one user message. History is append-only; thinking blocks go back unchanged; a conversation is bound to the model it started with (changing the model starts a new conversation). Request shape: `client.beta.messages.stream({ model, max_tokens: 64000, system: [{ type: 'text', text, cache_control: { type: 'ephemeral' } }], tools (deterministic order, each with eager_input_streaming: true), tool_choice: { type: 'auto' }, thinking: { type: 'adaptive', display: 'summarized' }, output_config: { effort, task_budget? }, betas, fallbacks, messages })`; the volatile project context (target, namespaces, counts, the pending changeset summary) is a text block at the start of the run's user message, after the cache breakpoint. Main owns the conversation's `BetaMessageParam[]` per conversation id (the renderer never sees raw thinking blocks); the renderer owns the display transcript. The IPC domain is `msm:v1:ai:*`: invoke channels `keyStatus`, `setKey`, `clearKey`, `testKey`, `start`, `cancel`, `toolResult`, `newConversation`, `dropConversation`; one main-to-renderer event channel `msm:v1:ai:event` carrying `{ runId, event }` with `text_delta`, `thinking_delta`, `tool_request`, `tool_done`, `usage`, `fallback`, `done`. Tool execution is a round trip: main pushes `tool_request { requestId, name, input }`, the renderer runs it against the session and answers with `ai:toolResult { runId, requestId, content, isError }`. Cancel aborts the stream (`AbortController`), answers any open tool request with an error result on the host side and ends the run with `done { reason: 'cancelled' }`; a cancelled run leaves the conversation consistent (the partial assistant turn is dropped, nothing is appended).

**D4. Tools, in four groups.** Names are fixed here; schemas live in `packages/ai/src/tools/`.

- *Read-only:* `project_summary` (target facts, namespaces, element counts per kind, whether an `msm:mod` element exists, the pending changeset summary), `list_kinds`, `kind_schema { kind }` (a compact text rendering of the kind's mcdoc struct, bounded depth and length), `list_elements { kind?, namespace?, filter? }`, `read_element { id }` (data and its current problems), `list_problems { elementId?, severity? }`, `list_templates { kind?, category? }`, `template_data { templateId, id }` (the element data the template would create), `list_starters` (with parameters and defaults), `target_facts`, `script_api_typings`, `pending_changes`.
- *Proposals (never applied directly; they go into the run's changeset, D5):* `create_elements { elements: [{ id, kind, data }] }` (one or many in one call), `update_element { id, data }` (whole data; the host shows a diff), `delete_element { id }`, `rename_element { from, to }` (references updated as F2 rename does), `create_texture { namespace, path, pattern, colour }` (a placeholder PNG from the library's generator; never Mojang assets; the only way the helper creates binary assets), `add_starter { starterId, namespace, values }` (a whole starter bundle, with [ADR 0040](0040-wizards-as-parameterised-starters.md) parameter values, as changeset items; Creator flows are starters, so "make a sapphire gear set" is one such call, [ADR 0043](0043-creator-guided-flows.md) D5).
- *Checks:* `run_checks { scope: 'pending' | 'all' }` builds a scratch project (the current project with the pending changeset applied through the same `ProjectCommand.apply` functions, no stack) and returns its problems from schema validation, plugin validators, the reference index, the mcfunction checker and the TypeScript check, grouped by element. The helper is told to run it after every batch and before finishing.
- *User decisions (the tool result is the user's answer; no deadline, cancel ends them):* `propose_plan { title, items: [{ itemId, kind, elementId, summary, dependsOn }], assets, notes }` shows the plan in the panel; the result is `{ decision: 'build_all' | 'step' | 'revise', items, comments }` (the user may edit or remove items first). `checkpoint { completedItemIds, nextItemId, summary }` returns `{ decision: 'continue' | 'stop' }`: in step mode it waits for the user, in build-all mode the host answers `continue` at once. Everything else (ids, kinds, data) is checked by the host: unknown kinds, invalid ids, ids in reserved namespaces, duplicates and data that fails `validateJson` come back as `is_error` results with the problems, so the model fixes them instead of the user.

No file system, shell, network, install or export tools. Every tool result is JSON text, bounded (long lists are paged with `cursor`; `read_element` data over 64 kB is truncated with a notice).

**D5. Edits land as one reviewable changeset, applied as one undo step.** A run accumulates *change items* (`create`, `update`, `delete`, `rename`, `asset`), each with a before/after view and the problems `run_checks` found for it; the panel shows them live while the run proceeds and as a review list when it ends, each with an accept checkbox (all accepted by default). **Apply** executes one `ProjectCommand` (`ai.apply-changeset`, label "Apply AI helper changes") that adds namespaces, elements and asset records and writes the asset bytes exactly as `addBundle` does, so Undo reverts everything together; the app then runs its normal validation pass. **Discard** drops the changeset. Items rejected by the user are left out; an accepted item that references a rejected one is marked with a warning, not refused. Items that no longer fit the project (the element was edited by hand meanwhile, a `create` whose id now exists) are shown as conflicts and are not applied. The same mechanism serves a one-line edit in chat mode and a hundred-element build; the helper never changes the project any other way.

**D6. Build mode.** The panel has two modes. *Chat* answers questions and proposes small edits. *Build* is for whole content from one prompt: the system prompt tells the model to call `propose_plan` first, then, after the user's decision, to work through the items in dependency order with batched `create_elements` and `add_starter` calls, to call `run_checks` after every batch and fix what it reports, to call `checkpoint` after each plan item (which pauses only in step mode), and to finish with a summary. A user who writes "go" or clicks "Build all" gets a one-shot run; "Step through" pauses after every item with Continue and Stop; "Revise" sends comments back as the tool result. Build mode defaults to effort `high` (chat `medium`) and a larger turn budget (D7). The model is told what exists (starters such as Custom ore, Custom sword and Custom mob with their parameters; templates per kind; the `msm:mod` singleton that every Fabric mod project needs; the placeholder texture generator) and that textures are placeholders the user replaces. The user's project is never touched until Apply.

**D7. Guard rails, budgets and cost.** Every run has limits the user can see and change in the panel ("Run limits"): `maxToolTurns` (assistant turns that call tools; defaults 24 in chat, 150 in build), `maxOutputTokens` (the sum of `usage.output_tokens` across the run's requests; defaults 100,000 in chat, 600,000 in build) and `taskBudget` (on by default: `output_config.task_budget.total` is `maxOutputTokens` when at least 20,000, so the model paces itself). Reaching a limit ends the run with `done { reason: 'limit' }` and a message offering to continue with a higher limit (a new run on the same conversation). A Stop button cancels at any time. The panel shows the run's usage (input, output, cache read and cache creation tokens, requests) and an approximate cost from the model table in `@msm/ai` (`checkedOn` date next to the prices; the label says "approximate"). Settings hold the defaults per mode, the model, the effort per mode and the fallback switch; limits changed in the panel apply to that run only. Refusal fallback (`fallbacks: 'default'`, Opus and Sonnet only) is **on by default** and shown in Settings as "Allow Anthropic to answer with another Claude model when a request is declined"; a fallback is shown in the transcript as a notice naming both models.

**D8. UI.** A third tab "AI helper" in the right dock (`DockTab` `assistant`) next to Preview and Problems, toggled by View > "AI Helper" (`CmdOrCtrl+Shift+A`), a toolbar button and the palette ("Open AI helper"). The panel: the mode switch, the transcript (assistant text through `Markdown.tsx`, streamed; thinking summaries in a collapsed "Thinking" line; tool calls as one-line entries with a disclosure), the plan view, the changeset review with Apply and Discard, the input box with Send and Stop, "New conversation", the usage line and "Run limits". Without a key the panel shows the privacy notice and a button to Settings. Entry points with context: "Explain this problem" on a Problems row (and the palette command "Explain this problem with the AI helper" for the selected problem) and "Ask about this element" on the element's editor header (palette "Ask the AI helper about this element"); both open the panel in chat mode with a visible context block (the problem's code, message, element id and path; the element's kind and data) that is sent as part of the user message, so the user sees exactly what leaves the machine. Conversations are kept per project in renderer memory and in main for the current app session; they are **not persisted**: transcripts contain project content and would need their own encryption and retention rules, the thinking blocks are bound to the model, and nothing in the workflow needs yesterday's conversation. Persisting is a later option with its own ADR.

**D9. Tests without the network.** `ModelClient` is the seam (like `AutoUpdaterLike`): `@msm/ai` ships `ScriptedModelClient`, which replays a JSON script of assistant turns (text, thinking, `tool_use` blocks matched by order) and records what it was sent. Unit tests cover the loop (parallel tool results in one message, invalid tool input, `max_tokens` and `refusal` before tools, limits, cancel, fallback events, append-only history and thinking blocks passed back, cache breakpoint placement), the tool schemas, the key store (fake `safeStorage`, unavailable encryption), the main service (runs, cancel, the tool round trip over a fake sender), the renderer executor (every tool against a session fixture), the changeset (check, apply as one undo step, undo, per-item accept, conflicts) and the components. A **scenario test** drives a scripted build ("ruby tools mod": ore block and item, storage block, recipes, loot table, the `msm:mod` element, placeholder textures, a mob through `add_starter`) through the real session and executor, applies the changeset and exports the resource pack, the data pack and the Fabric content jar (stub runtime) with zero blocking problems. One Playwright spec `ai-path` launches the app with `MSM_E2E_AI_SCRIPT=<file>` (main then uses the scripted client and reports the key as set) and checks the panel, the plan, the changeset, Apply, Undo and the exports. CI makes no real API calls; the real `createAnthropicModelClient` is covered by a test against a local HTTP stub only if the SDK supports `baseURL` without a key format check (verify at implementation; otherwise the adapter is exercised by hand once per release).

**D10. Docs and release.** User guide page `docs/guide/ai-helper.md` (getting a key, what is sent, modes, build mode walk-through, the changeset review, limits and cost, troubleshooting by error class) in the VitePress sidebar; DESIGN §8 gains "AI helper"; this ADR is accepted with the release. The helper ships as **v0.7.0** (app and `engine-mod` `mod_version` together, as the runtime version test requires) before 1.0; `CHANGELOG.md` gets its section.

**D11. Rejected alternatives.** *A plugin:* plugins have no network, no editors and no commands (ADR 0035), and the helper needs main-process secrets. *The SDK tool runner (`toolRunner`):* its loop runs where the tools run; here the tools run in another process, and the manual loop keeps the renderer round trip, the limits and cancellation explicit. *Applying edits silently with per-edit undo:* ten undo steps for one request is unusable, and the user must see a diff before anything changes. *Running the loop in the renderer:* the key and the SDK would be in the sandboxed renderer, and CSP `connect-src 'self'` would have to open to `api.anthropic.com`. *Direct file writes by the model:* everything in MSM is an element; files are lowering output. *Claude Managed Agents:* the project lives on the user's disk and the tools are the app itself; a hosted sandbox adds nothing. *Persisting conversations:* see D8. *A base URL or proxy setting:* out of scope for v1; a later setting if asked.

## Consequences

- One new package (`@msm/ai`), one new dependency (`@anthropic-ai/sdk`, about 0.4 MB minified in a lazy main chunk), nine invoke channels and one event channel in the `ai` domain, a new `AppSettings.ai` block, the encrypted key file, a third dock tab, a Settings section, a guide page and a 0.7.0 release.
- The app stays fully usable without a key; the helper is off until a key is set, and every change it proposes passes the same validation gate as hand-made content before it is shown and again after Apply.
- Project content (element JSON, ids, problems, template and target data, script typings) is sent to Anthropic when the user sends a message; asset bytes, file paths and the key never are. The guide and the Settings section say so.
- Cost is the user's: the panel shows tokens and an approximate price per run, and limits stop runaway runs.
- B160–B162 of the Phase 7 plan wait for the helper's briefs (B170–B175, AI helper plan, closed with 0.7.0) and the sibling Creator plan (closed with 0.7.0); B160 then builds on the helper's `App.tsx`, `shared/` and `main/` changes.
- The changeset, review and single-undo Apply are shared with the Creator ([ADR 0043](0043-creator-guided-flows.md)), which is the second front end of the same generator layer (starters with parameters).
- Resolves [DESIGN Open Question 14](../DESIGN.md#18-open-questions).

## Status

**Accepted (2026-11-06, shipped in 0.7.0).** Implemented by B170 (`@msm/ai`), B171 (main), B172 (renderer logic), B173 (UI), B174 (scenario tests, e2e `ai-path`), B175 (guide `docs/guide/ai-helper.md`, release).

Findings:

- *SDK.* `@anthropic-ai/sdk` pinned to **1.1.0** (the newest at least two weeks old on 2026-11-05; 1.4.0 has the same beta Messages surface for this use; move up after 2026-11-16). Verified against the installed types: `client.beta.messages.stream(params, { signal })` takes `betas`, `fallbacks: 'default'`, `output_config: { effort, task_budget: { type: 'tokens', total } }`, top-level `cache_control`, `thinking: { type: 'adaptive', display: 'summarized' }` and `eager_input_streaming` per tool; `betas` go in the `anthropic-beta` header. SDK 1.x sends the key as `Authorization: Bearer` and reads `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` unless pinned, so the adapter pins `baseURL`, `authToken: null` and `webhookKey: null`. A local `node:http` SSE stub with a dummy key exercises the real adapter in a unit test.
- *JSON Schema.* `z.toJSONSchema` output needed small edits: no `$schema`, no `propertyNames`, no zod safe-integer bounds, `additionalProperties: false` on objects with properties.
- *Loop and executor.* Whole-turn commits keep the conversation valid after cancel; unparseable eager tool JSON is retried twice. Tool calls of one turn run one at a time in arrival order (B174), so parallel calls see each other's proposals; `add_starter` drops a starter's `pack.mcmeta` and `msm:mod` when the project already has one, and stamps `meta.creator` for Creator flows (B192, ADR 0043 D5). `run_checks` includes an in-memory lowering pass for `lowering.conflict` and `lowering.merge-conflict` (B192).
- *Key store.* The asynchronous `safeStorage` API (the synchronous one is deprecated in Electron 45.2.2); the Linux `basic_text` backend counts as unavailable, so D1's refusal holds there.
- *Size.* `ai-client` chunk 315,407 + 38,959 + 293 bytes minified; `app.asar` 30.0 MB of 32 MB after B174 (see the ROADMAP Milestone Log for the release run); `out/renderer` contains no `api.anthropic.com`.
- *Not done in v1:* the real model has not been exercised by an automated test (scripted client only; a manual run with a real key is the user's check before relying on it); conversations are not persisted; no base URL setting.
