# ADR 0070: Mob bodies, movement modes and ranged attacks

## Context

`msm:entity` makes one kind of mob: a ground-walking `PathfinderMob` (`MsmEntity`) with six goals, attributes, triggers, sounds, a spawn egg, natural spawns and a GeckoLib model ([ADR 0028](0028-entity-definition-format-v1.md), [ADR 0057](0057-project-sound-events-and-mob-sounds.md), [ADR 0061](0061-more-triggers.md)). The coverage audit (L7, backlog B7) lists what is missing: ranged attacks, flying and swimming, taming, breeding and babies, riding, variants, boss bars, more mob kinds and a renderer without GeckoLib. This ADR covers the mob's base class, its movement and its fighting; taming, breeding, riding, variants and boss bars are [ADR 0071](0071-tameable-breedable-rideable-mobs-variants-and-boss-bars.md); the renderer without GeckoLib is [ADR 0072](0072-vanilla-model-renderer.md); flows, templates and library content are [ADR 0073](0073-mob-flows-templates-and-presets.md). The working plan is `docs/PLAN-mob-expansion.md`.

Facts read on 2026-11-14 with `javap` (JDK 25) over the Loom-cached merged jars `minecraft-merged-deobf-26.3.jar` and `minecraft-merged-deobf-26.4-snapshot-7.jar`, the cached Fabric API module jars and this repository (the fact table with every signature is in the plan, F1 to F18):

- **Vanilla behaviour hangs on the class.** Breeding, babies and taming live in `Animal`, `AgeableMob` and `TamableAnimal` (`isFood` and `getBreedOffspring` are abstract; `BreedGoal`, `FollowParentGoal`, `FollowOwnerGoal`, `SitWhenOrderedToGoal`, `OwnerHurtByTargetGoal` and `OwnerHurtTargetGoal` take an `Animal` or `TamableAnimal`). Hostility lives in `Monster` (`implements Enemy`; `isPreventingPlayerRest` stops sleeping nearby, `getSoundSource` is `HOSTILE`, peaceful removal). Java's single inheritance means one `MsmEntity extends PathfinderMob` cannot be all three.
- **Goals with class bounds.** `RangedBowAttackGoal<T extends Monster & RangedAttackMob>` and `RangedCrossbowAttackGoal<T extends Monster & RangedAttackMob & CrossbowAttackMob>` accept only monsters. `RangedAttackGoal(RangedAttackMob, double, int, float)` is the same on both versions, but its five-argument form takes `(int, int)` on 26.3 and `(IntSupplier, IntSupplier)` on 26.4.
- **Projectiles.** `ProjectileUtil.getMobArrow(LivingEntity, ItemStack, float, ItemStack)` makes a mob's arrow; `ProjectileItem.asProjectile(Level, Position, ItemStack, Direction)` plus `shoot` makes the projectile of every vanilla throwable item (`ArrowItem`, `SnowballItem`, `EggItem`, `ExperienceBottleItem`, `FireChargeItem`, `FireworkRocketItem`, `ThrowablePotionItem`, `TridentItem`, `WindChargeItem`; 26.4 adds `IceBallItem`). The runtime's own `MsmThrownItem(Level, LivingEntity, ItemStack)` ([ADR 0056](0056-throwables.md)) already takes any living thrower.
- **Movement controls.** `FlyingMoveControl(Mob, int maxTurn, boolean hoversInPlace)`, `SmoothSwimmingMoveControl(Mob, int, int, float, float, boolean)`, `SmoothSwimmingLookControl(Mob, int)`, `FlyingPathNavigation`, `WaterBoundPathNavigation` and `AmphibiousPathNavigation` `(Mob, Level)`, `WaterAvoidingRandomFlyingGoal(PathfinderMob, double)` and `RandomSwimmingGoal(PathfinderMob, double, int)` are identical on both versions; `Mob.moveControl`, `lookControl` and `navigation` are protected fields and `createNavigation(Level)` is called from the `Mob` constructor. `LivingEntity.travelFlying` (four floats on 26.3, three on 26.4), `checkFallDamage` and `jumpInLiquid` differ between versions; `moveRelative`, `move`, `causeFallDamage(double, float, DamageSource)`, `canBreatheUnderwater` and `getDefaultGravity` do not.
- **Spawn checks.** `Animal.checkAnimalSpawnRules` and `WaterAnimal.checkSurfaceWaterAnimalSpawnRules` are bound to their classes' entity types; `Monster.checkMonsterSpawnRules` takes any `Mob`. `MobCategory` has the same eight constants on both versions.
- **Fabric** `FabricEntityType.Builder.createMob(EntityFactory<T extends Mob>, MobCategory, UnaryOperator<Mob<T>>)` is identical in object-builder 24.1.13 (26.3) and 25.0.8 (26.4).
- **Not goal-driven.** Allays, axolotls, frogs, camels, sniffers, wardens, piglins and villagers run on `Brain` behaviours, not goals; phantoms, ghasts and vexes have their own move controls.

## Decision

- **D1 A `base` field picks the vanilla class.** The entity definition and element gain `base?: "mob" | "animal" | "monster"`. Absent means `mob`: today's `PathfinderMob`, so every existing definition registers and behaves exactly as before. `animal` builds on `TamableAnimal` (taming stays off unless `msm:tameable` is present, ADR 0071), which brings ages, breeding, leads and animal spawn checks; `monster` builds on `Monster`, which brings `Enemy` (iron golems attack it), no sleeping nearby, hostile sounds and removal in peaceful. We chose an explicit field over deriving the class from the components because the class changes vanilla behaviour beyond the components (wander preferences, despawning, golems), and a beginner sees it as the Studio's "Kind of mob" picker. Category and base stay separate fields (a `monster` base in the `creature` category is allowed, with a validator info).
- **D2 Runtime classes.** Three driver classes extend the vanilla bases: `MsmEntity extends PathfinderMob` (kept), `MsmAnimal extends TamableAnimal` and `MsmMonster extends Monster`, all implementing an `MsmMob` interface and delegating every shared behaviour to one `MobDriver` per entity built from the definition (goals, events, sounds, movement, ranged attacks, and the ADR 0071 modules), the same pattern as `BlockBehaviourDriver` ([ADR 0067](0067-block-types-and-states.md) D4). The GeckoLib bridge gets one subclass per base (`MsmGeoEntity`, `MsmGeoAnimal`, `MsmGeoMonster`), each a thin `GeoEntity` that delegates its controllers to one shared `GeoControllers` helper; they are still reached only through `GeckolibEntities` after `isModLoaded("geckolib")`. The registrar's maps become `EntityType<? extends Mob>`. Spawn checks of D6 that vanilla binds to a class are repeated in the runtime (as `any_light_monster` is today). Overrides whose signature changed between versions (`canBeABaby`, `setAgeLocked`, `travelFlying`, `checkFallDamage`, `jumpInLiquid`) are never overridden or called; `canBeABaby` and `setAgeLocked` are left alone, flight avoids fall damage through `causeFallDamage`.
- **D3 Movement modes.** `msm:movement` gains `mode?: "walk" | "fly" | "swim" | "amphibious"` (default `walk`), `flying_speed?: float` (the `flying_speed` attribute, default 0.4 as a bee's; verify at implementation), `hovers?: boolean` (fly: stays in place when idle, as a bee; default true), `breathes_air?: boolean` (swim: needs to surface as a dolphin; default false), `dry_out_ticks?: int @ 20..` (swim without `breathes_air`: health is lost after this many ticks out of water, default 300 as vanilla's water animals; verify at implementation) and `step_height?: float`. `fly`: `FlyingMoveControl` (max turn 20), `FlyingPathNavigation` that can open doors off and float on, no gravity, no fall damage; `wander` becomes `WaterAvoidingRandomFlyingGoal`. `swim`: `SmoothSwimmingMoveControl` and `SmoothSwimmingLookControl` with a dolphin's or fish's numbers (verify at implementation), `WaterBoundPathNavigation`, breathes water, `travel` in water through `moveRelative` and `move` (both versions identical), `wander` becomes `RandomSwimmingGoal` (interval 40), the float goal is not added, and out of water it flops and dries out unless `breathes_air`. `amphibious`: `AmphibiousPathNavigation`, walks on land, swims in water with the walking move control, breathes both, `wander` stays the walking stroll (avoid water false). `swims` keeps its meaning (float goal) for `walk` and `fly`.
- **D4 `msm:ranged_attack` component** (like `msm:attack` for melee):

  ```
  struct RangedAttack {
    projectile: #[id="item"] string,     // minecraft:arrow, any vanilla projectile item (target fact), or a project item with msm:throwable
    damage?: float @ 0..,                 // arrows only: base damage, as setBaseDamage (hit ≈ damage x speed, rounded up); default 2
    speed?: float @ 0.1..5,               // launch speed in blocks per tick; default 1.6 (a skeleton's arrow)
    inaccuracy?: float @ 0..20,           // default 6
    interval_ticks?: int @ 5..,           // cooldown between shots; default 40
    charge_ticks?: int @ 0..200,          // aiming time before a shot (the bow pose); default 20
    range?: float @ 1..64,                // blocks; default 15
    sound?: #[id="sound_event"] string,   // default minecraft:entity.skeleton.shoot
    on_shoot?: string,                    // event after each shot; other = the target
  }
  ```

  Arrows (`minecraft:arrow`, `tipped_arrow`, `spectral_arrow`) go through `ProjectileUtil.getMobArrow` with a weapon stack of `minecraft:bow`, other vanilla projectile items through `ProjectileItem.asProjectile` and `shoot`, and a project item with `msm:throwable` through `MsmThrownItem`, so its damage, gravity and `on_hit_entity`/`on_hit_block` events apply with the mob as thrower. Every mob class implements `RangedAttackMob`. The list of vanilla projectile items is a target fact (D7). A projectile that is neither is a validator error and a runtime load error that drops the component.
- **D5 New goals.** `ranged_attack { speed?, strafe?: boolean }` is the runtime's own `MsmRangedAttackGoal` (approach until within `range` and in sight, set `aggressive` while charging so renderers can pose, shoot, wait `interval_ticks`; with `strafe` it circles as a skeleton), because vanilla's bow and crossbow goals accept only monsters and the plain ranged goal's interval form differs between versions; `ranged_attack` without `msm:ranged_attack` adds nothing (a validator warning, as `melee_attack` without `msm:attack`); its targets come from a `melee_attack`-style `targets`, `must_see` and `retaliate` on the goal. `tempt { items, speed?, scared?: boolean }` (`TemptGoal`), `panic { speed? }` (`PanicGoal`), `leap_at_target { height? }` (`LeapAtTargetGoal`). Goals of ADR 0071 (follow owner, sit, defend, breed, follow parent) are added by their components, not listed. Unknown goal types are still dropped with an error by older runtimes.
- **D6 Spawn rules and kinds.** `spawn.rule` gains `animal` (the animal check: grass-like ground and light, repeated by the runtime for any base) and `water_animal` (the surface water check). Categories are unchanged; the Studio's "Kind of mob" picker sets base, category, placement, rule and movement mode together (creature, farm animal, pet, monster, flying creature, water creature, fish, ambient), and every value stays editable.
- **D7 Versions.** All shared code (D2's rule keeps it so); no new runtime seam is expected. Plugin API 1.11.0 (additive) adds `TargetFacts.entities?: EntityFacts { projectileItems: readonly string[]; saddleTag: string }` (ADR 0071 D4 uses the second); both targets list their projectile item ids (26.4 adds `minecraft:ice_ball`; verify the id at implementation).
- **D8 Java eject (26.3 generator).** Generated entity classes extend the same vanilla base, set the same controls and navigation, copy `MsmRangedAttackGoal` as a template (like `FollowTypesGoal`), and implement `RangedAttackMob`.
- **D9 Not in this batch (limits).** Brain-driven mobs (allay item fetching, axolotl play dead, frog tongue, camel dash, piglin bartering); phantom swoops, ghast and vex flight and bat fluttering (each its own move control); crossbow charging poses and held weapons drawn in the mob's hand (needs an `ArmedModel` bone mapping, follow-up); mobs switching between melee and ranged by distance (both goals may be listed; priorities decide); fish buckets (`Bucketable` with a bucket item per mob and its client model); custom projectile entities with their own models (ADR 0056 follow-up).

## Consequences

- Format 1 grows additively: one top-level field, movement fields, one component, four goal types and two spawn rules. The corpus (prefix `entity-mx-`), the Codecs, the plugin, the generator and the app move together; a definition without the new fields registers and behaves as before.
- The runtime gains two driver classes, two GeckoLib subclasses and a `MobDriver` with one module per feature, so later features add a module rather than editing every class.
- Plugin API 1.11.0 is additive; built-in plugins keep `^1.0.0`.
- A project using any new field needs the runtime release that ships this.

## Status

Proposed (2026-11-14). Defaults the user may veto: the field name `base` and its values (D1); absent `base` meaning `mob` rather than derived from the components (D1); the movement defaults (D3); the ranged defaults copying a skeleton (D4); the component name `msm:ranged_attack` (D4).
