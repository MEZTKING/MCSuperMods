# ADR 0031: Rhino 1.9.2 in `msm_runtime` and TypeScript-to-ES5 script transpilation

## Context

Tier 1 scripting ([Scripting and Escape Hatches](../DESIGN.md#12-scripting-and-escape-hatches), [ADR 0003](0003-rhino-for-scripting.md)) was designed as "TypeScript in the app, transpiled by esbuild to the ES2015 subset Rhino's ES6 mode handles, run in game by Rhino embedded in `msm_runtime`". Open Question 2 asked whether Rhino's coverage is enough. Phase 6 verified it (2026-11-05, in the session container, see `docs/PHASE6-PLAN.md`):

- Rhino's current release is **1.9.2** (Maven Central `org.mozilla:rhino:1.9.2`, 2026-10-27, MPL 2.0, Java 17 or newer, the plain runtime jar of 1.68 MB with no dependencies; `rhino-tools`, `rhino-engine` and `rhino-xml` are separate artefacts we do not need). Its default language level is `Context.VERSION_ES6` (200); `VERSION_ECMASCRIPT` (250) exists.
- Rhino 1.9.2 runs `let`/`const`, arrow functions, template literals, default parameters, object destructuring, array destructuring without rest, array spread, generators, `Promise` (with `Context.processMicrotasks()`), `Symbol`, `Map`/`Set`/`WeakMap`, `Object.entries`, `Array.prototype.includes`, `String.prototype.padStart`, regular expressions with named groups, optional chaining, `??` and `**`. It does **not** parse `class`, `for...of`, spread in calls, array rest patterns or `async`/`await`, under either language version.
- esbuild 0.28.2 (current on npm) keeps exactly those constructs at `target: 'es2015'`, and refuses to lower them to ES5 ("Transforming class syntax ... is not supported yet", likewise for-of, destructuring, generators, async functions, rest arguments). esbuild cannot bridge the gap.
- TypeScript 6.0.3 (already in the repository) lowers everything to ES5 with `transpileModule` (`target: ES5`, `module: CommonJS`, `downlevelIteration: true`, `ignoreDeprecations: "6.0"`, which silences the deprecation of the ES5 target that TypeScript 7 will remove). A sample using classes with private fields and `super`, generators, async/await, destructuring with rest, call and array spread, for-of over a `Map`, named regex groups and `Object.entries` ran in Rhino 1.9.2 unchanged in behaviour, with a `ClassShutter` denying every Java class, `initSafeStandardObjects` (no `java`, `Packages` or `JavaAdapter` globals), interpreted mode and an instruction observer that aborted an endless loop after the configured 500 ms. Transpilation is deterministic and takes about 100 ms for a 50-line script; a full semantic check with a virtual compiler host takes about 300 ms.

## Decision

**D1. Engine: Rhino 1.9.2, nested.** `msm_runtime` depends on `org.mozilla:rhino:1.9.2` through Loom's `include` configuration (jar-in-jar; Loom generates a `fabric.mod.json` for a plain library, verify in the spike B130) plus `implementation`. The runtime jar neither shades nor modifies Rhino. The jar's MPL 2.0 notice is kept: the runtime jar carries `META-INF/licenses/rhino-LICENSE.txt` (copied from the Rhino source tree's `LICENSE.txt`, MPL 2.0 text) and the README credits Rhino with a link to its repository. MPL 2.0 is file-level copyleft; nesting an unmodified upstream jar in an MIT project is permitted, and we distribute no modified Rhino files.

**D2. Transpiler: TypeScript, not esbuild.** The app transpiles each `msm:script` element with TypeScript's `transpileModule` to ES5 CommonJS in the Electron main process (a lazy chunk; `typescript` is bundled into main, about 3.6 MB minified). esbuild is not used. This supersedes the "esbuild to ES2015" part of ADR 0003 and DESIGN §12; the Rhino decision of ADR 0003 stands. The language level in game is `VERSION_ES6`, so the ES2015 built-ins TypeScript's ES5 output relies on (`Promise`, `Map`, `Symbol`, `WeakMap`) exist. TypeScript is pinned to a 6.x release for the transpiler; a move to TypeScript 7 (which drops the ES5 target) needs a superseding ADR, as does Rhino 2.0 once it parses classes and `for...of` natively.

**D3. Sandbox.** Every script runs in a scope from `Context.initSafeStandardObjects()` with a `ClassShutter` that returns `false` for every class name, so no Java class, package, reflection or `JavaAdapter` is reachable; the only host objects are the `msm` API ([ADR 0032](0032-script-api-v1-and-typings.md)) and the CommonJS `require`, `module` and `exports` the transpiled output needs (`require` resolves `msm:runtime` and relative ids among the same mod's scripts, nothing else). The `ContextFactory` subclass `MsmContextFactory` sets interpreted mode (the instruction observer works only there), `setMaximumInterpreterStackDepth(1000)`, `setInstructionObserverThreshold(10_000)` and aborts a script when one top-level call has run for more than **2000 ms** of wall-clock time (`observeInstructionCount` throws `ScriptTimeout`, an `Error` subclass the host catches and logs, with the script id and the handler). Scripts run on the server thread only; there is no file, network or thread access. Rhino's compiled mode is never used.

**D4. Lifecycle and errors.** Scripts live in content jars at `msm/<namespace>/script/<path>.js` (ES5 CommonJS, written by the content-jar exporter from the project's `.ts` elements). `DefinitionScanner` ignores them (it reads `.json` only), so older runtimes never see them; `ScriptScanner` reads them from every mod container. All scripts are loaded on `ServerLifecycleEvents.SERVER_STARTING` in mod id then path order into one `ScriptHost` per server, and reloaded (fresh scope, handlers cleared) on `ServerLifecycleEvents.END_DATA_PACK_RELOAD`, so `/reload` picks up edited scripts in a hand-made install; the host is discarded on `SERVER_STOPPED`. A script that throws while loading is logged once (`[msm_runtime] script <id>: <message> (<file>#<line>)`) and contributes no handlers; the other scripts load. A handler that throws is logged with the same format, rate-limited to one line per handler per 100 ticks; the game continues. Microtasks (`Promise` callbacks) run after every handler call and at the end of every server tick. The runtime logs `[msm_runtime] loaded S script(s); E error(s)` after loading; CI's server tool checks it.

**D5. Validation gate.** `msm:script` lowers to a `msm`-layer `OutputFile` with `language: 'typescript'` holding the TypeScript source; the content-jar exporter asks its host (`createFabricContentJarExporter({ transpileScript })`) to transpile each one and writes the `.js` instead. The export gate's `validateText` for `typescript` reports TypeScript syntax errors as errors (they block) and semantic errors from a full check against the generated typings and a curated `lib` set as warnings (they pass, since Rhino is duck-typed), with ranges mapped to the script's lines. The same checker feeds the Problems panel; the Monaco TypeScript worker gives the editor completions, hover and squiggles from the same typings.

**D6. Size budgets.** The renderer gains the Monaco TypeScript worker as a lazy chunk (about 7 MB minified), so `tools/check-size`'s renderer budget rises from 8 MB to 16 MB with the lazy-chunk justification; `app.asar` keeps its 25 MB budget (expected about 17 MB after `typescript` joins main).

## Consequences

- Scripts written in idiomatic TypeScript (classes, async/await, for-of, spread) run in game; the ES5 output is readable in the exported jar.
- The runtime jar grows by Rhino's 1.68 MB; the installer stays far below its budget.
- `typescript` becomes a runtime dependency of the app's main process (bundled); the Monaco TypeScript worker is loaded only when a script is edited.
- GraalJS stays the documented fallback and is not needed; Open Question 2 is closed by this ADR.
- Script errors never crash a server; a runaway script costs at most two seconds of one tick before it is aborted.

## Status

Proposed (2026-11-05). Findings of the spike (B130) are appended here before Wave 1; accepted at Phase 6 close.

### Spike findings (B130, 2026-11-05)

Checked in `engine-mod/` (`scripting/`, `MsmScriptSpikeGameTest`, nine GameTests) and on a production dedicated server (`tools/run-fabric-server` with a hand-made content jar holding one script and the built runtime as `--extra`).

- **D1 holds: Loom `include` nests Rhino as a plain library** in the non-remapping Loom 1.19.3. `implementation` plus `include` of `org.mozilla:rhino:1.9.2` put `META-INF/jars/rhino-1.9.2.jar` (1,677,320 bytes, the upstream jar plus a Loom-generated `fabric.mod.json`) into `msm_runtime-0.5.0.jar`; the runtime's `fabric.mod.json` gains only `"jars": [{"file": "META-INF/jars/rhino-1.9.2.jar"}]`, its `depends` are unchanged, and the runtime jar holds no `org/mozilla` classes of its own (1.80 MB in all). The nested metadata is `{"schemaVersion": 1, "id": "org_mozilla_rhino", "version": "1.9.2", "name": "rhino", "custom": {"fabric-loom:generated": true}}`; the production server's mod list shows `msm_runtime 0.5.0 \-- org_mozilla_rhino 1.9.2`. No `files(...)` or Shadow fallback is needed.
- **ServiceLoader from the nested jar works.** A regular expression with named groups (which needs Rhino's `RegExpLoader` service) and a `Promise` callback run on the production server with Rhino only nested, and in the GameTest server.
- **Sandbox as decided.** `typeof java`, `Packages` and `JavaAdapter` are `undefined`; an endless loop (also inside `try`/`catch`) is stopped after 2002 to 2005 ms by `ScriptTimeout`, which a script cannot catch, and the next test runs; a syntax error is logged once at load as `[msm_runtime] script msm_spike:broken: syntax error (msm/msm_spike/script/broken.js#5)` and the other scripts load; a throwing handler is logged once (`... block.interact handler: TypeError: Cannot call method "boom" of undefined (msm/msm_spike/script/glow.js#35)`), rate-limited, and the server keeps running.
- **Lifecycle.** `SERVER_STARTING` is early enough on the GameTest server and the dedicated server: scripts load before the first tick and before the GameTests run; `[msm_runtime] loaded 3 script(s); 1 error(s)` (S counts every script file found, E the scan and load errors). The registration lines are unchanged byte for byte (scripts are `.js`, which `DefinitionScanner` does not count). `msm.schedule(5, fn)` called during server tick T runs at the end of tick T + 5 (`END_SERVER_TICK`).
- **Cancelling an interaction.** `UseBlockCallback` returning `InteractionResult.FAIL` makes `ServerPlayerGameMode.useItemOn` return `Fail` without running the block's own use (the block's `msm:on_interact` did not fire). On the client, `Minecraft.startUseItem` stops its hand loop (and skips `useItem`) on `Fail` or `Success`, so `FAIL` is the result that stops both hands, but only the client's own result decides that: a server-only handler cannot stop the client from sending an off-hand or `useItem` packet when its prediction was `PASS`. B133 should therefore ignore the off hand for a player whose main-hand interaction a script cancelled in the same tick (and fire `block.interact` once per click). `GameTestHelper.useBlock` calls the block directly and bypasses `UseBlockCallback`; GameTests drive `ServerPlayerGameMode.useItemOn` and `destroyBlock` instead. `PlayerBlockBreakEvents.BEFORE` returning `false` makes `destroyBlock` return `false` and keeps the block.
- **Per-call cost: `server.tick` stays in API v1.** 10,000 calls of a trivial handler (`n = n + e.tick`, a fresh event object, the budget bookkeeping and `processMicrotasks()` per call, interpreted mode) after 20,000 warm-up calls cost a mean of 0.9 to 4.3 microseconds per call with one entered context, and 1.2 to 11 microseconds when a Rhino context is entered per call (six runs), far below the plan's 0.2 ms threshold.
- **Not covered by the spike** (B133): reload on `END_DATA_PACK_RELOAD`, relative `require` between scripts, the rest of API v1. Microtasks queued in a Rhino context are lost when the context exits, so the host runs them before leaving it (after each handler call); "at the end of every server tick" only matters if B133 keeps one context entered across a tick.
