# ADR 0074: Containers and block entities

## Context

`msm:block` has no block entity: it keeps no state beyond its block state properties, holds no items and opens no screen. The coverage audit (backlog B8; rows "Block entities", "Menus and screens") calls this the largest gap for "machines", and suggests starting with vanilla menus only, because a screen of our own needs client code. This ADR covers blocks that hold items (storage, a hopper-sized box, a 3 by 3 box, a holder with no screen), their saved state, menus, hopper and comparator interaction and drops. Machines that process items over time are [ADR 0075](0075-machines-and-machine-recipes.md); the Studio, Creator flows, templates, the Script API and the AI helper are [ADR 0076](0076-container-and-machine-flows-studio-and-script-api.md). The working plan (B309–B328) was deleted at close; its fact table (F1–F22) and limits (C1–C18) are kept under Findings below.

Facts read on 2026-11-14 with `javap` (JDK 25) over the Loom-cached merged jars `minecraft-merged-deobf-26.3.jar` and `minecraft-merged-deobf-26.4-snapshot-7.jar` and the Fabric API module jars of 0.165.2+26.3 and 0.165.4+26.4 (the fact table under Findings lists every signature):

- **Block entity types.** `BlockEntityType(BlockEntitySupplier, Set<Block>)` is a public constructor on both versions. It keeps the given set without copying it and creates an intrusive registry holder, so every type built must be registered before the registries freeze. A block has a block entity only when its class implements `EntityBlock` (`BlockStateBase.hasBlockEntity` is an `instanceof` check).
- **Vanilla does most of the work for a `Container` block entity.** `BaseContainerBlockEntity` (items, custom name, `lock`, the `container` item component through `applyImplicitComponents`/`collectImplicitComponents`, `createMenu`) and `RandomizableContainerBlockEntity` (loot tables with seeds) are identical on both versions; `BlockEntity.preRemoveSideEffects` drops the contents of any `Container` when the block goes (`Containers.dropContents`); hoppers reach any `Container` or `WorldlyContainer` block entity through `HopperBlockEntity.getContainerAt`; comparators read `AbstractContainerMenu.getRedstoneSignalFromBlockEntity` (the barrel's rule); `ContainerOpenersCounter` drives a barrel's `open` property and sounds.
- **Vanilla menus need no client code.** `ChestMenu(MenuType, int, Inventory, Container, int rows)` with `MenuType.GENERIC_9x1` to `GENERIC_9x6`, `HopperMenu(int, Inventory, Container)` (5 slots), `DispenserMenu(int, Inventory, Container)` (9 slots) and `ShulkerBoxMenu(int, Inventory, Container)` (27 slots, its `ShulkerBoxSlot` refuses items whose `canFitInsideContainerItems()` is false) are public and identical on both versions. The client opens the vanilla screen for a vanilla menu type, so the runtime adds no client class, no menu type and no network payload.
- **A menu of our own would need client code and seams.** `Slot`'s constructor gains a `Slot.Section` argument on 26.4; `AbstractContainerScreen` changes its drawing methods and fields; `MenuScreens.register` and `BlockEntityRenderers.register` take a `Registry` on 26.4 (through Fabric's transitive access wideners on both). None of it can be drawn or clicked in CI (audit L16).
- **Menu data is 16-bit.** `ClientboundContainerSetDataPacket` writes each `ContainerData` value as a short on both versions.

## Decision

- **D1 A component, not a block type.** `msm:block` gains the component `msm:container`. We chose a component over a new `type` because a container is a behaviour that combines with the facing types (a barrel is `directional`, a furnace `horizontal`): it is allowed on the types `block`, `pillar`, `horizontal` and `directional` (the `MsmBlock` family, as `msm:shape` and `msm:redstone` are, [ADR 0067](0067-block-types-and-states.md) D3) and on no other type; elsewhere it is a validator error (`blocks-items.component-not-for-type`) and a runtime load error that drops it while the block still registers.

  ```
  struct Container {
    layout?: "chest" | "hopper" | "dispenser" | "none",  // default "chest"
    rows?: int @ 1..6,                 // chest only; default 3 (27 slots, a chest's)
    size?: int @ 1..9,                 // none only: the number of slots; default 1
    keep_contents?: boolean,           // default false; true needs layout chest with 3 rows (D6)
    hoppers?: boolean,                 // default true: hoppers, droppers and pipes may insert and extract
    comparator?: boolean,              // default true: comparators read the contents (the barrel's formula)
    open_sound?: #[id="sound_event"] string,   // default the target's container sounds (a barrel's)
    close_sound?: #[id="sound_event"] string,
    on_open?: string,                  // event; self and other = the player
    on_close?: string,
  }
  ```

  Layouts map to vanilla menus: `chest` to `ChestMenu` with `rows` rows (`GENERIC_9xN`), `hopper` to `HopperMenu`, `dispenser` to `DispenserMenu`, and `chest` with `keep_contents` to `ShulkerBoxMenu`. `none` opens no screen: the block is a holder of `size` slots that hoppers, comparators, commands and scripts reach; using the block with an item puts as much of the held stack as fits into the first slot that takes it, and using it with an empty hand takes the last filled slot out (a pedestal; the item is not drawn on the block, limit C9). `msm:on_interact` still fires after the menu opens or the holder is used, as ADR 0067 D3 orders it.
- **D2 Runtime classes.** `registry/container/MsmContainerBlock extends MsmBlock implements EntityBlock` (so `MsmBlock` gains a protected constructor; the shapes, facing, redstone and events stay in `MsmBlock` and `BlockBehaviourDriver`), and `MsmStorageBlockEntity extends RandomizableContainerBlockEntity implements WorldlyContainer`, so loot tables (`LootTable` and `LootTableSeed`, the `container_loot` component), custom names, `lock`, the `container` component and `/data`, `/item` and `/loot ... insert` work as on a chest. The registrar registers one `BlockEntityType` per container block, with the block's own id, right after the block (a type id already registered is a load error that registers the block without its container). Items are saved under `Items` in vanilla's `ContainerHelper` shape.
- **D3 State and sounds.** A container block has vanilla's `open` property (`BlockStateProperties.OPEN`), set while a player has it open through `ContainerOpenersCounter` (the barrel's rule, with its scheduled recheck), and plays `open_sound` and `close_sound`; lowering writes `open=true` variants that use the open model or texture when one is given and the closed one otherwise. The property is chosen through `MsmBlock`'s thread-local set-up, like `powered` and the facing properties.
- **D4 Hoppers and comparators.** Every face reaches every slot when `hoppers` is true; when false, `getSlotsForFace` is empty, so vanilla hoppers and Fabric item transfer leave the block alone (commands and scripts still work). `comparator: true` gives `hasAnalogOutputSignal` and the barrel's `getRedstoneSignalFromBlockEntity`.
- **D5 Breaking.** The contents drop when the block is broken, as vanilla's `BlockEntity.preRemoveSideEffects` does for every `Container`; the block itself drops through its loot table as today.
- **D6 Keeping the contents (a shulker-box crate).** `keep_contents: true` needs `layout: chest` and `rows: 3` (a validator error otherwise, and a runtime load error that turns the option off), because only the vanilla shulker box menu refuses container items in its slots and a slot of our own would need a version seam (F7 under Findings). The block entity then skips dropping its contents; the block item is an `MsmContainerBlockItem` whose `canFitInsideContainerItems()` is false; lowering's loot preset copies `minecraft:custom_name`, `minecraft:container`, `minecraft:lock` and `minecraft:container_loot` from the block entity (vanilla's shulker box loot; the fourth component added at implementation, see Findings); breaking it in creative with contents drops the item, as a shulker box does. Hoppers refuse items that cannot fit inside container items too.
- **D7 Versions.** All runtime code is shared: every class and member used is identical on both versions (the fact table under Findings). The runtime never constructs a plain `Slot`, never calls the four-argument `Block.getDrops` (26.3 only) and never overrides `spawnAfterBreak` (its signature differs). Plugin API 1.12.0 (additive) adds `BlockFacts.containerSounds?: { open: string; close: string }` (both targets: `minecraft:block.barrel.open` and `minecraft:block.barrel.close`, checked against the vendored sound list) and `BlockFacts.machineRecipeTypes?` ([ADR 0075](0075-machines-and-machine-recipes.md) D7).
- **D8 Lowering and validators.** `@msm/plugin-blocks-items` writes the component into the runtime definition, the `open` variants of the blockstate, the open model when the element names one (the model slot `open` in `models`, which this ADR allows on `block` too, or for `horizontal` and `directional` blocks with `textures` the texture slot `front_open`, from which lowering writes `<id>_open`), and the `keep_contents` loot preset. Validators (codes `blocks-items.*`): `container-layout-fields` (`rows` outside `chest`, `size` outside `none`), `keep-contents-layout`, `container-sound-unknown`, `container-event-unknown`, and the existing `component-not-for-type`.
- **D9 Java eject (26.3 generator).** Generated `block/<Name>Block` classes implement `EntityBlock` for containers, with one generated `block/<Name>BlockEntity` each over the same vanilla classes and `ModBlockEntities.java` registering the types after the blocks. The generator copies the runtime's holder interaction and keep-contents rules as templates.
- **D10 Not in this batch (limits).** A screen or GUI texture of our own (needs a client menu screen and the seams of the Context; deferred to backlog B15); drawing the held item on a holder or animating a lid (a `BlockEntityRenderer`, client code); double chests (a `ChestType` property and the chest renderer); per-player storage like an ender chest; containers on family types (slabs, doors); fluids and energy. Each is listed in the limits under Findings.

## Consequences

- Format 1 grows additively: one component on `msm:block`, two texture slots. The corpus (prefix `container-`), the Codecs (`BlockComponents` grows from 12 to 14 fields, two below the `RecordCodecBuilder` limit of 16), the plugin, the generator and the app move together. A block without the component registers exactly as before.
- The runtime registers its first block entity types; a content jar that adds a container block changes the block entity type registry, which Fabric's registry sync checks between client and server like the block registry.
- Everything a player sees is a vanilla screen with vanilla textures and the block's own name, on both versions, with no client code; the in-game check confirms the screens (CI cannot open them).
- Vanilla pack safety ([ADR 0066](0066-vanilla-pack-safety.md)) needs no new rule for containers: their blocks and items are mod-only ids already, so the keep-contents loot table and any recipe naming the block are left out of vanilla data packs.

## Findings

Recorded at close (2026-11-14) from B309–B327 (commits 90a3d1e to 493df62); the facts and limits of the deleted plan follow as tables.

- **No seam and no Mixin.** Every member the batch uses is the same on both versions; the members of F7, F17 and F18 stay untouched. `MsmBlock`'s constructor is protected and takes `MsmBlock.Setup(boolean tracksPower, BlockType type, boolean open, boolean lit)` (`Setup.of(BlockDefinition)`); `MsmBlock.create` builds an `MsmContainerBlock` when `BlockEntityHooks.wantsBlockEntity(def)` says so. `BlockEntityHooks.afterBlockRegistered(RawDefinition, BlockDefinition, Block, List<String> errors)` runs after the block and before its item, so `BlockEntityHooks.blockItem(Block, Item.Properties)` can still choose `MsmContainerBlockItem` for every type but doors. The registrar logs `[msm_runtime] registered N block entity type(s) and M machine recipe type(s)` after the block loop.
- **`open` on every container.** Every layout, `none` included, has the `open` property; on the `block` type the variant keys are `open=false` and `open=true` with no `facing`. Containers do not tick: the opener recheck is a scheduled tick, as the barrel's. The GameTests check that a container still rotates and mirrors.
- **Format.** Layout fields go through a dispatcher (`msm:container_layout[[layout]]`), so `rows` outside `chest`, `size` outside `none` and `keep_contents` on `hopper` are schema unknown-field errors; the validator `container-layout-fields` is a second check. `BlockComponents.container()` is the 13th of 16 fields (C18 confirmed). The corpus has 24 `container-` cases, decoded by `ConformanceCorpusTest`.
- **Fabric item transfer (F19, C17) verified.** Pipes of other mods reach MSM containers through the hopper faces.
- **Holder rules** (D1, copied by the eject). Put-in goes to the first slot that takes any of the held item, up to `min(container max, item max)` (`ItemStack.consume`); take-out takes the whole last filled slot (`Inventory.add`, else `Containers.dropItemStack` at the player, because 26.3's `LivingEntity.drop` takes a `Prediction`); `on_open` fires on each holder use; an item that fits nowhere returns `TRY_WITH_EMPTY_HAND`. Open and close sounds play at the block centre, volume 0.5, pitch 0.9 to 1.0; an unknown sound falls back to the barrel's in the runtime and in the eject.
- **Keep contents** (D6 changed). The loot preset copies four components, not three: vanilla's shulker box also copies `minecraft:container_loot` (the same on 26.3 and 26.4), so `KEEP_CONTENTS_COMPONENTS` lists `minecraft:custom_name`, `minecraft:container`, `minecraft:lock` and `minecraft:container_loot`. `HopperBlockEntity.addItem` already refuses container items into a keep-contents crate; creative break of a filled crate drops the full block item.
- **Loot tables.** `/data merge block ... {LootTable:"..."}` fills a container on first open (GameTest and parity). 26.x loot entries take `modifier`, not `functions`; the offline mcfunction checker rejects block states on mod blocks in `setblock`.
- **Vanilla pack safety** (ADR 0066) needed no rule change: the generic scan in `vanilla-packs/mod-only.ts` reads `type` (only `recipes`, `recipe`, `recipe_id` and `function` are skipped), and container and machine ids are already mod-only block ids. Keep-contents loot tables, machine recipes, crafting recipes for container blocks and the blocks' loot tables are left out with `export.mod-only-reference`. A future field naming a project data file must not use a key the scan skips. F22 was confirmed, so ADR 0075 D10 is required.
- **Validators** (D8): `container-layout-fields`, `keep-contents-layout` and `container-event-unknown` are errors, `container-sound-unknown` a warning (project sound keys accepted as in ADR 0057); with the machine codes of ADR 0075 they make the 12 `CONTAINER_PROBLEM_CODES`. Generated models are `<id>_open` (and `<id>_open_vertical` for directional blocks); blockstates double every variant with `open=`.
- **Eject** (D9). The 26.3 generator writes `ModBlockEntities.java` after `ModBlocks`, shared `block/` classes (`ContainerSpec`, `BlockEvents`, `StorageBlockEntity`, `ContainerMenus`, `ContainerOpeners`, `HolderInteraction`, `ContainerBlockItem`) and per block `<Name>Block.java` and `<Name>BlockEntity.java` (a clash with a shared class name numbers the block, such as `StorageBlock2`). The copied classes are compared line by line with the runtime in the target tests. Generation is stricter than the runtime: a container on a family type, layout fields outside their layout, out-of-range values, unknown fields and undeclared events fail it. Ejected ids equal block ids and the saved data is the same.
- **Counts.** `MsmContainerGameTest` has 19 GameTests; the sample machines fixture logs `registered 9 block entity type(s) and 3 machine recipe type(s)` and passes 19 parity tests on the 26.3 content jar, the 26.3 ejected jar and the 26.4 content jar (ADR 0076 Findings).

### Limits

The hard limits of the batch (C1–C18), referred to by ADRs 0075 and 0076, the coverage audit and the guide:

| # | Limit | Why | What users see | Mitigation in this batch |
|---|---|---|---|---|
| C1 | **Custom recipe types need code registration.** | `RecipeType` and `RecipeSerializer` are frozen registries (F11). | Machine recipes work only with the Fabric mod jar; a vanilla data pack cannot carry them. | Left out of vanilla packs (ADR 0066); one type per machine registered at start-up. |
| C2 | **Machines and containers are fixed when the game starts.** | Registry freeze (audit L1). | Adding a machine, changing its layout or recipe types needs a restart; recipes themselves reload with `/reload`. | Documented. |
| C3 | **Only vanilla screens.** | A screen of our own is client code with version seams (F7, F18) that CI cannot check (L16). | Chest, hopper, dispenser, shulker box and furnace screens with vanilla textures; no custom layout, background or progress bar; the title is the block's name or an anvil name. | Deferred to backlog B15; vanilla menu types need no client code at all. |
| C4 | **Three slots per machine.** | The furnace menu is the only vanilla screen with progress (F5, F6). | One input, one fuel, one output; no byproducts, several inputs or outputs. | `count` per recipe; deferred with C3. |
| C5 | **Menu data is 16-bit.** | `ClientboundContainerSetDataPacket` sends shorts (F8). | A time or burn duration above 32767 ticks would show a wrong arrow or flame. | Times capped at 32767 in the format; fuel above it shows wrong (as in vanilla). |
| C6 | **Shrinking a container loses items.** | `ContainerHelper` loads only slots that exist. | Lowering `rows` or `size` after use deletes the items in removed slots when the chunk loads. | Guide warning; a validator cannot know the old size. |
| C7 | **Removing `msm:container` or `msm:machine` from a used block** | The saved block entity no longer matches its block. | The contents are dropped by the game on load (logged). | Guide warning. |
| C8 | **Block entity type ids equal the block id.** | One type per block (F1). | A clash with another mod's block entity type id skips the container (one load error). | Load error; ids are namespaced. |
| C9 | **Nothing is drawn by a block entity.** | A `BlockEntityRenderer` is client code with a 26.4 seam (F18). | A holder does not show its item; no chest lid animation; only `open` and `lit` block states change the look. | `open` and `lit` models; deferred to B15. |
| C10 | **The client predicts with vanilla furnace rules.** | The client builds a vanilla `FurnaceMenu`; only the server menu is ours (ADR 0075 D4). | Shift-click and fuel placement may flicker before the server corrects them. | Server-side `canSmelt`/`isFuel` overrides; in-game check. |
