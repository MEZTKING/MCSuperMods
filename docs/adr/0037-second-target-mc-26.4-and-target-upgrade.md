# ADR 0037: Second target `mc-26.4` (snapshot now, release when it lands) and the project target upgrade

## Context

The ROADMAP names the second target as "26.4 or whatever is current"; DESIGN §9 states the support policy as the current release and the previous one. Checked on 2026-11-05 against live sources:

- `piston-meta.mojang.com` version manifest: latest release **26.3** (2026-09-15), latest snapshot **26.4-snapshot-7** (2026-11-03; snapshots weekly since 2026-09-22); 26.2 was released 2026-06-16. Three releases a year puts the 26.4 release around mid-December 2026 (an expectation, not a fact).
- `misode/mcmeta` tags exist for `26.4-snapshot-7-summary` (`version.json`: data version 5127, data pack format 126.0, resource pack format 102.0) and for `26.2-summary` (4903, 107.1, 88.0); 26.3 is 5023, 121.0, 97.1.
- Registry diff 26.3 → 26.4-snapshot-7 (mcmeta `registries/data.min.json`): 190 → 192 registries; removed `rule_test`, added `rule_test_type`, `block_sound_set`, `tag/block_sound_set`; `fluid` loses `flowing_water` and `flowing_lava`; `worldgen/feature_type` loses `large_dripstone` and gains `crevasse`, `large_speleothem`; `worldgen/density_function_type` loses `interpolated` and gains `domain_warp`, `upscale`; `particle_type` loses `item_snowball` and gains `freezing`; additions only elsewhere (25 blocks, 28 items, biome `ice_caves`, entities `frostbite`, `ice_ball`, effect `freezing`, environment attribute `visual/has_sky_occluder`, `block_predicate_type` `below_heightmap`, jukebox song `flurry`). The 26.3 data formats (flat feature configs, biome attributes, loot `condition`/`modifier`) are unchanged.
- Registry diff 26.2 → 26.3 is a format change: `worldgen/configured_feature` and `configured_carver` renamed, `worldgen/block_state_provider_type`, `material_condition`, `material_rule` and `loot_condition_type` members replaced, `environment_attribute` `gameplay/natural_mob_spawns` and `attribute_type` `mob_spawn_settings` new, `predicate` registry new. Every lowering function, template, starter and example would need a second shape for 26.2.
- Fabric: Loader 0.20.1 is stable and listed for `26.4-snapshot-7` on `meta.fabricmc.net`; Fabric API for 26.4 runs `0.162.1+26.4` … **`0.165.4+26.4`** (its POM names `fabric-gametest-api-v1` 4.0.44, `fabric-events-interaction-v0` 5.3.15); Loom 1.19.3 is the latest release (1.20.0-alpha.4 pre-release); the Fabric example mod has no `26.4` branch and its `26.3` branch uses `loom_version=1.19-SNAPSHOT`.
- GeckoLib on Modrinth (Fabric): 5.5.7 for 26.3 only; nothing for 26.4 snapshots; 5.5.5 for 26.2.
- vanilla-mcdoc: the `generated` branch's `symbols.json` is at ref `1a674539af7150444db0e2fa8fc46318f91ed86b`; the 26.3 target's vendored export (`0ca060a4…`, 2026-11-04) already carries 46 `26.4` gates, so one tree describes both versions; `compareGameVersions('26.4-snapshot-7', '26.4')` is `1`, so `since="26.4"` gates admit the snapshot and `until="26.4"` gates exclude it.
- A target's vendored data is about 5.4 MB (mcdoc symbols 3.5 MB, mcmeta 1.9 MB), bundled into `out/main/vendor/` and the asar, which is 23.9 MB of its 25 MB budget at Phase 6 close (the TypeScript transpiler in main took it from 13 MB).

## Decision

**D1. The second target is `mc-26.4`, tracking the 26.4 line.** Until Mojang releases 26.4 the package describes the newest snapshot (`mcVersion: '26.4-snapshot-7'`, `channel: 'snapshot'`, `mcmetaRef: '26.4-snapshot-7'`); when 26.4 is released (reserve brief B163, or the close brief if it lands first) the same package is re-pinned to the release (`mcVersion: '26.4'`, `channel: 'release'`, GeckoLib facts added once a 26.4 build exists). 26.2 is not added: its data formats differ from 26.3 in every worldgen and loot kind, which would double the lowering and library surface for a version users are leaving, while 26.4 is where projects go next and differs by registry entries only. DESIGN §9's support policy is reworded to "the current release and the next version's snapshots (release when it lands); the previous release stays supported through the previous app release".

**D2. Facts of `mc-26.4` (verified 2026-11-05 unless marked).** `java` 25 (verify at implementation against the 26.4 client manifest), `packFormats` resource 102.0 and data 126.0, `dataVersion` 5127, `mcdocRef` `1a674539af7150444db0e2fa8fc46318f91ed86b`, `mcmetaRef` `26.4-snapshot-7`, folders as 26.3 (the sync script and the schema-load test confirm), `worldgen.featureSteps` and `biomeAttributes` as 26.3 (checked against the 26.4 mcdoc at implementation), `fabric` loader `0.20.1`, api `0.165.4+26.4`, loom `1.19.3` (B151 verifies it handles the snapshot; otherwise the Loom version becomes a per-version property), `minecraftDependency` `>=26.4- <26.5-` (Fabric's semver treats `26.4-snapshot-7` as a pre-release of 26.4, which `~26.4` would exclude; verify at implementation on the headless server), `gradle` `9.8.2`; no `geckolib` (entities export reports `export.no-geckolib-target`); `javaProject` only if the ejected sample mod builds against 26.4 in B153, else omitted (`export.no-java-project-target`).

**D3. Target migration hooks.** `mc-26.4` implements `migrateFrom(previous, project)`: for a project on `mc-26.3` it walks every element's data for ids in the registries whose members were removed between the two vendored `registries.json` files (the removed-id table lives in the 26.4 target as data and a test asserts it equals the diff of the two vendored files, so it cannot drift), reports each as a `target.removed-id` problem with `elementId` and `path`, and applies known renames as `MigrationChange`s with `data` (26.3 → 26.4: `minecraft:large_dripstone` feature type → `minecraft:large_speleothem` only if the 26.4 mcdoc confirms the config shape, else reported). A hook from an unknown target reports one `target.no-migration-path` problem and no changes. Pack formats need no change: lowering writes them from the target. Schema differences surface through the normal validation pass after the switch.

**D4. The "Upgrade project target" command.** `File > Upgrade Project Target…` (palette "Upgrade project target…", command id `upgradeTarget`) opens `UpgradeTargetDialog`: it lists every built-in target other than the project's (snapshot badge for `channel: 'snapshot'`), runs the chosen target's `migrateFrom` with the current project (pure; nothing applied yet), shows the changes and problems, and on "Upgrade" applies, as one undo step, the `targets` change (`commands.setTargets([id])`, new in `@msm/core`) and every `MigrationChange` with `data`; the schema context reloads for the new target and validation runs. Downgrading uses the same dialog (the previous target's hook, which may only report). The status bar shows the project target (`data-testid="project-target"`), and the New project dialog offers a target select defaulting to the newest release target (`defaultTargetId` is the first target with `channel: 'release'`).

**D5. Everything else is already per target.** Pack names (`…-mc-26.4.zip`), `fabric.mod.json`, the runtime jar ([ADR 0038](0038-per-version-runtime-builds.md)), the Test in Minecraft instance name (`MCSuperMods Test (<mcVersion>)`) and `tools/run-fabric-server` take their facts from the target; the Java generator is copied from 26.3 and adjusted where B151 finds differences.

## Consequences

- Two targets in `builtInTargets` means every per-target test (71 plugin test files, the exporters' library tests) runs twice; entries that cannot validate on 26.4 declare `supports` ([ADR 0036](0036-plugin-api-1.0-and-compatibility-policy.md) D4) rather than failing, and the sample-mob export on 26.4 is expected to report `export.no-geckolib-target`.
- The asar grows by about 5.4 MB to about 29 MB, so the `app.asar` budget in `tools/check-size` rises from 25 MB to 32 MB with its README row rewritten (B153 records the measured number). Moving the vendored data out of the asar into `extraResources` is the recorded next step if the asar keeps growing (reserve B166); the 150 MB installer budget is not at risk.
- Snapshot churn: the 26.4 package is refreshed by re-running the two sync scripts and the target tests; a weekly refresh is not promised, and the guide says that the snapshot target follows the latest snapshot MSM was built against.
- Resolves DESIGN Open Question 1 as far as 26.x goes (Loom's non-remapping variant is the plain `net.fabricmc.fabric-loom` plugin on unobfuscated jars) and records Open Question 3's status (GeckoLib lags snapshots; the fallback renderer stays unbuilt).

## Status

Proposed (2026-11-05). B152 creates the package, B153 integrates and migrates, B160 builds the command; the release re-pin is reserve B163. Accepted at Phase 7 close.

B151 findings (2026-11-05): on a 26.4-snapshot-7 Fabric dedicated server (Loader 0.20.1, Fabric API 0.165.4+26.4) Fabric Loader reports the game as `26.4-alpha.7`. A content jar with `"minecraft": ">=26.4- <26.5-"` loads (so does `>=26.4-` and `~26.4-`); `~26.4` fails mod resolution ("requires any version between 26.4 (inclusive) and 26.5- (exclusive) … only the wrong version is present: 26.4-alpha.7"). `minecraftDependency` `>=26.4- <26.5-` is confirmed; it also admits the 26.4 release, so the re-pin (B163) need not change it. Loom 1.19.3 handles the snapshot (no per-version Loom needed). The runtime's `msm:sound_type` `amethyst` maps to the 26.4 `block_sound_set` `minecraft:amethyst_block` (see ADR 0038).
