# ADR 0080: Custom particle types and richer particle options

## Context

A project can show particles today only through vanilla's option-less particle types: the `spawn_particle` action and the script method `world.spawnParticle` send a `SimpleParticleType` from the server (audit L13: no dust colour, no block or item particles, no `count 0` motion, nothing beyond the vanilla send distance), an effect, a leaves block and a portal name an option-less type, and a portal's colour exists only as coloured dust (ADR 0077 limit P3). The coverage audit (backlog B14, rows "Particle definitions (`particles/*.json`)" and "Particle types", limits L3, L13 and L16) asks for particle types of a project's own, with their own pictures and behaviour, usable everywhere vanilla particles are used (events and actions, blocks, items, scripts, `/particle`), plus richer options for vanilla's particles, a Particle Studio, Creator flows and templates. This ADR covers the format, the runtime (server and client), the versions, lowering, validators, vanilla pack safety and the eject; [ADR 0081](0081-particle-studio-flows-and-tests.md) covers the app, the library, the AI helper and the tests. The working plan is `docs/PLAN-particles.md` (fact table F1–F23, limits K1–K16).

Facts read on 2026-11-14 with `javap -protected` and `javap -c -p -constants` (JDK 25, `/root/jdk/jdk-25.0.5+8`) over the Loom-cached `minecraft-merged-deobf-26.3.jar` and `minecraft-merged-deobf-26.4-snapshot-7.jar`, the Loom-cached `fabric-particles-v1` 5.0.28 (in `fabric-api` 0.165.2+26.3) and 5.0.34 (0.165.4+26.4), `fabric-registry-sync-v0` 8.0.5 and 8.1.5, and the vendored vanilla-mcdoc and mcmeta data of both targets:

- **A particle type needs a codec and a stream codec only when it has options.** `ParticleType(boolean overrideLimiter)` is abstract with `codec()` and `streamCodec()`; `SimpleParticleType` is its own options object with a unit codec. Fabric's `FabricParticleTypes.simple(boolean)` builds one; `complex(...)` takes a `MapCodec` and a `StreamCodec`. `ParticleTypes.CODEC` (a `Codec<ParticleOptions>` dispatching on `type`) and `ParticleTypes.STREAM_CODEC` cover every registered type. All of it is the same on both versions.
- **`/particle` works for any registered type.** `ParticleArgument` reads the id, then parses `{...}` SNBT if present or an empty map otherwise and decodes it with the type's codec, so an option-less project type is used as `/particle <ns>:<id>` with no further code. Fabric registry sync marks `BuiltInRegistries.PARTICLE_TYPE` as synced, so client and server agree on the network ids of project types (a client without the mod cannot join, as with blocks).
- **The client side is a provider and a particle class; Fabric hides the version difference.** `ParticleProvider<T>.createParticle(T, ClientLevel, x, y, z, xd, yd, zd, RandomSource)` is the same on both versions, but vanilla's provider plumbing is not: 26.3 keeps providers in an `Int2ObjectMap` (`ParticleResources.getProviders()`), 26.4 in a client registry (`BuiltInClientRegistries.PARTICLE_PROVIDER`, `ParticleResources.bootstrap(Registry)`, `getProvider(T)`). Fabric's `ParticleProviderRegistry.getInstance().register(type, PendingParticleProvider)` with `PendingParticleProvider.create(FabricSpriteSet)` is identical in both module builds and absorbs the change. (The name on these versions is `ParticleProviderRegistry`; there is no `ParticleFactoryRegistry`.)
- **`TextureSheetParticle` is gone; `SingleQuadParticle` is its successor and is nearly the same on both versions.** `Particle` (position, velocity, `gravity`, `friction`, `hasPhysics`, `age`, `lifetime`, `getLightCoords(float)`) and `SimpleAnimatedParticle` are identical. `SingleQuadParticle` (`quadSize`, `rCol`/`gCol`/`bCol`, `alpha`, `roll`/`oRoll`, `sprite`, `setSpriteFromAge(SpriteSet)`, `setSprite`, `setColor`, `setAlpha`, abstract `getLayer()`) gains a protected `uvFlip` field on 26.4, and its `Layer` record changes its constructors and pipeline accessors (26.3: a `renderpearl` `RenderPipeline` and an `OitPipelineSet`; 26.4: a `Function<OitStage, RenderPipeline>`), while the constants `Layer.OPAQUE` and `Layer.TRANSLUCENT` exist on both. `SpriteSet.size()` exists on 26.4 only. A particle class that never constructs a `Layer`, never reads `uvFlip` and never calls `SpriteSet.size()` compiles unchanged on both. `LightCoordsUtil.FULL_BRIGHT` (15728880) is the full-bright light value on both.
- **Vanilla's particle pictures come from one atlas and one description file per type.** `assets/minecraft/atlases/particles.json` stitches the `particle` texture folder of every namespace with an empty prefix (so `assets/<ns>/textures/particle/spark_0.png` is the sprite `<ns>:spark_0`); `assets/<ns>/particles/<id>.json` lists a type's sprites as `{ "textures": [...] }` (`ParticleDescription`). A description for a type with no provider is ignored with a debug line ("Redundant texture list for particle"); a provider whose type has no sprites logs a warning ("Missing particle sprites"). Identical on both versions.
- **What vanilla's base particle does.** The four-argument `Particle` constructor sets friction 0.98, size 0.2 and a random lifetime; the seven-argument one also jitters the given velocity randomly. `tick()` applies gravity (`yd -= 0.04 × gravity`), moves with collision when `hasPhysics`, then multiplies the velocity by `friction`. The client adds a particle unless it is more than 32 blocks from the camera or the Particles option is Minimal; a type whose `getOverrideLimiter()` is true, or a spawn with the force flag, skips both checks. An exception thrown by a provider crashes the client ("Exception while adding particle").
- **Server-sent particles are visible to GameTests; client-only ones are not.** `ServerLevel.sendParticles` builds a `ClientboundLevelParticlesPacket` per player in range; the packet-reading player of `MsmSoundGameTest` and the parity `ParityEars` (a vanilla `Connection` in a Netty `EmbeddedChannel`) can read it. `Block.animateTick` runs only on the client.
- **A client test route may exist.** `fabric-client-gametest-api-v1` (6.0.12 and 6.0.17) is in both Fabric API builds and Loom's `configureTests { enableClientGameTests }` turns it on; the container has Xvfb and Mesa's software rasteriser. An earlier `runClient` under `xvfb-run` failed with "no GLX visual" (DEVLOG, Phase 5); `xvfb-run`'s default screen is 8-bit, which offers no GLX visual. Whether a 24-bit screen fixes it is checked by brief B356, not assumed.

## Decision

- **D1 A new kind `msm:particle`; every project particle is an option-less `SimpleParticleType`.** Definitions live at `msm/<ns>/particle/<path>.json` (kind folder `particle`, registry `particle_type`), registered by the runtime with `FabricParticleTypes.simple(always_show)` under the definition id. We chose option-less types because every field that takes a particle today (`spawn_particle`, `world.spawnParticle`, an effect's `particle`, a leaves block's `falling_particle`, a portal's `particles.type`, `/particle`, vanilla's enchantment `spawn_particles` and ambient particle attributes) accepts one with no change, and because no codec or stream codec of ours crosses the network. Behaviour is fixed per type; a project that wants two colours makes two particles (limit K2). Format (closed struct):

  ```
  struct Particle {
    format: int,
    textures: [#[id(registry="texture", path="particle/")] string] @ 1..64,
                                   // sprite ids in the particle atlas, in frame order
    animation?: ("age" | "loop" | "random"),  // default "age" with more than one texture:
                                   // frames run once over the lifetime; "loop" every frame_ticks;
                                   // "random": one random frame per particle
    frame_ticks?: int @ 1..1200,   // "loop" only; default 2
    lifetime?: (int @ 1..6000 | struct { min: int @ 1..6000, max: int @ 1..6000 }),  // ticks; default 20
    size?: float @ 0.01..16,       // quad size in blocks; default 0.2 (vanilla's)
    size_end?: float @ 0..16,      // size at the end of the lifetime; default size
    gravity?: float @ -16..16,     // vanilla's factor (yd -= 0.04 × gravity per tick); default 0
    friction?: float @ 0..1,       // velocity kept per tick; default 0.98 (vanilla's)
    collision?: boolean,           // stops on blocks; default true
    color?: int @ 0..16777215,     // tint; default 16777215 (white: the picture as drawn)
    color_end?: int @ 0..16777215, // tint at the end of the lifetime; default color
    alpha?: float @ 0..1,          // default 1
    fade?: ("none" | "out" | "in_out"),  // default "none"
    emissive?: boolean,            // full bright, as glow and end rod particles; default false
    translucent?: boolean,         // default true when alpha < 1 or fade is not "none", else false (cut-out)
    spin?: float @ -360..360,      // degrees per tick; default 0
    always_show?: boolean,         // drawn beyond 32 blocks and with Particles: Minimal; default false
  }
  ```

  The element is the definition plus nothing editor-only (lowering only sets `format`). Runtimes older than the release that ships this ADR ignore the `particle` folder entirely (`DefinitionScanner` reads known kinds only), so the ids are unknown there and every reference fails as an unknown particle type.
- **D2 Pictures.** Frames are separate PNGs in the particle atlas, as vanilla's own: a project sprite `<ns>:<name>` is the asset `assets/<ns>/textures/particle/<name>.png` (8 by 8 or 16 by 16 recommended), and vanilla sprites (`minecraft:generic_0`, `minecraft:glow` and the like) may be referenced, never bundled. Lowering writes the description `assets/<ns>/particles/<path>.json` (`{ "textures": [...] }`, schema `::java::assets::particle::Particle`) beside the runtime definition. A strip or sheet is split into frames by the Particle Studio (ADR 0081 D1), not by the format. The resource pack plugin gains the vanilla kind `minecraft:particle` (the same description file, folder `particles`), so a resource pack can retexture vanilla particles; a resource pack cannot add particle types (limit K1). The folder is fixed in the kind, as `minecraft:equipment`'s is, because adding a `ResourceFolderKey` is not additive in plugin API 1.x; the target supplies it as a fact (D9).
- **D3 Registration order and load rules.** Particle types register right after sound events and before effects, potions, blocks and items, so every later definition can name them (an effect's `particle`, leaves, portals, `spawn_particle` in any event); the runtime logs `[msm_runtime] registered N particle type(s)`. A definition with an unknown key or a value out of range is an error and registers nothing (closed struct); an id already in `BuiltInRegistries.PARTICLE_TYPE` is an error; `lifetime.min` above `max` is an error. Definitions are read from the same jar on both sides (limit K3).
- **D4 The client: one particle class, one provider, no Mixin.** `client/particle/MsmParticle extends SingleQuadParticle` and `client/particle/MsmParticleProvider` are registered for every project type by `MsmRuntimeClient` through `ParticleProviderRegistry`. The particle uses the four-argument base constructor and sets the velocity given by the spawn exactly (the server or the caller already randomises it); it sets `gravity`, `friction`, `hasPhysics` and its lifetime from the definition and lets vanilla's `tick()` move it; on each tick it applies the frame (`age` through `setSpriteFromAge`, `loop` and `random` through `SpriteSet.get`), the size curve, the colour and alpha curves and the spin; `getLayer()` returns `Layer.OPAQUE` or `Layer.TRANSLUCENT`; `getLightCoords` returns `LightCoordsUtil.FULL_BRIGHT` when `emissive`. The curves are computed by a pure class `client/particle/ParticleLook` with no Minecraft client types, unit-tested and tied to the app's preview by a shared golden (ADR 0081 D6). The provider never throws: a type whose sprite set is empty creates no particle and logs one warning per type (limit K10). Written from this ADR, never from a vanilla particle class.
- **D5 Richer particle options for spawning.** The action `spawn_particle` and the script method `world.spawnParticle` accept either an id (an option-less type, vanilla or project) or a vanilla particle options object with a `type` and that type's fields, as vanilla's own particle JSON (for example `{ "type": "minecraft:dust", "color": [1, 0.5, 0], "scale": 1.5 }`, `{ "type": "minecraft:block", "block_state": "minecraft:stone" }`, `{ "type": "minecraft:item", "item": { "id": "minecraft:diamond" } }`). The runtime keeps the object as JSON and decodes it with `ParticleTypes.CODEC` through `RegistryOps` of the server's registry access the first time it is used (cached per action), because block and item options name registry entries that do not exist yet at init; every options object is also decoded once at `SERVER_STARTED` (`MsmRegistrar.checkAfterStart`), which logs one error naming the definition and the field (limit K11). A failed decode sends nothing. Two new fields: `motion` (`[x, y, z]` blocks per tick: each particle starts with exactly this velocity, vanilla's `count 0` form; closes the L13 item) and `force` (vanilla's `/particle ... force`: sent to players up to 512 blocks away and drawn whatever their Particles option). `count` gains an upper bound of 1000 (one packet per player per action). The script method takes the same object and the options `{ count, spread, speed, motion, force }` (Script API 1.3, "Since runtime 1.7.0", verify the number at implementation). Runtimes older than this ADR reject an object `particle`, `motion` and `force` (the usual wording in the mcdoc).
- **D6 Ambient block particles: `msm:ambient_particles`.** A new block component, allowed on every block type except `portal` (which has its own `particles`): `{ particle: <id or options object>, chance?: float @ 0..1 (default 1), count?: int @ 1..16 (default 1), offset?: [x, y, z] (default [0.5, 0.5, 0.5], from the block's corner), spread?: [x, y, z] (default [0.5, 0.5, 0.5]), velocity?: [x, y, z] (default [0, 0, 0]), states?: { <property>: <value> } (only while the block state matches, for example { "lit": "true" } on a machine) }`. It runs from `animateTick` (client only, about every tick for blocks near the player, as a torch's flame), added to `MsmBlock`, the container and machine block and every family class in `registry/types/` by delegating to `BlockBehaviourDriver.animateTick`; the leaves classes call vanilla's first. The spawn plan (which particles, where, with what velocity) is a pure helper tested on the server with a seeded random; the drawing is an in-game check (limit K5). It is the 15th of the 16 fields of `BlockComponents` (ADR 0074 limit C18: one left after it). Items and mobs show particles through their triggers and `spawn_particle` (server-sent); a held-item or thrown-item trail is not in this batch (D11).
- **D7 Existing fields.** An effect's `particle`, a leaves block's `falling_particle` and a portal's `particles.type` keep "a particle type without options"; project particles satisfy that. The validators now know which vanilla types take options (D9), so naming one there, or as a plain id in `spawn_particle`, is an error at edit time (`blocks-items.particle-needs-options`) instead of a runtime load error only. ADR 0077 limit P3 is narrowed: a portal shows its own particle type with any colour, drawn by D4.
- **D8 Versions.** All runtime code is shared, server and client: every member used is the same on both versions (plan fact table). The runtime never touches `ParticleResources`, `BuiltInClientRegistries.PARTICLE_PROVIDER`, `SingleQuadParticle.Layer`'s constructors or accessors, `SingleQuadParticle.uvFlip`, `SpriteSet.size()` or `ParticleLimit`. If a 26.4 build breaks on a client member anyway, the difference goes behind a seam in `src/mc/<mc>/` (the `EntityRendererRegistration` pattern) and the plan's notes record it.
- **D9 Plugin API 1.14.0 (additive).** `TargetFacts.particles?: { withOptions: readonly string[]; descriptionFolder: string; textureFolder: string }`: the namespaced vanilla particle types that take options (from the vendored vanilla-mcdoc `minecraft:particle` dispatcher, checked against the vendored `particle_type` registry: 22 on both targets, `block` to `vibration`), `particles` and `particle`. Built-in plugins keep `^1.0.0`; an external plugin reading the facts must handle their absence.
- **D10 Lowering, validators and vanilla pack safety** (`@msm/plugin-blocks-items`, `@msm/plugin-resourcepack`, `@msm/exporters`). `msm:particle` lowers to the definition (layer `msm`, schema `msm:particle_definition`) and the description file (layer `resourcepack`); no lang key. Validators (`blocks-items.*`): `particle-lifetime-range` (min above max; error), `particle-frame-ticks-unused` (`frame_ticks` without `loop`; warning), `particle-needs-options` (D7; error), `particle-options-invalid` (an options object checked against the target's `::java::util::particle::Particle` through `validateJson`; error), `particle-options-unknown-type` (error), `particle-description-clash` (a `minecraft:particle` element with the same id as an `msm:particle`; error), and `component-not-for-type` for `msm:ambient_particles` on a portal. Missing frame pictures are reported by the app (validators see no assets), as `transparent-texture-on-solid-block` is. Vanilla pack safety ([ADR 0066](0066-vanilla-pack-safety.md)): `particle_type` joins the mod-only registries (D2 there), so a biome or enchantment naming a project particle is left out of the vanilla data pack (`export.mod-only-reference`, already fatal folders) and a function running `particle <ns>:<id>` is kept with `export.mod-only-function` (only that function fails on a vanilla server, ADR 0066 D5); whether a `dimension_type` or `timeline` naming an unknown particle fails the whole pack is probed on vanilla servers of both targets (brief B346) and, if so, those folders join ADR 0066's fatal list. The vanilla resource pack keeps project descriptions and pictures (harmless: a description for an unknown type is ignored).
- **D11 Java eject (26.3 generator).** A generated `ModParticles` registers the project's types; the generated client initialiser registers a generated `particle/ModParticle` and `ModParticleProvider` copied from the runtime's `MsmParticle`, `MsmParticleProvider` and `ParticleLook` as templates (compared line by line in the target tests); `spawn_particle` options objects and `motion`/`force` go into the generated actions; `msm:ambient_particles` into the generated block classes' `animateTick`. Generation is stricter than the runtime: an options object that does not decode, or `msm:ambient_particles` on a portal, fails generation. Eject stays 26.3 only.
- **D12 Not in this batch (limits).** Particle types with options of our own (per-spawn colour or size on a project type), particles of other shapes (trails, ribbons, 3D models, item-shaped), particles attached to an entity (tracking emitters), client-side held-item or throwable trails (client code that belongs with backlog B15), particles from scripts on the client (L2), sounds or events fired by particles, collisions reported to the server, per-particle light emission onto blocks, editing vanilla particle behaviour (only its pictures, through resource packs), and particles in vanilla packs.

## Consequences

- Format 1 grows additively: one kind, one block component, two action fields and a wider `particle` field. The corpus (prefixes `particle-`, `action-particle-` and `ambient-particles-`), the runtime Codecs, the plugin, the app and the generator move together; a project without particles exports byte-identical files.
- The runtime gains its second client feature with real per-frame logic. CI checks registration, `/particle`, the packets and the network round trip on both targets, the curves through a cross-language golden, and, if brief B356 finds a working route, one headless client run; everything visual otherwise reaches the user's in-game check first (limits K4, K5).
- Project particles need the Fabric mod jar on client and server; vanilla packs leave them out or warn.
- `BlockComponents` keeps one Codec field after this batch.

## Status

Accepted (2026-11-14), with the defaults below; the user may still veto them. Vetoable defaults: a new kind `msm:particle` with option-less types and behaviour fixed per type rather than options of our own (D1); the field names and defaults of D1 (`lifetime` 20, `size` 0.2, `friction` 0.98, `gravity` 0, `collision` on, `animation` `age`, `frame_ticks` 2, `translucent` derived, `always_show` off); frames as separate PNGs rather than a sheet in the format (D2); the `minecraft:particle` resource pack kind (D2); registration before effects (D3); options objects decoded at first use and checked at server start (D5); the names `motion` and `force` and the `count` cap of 1000 (D5); the component name `msm:ambient_particles`, its defaults and `states` (D6); keeping project descriptions and pictures in vanilla resource packs (D10); a held-item or throwable trail left for later (D12).
