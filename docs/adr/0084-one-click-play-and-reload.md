# ADR 0084: One-click Play and Reload

## Context

**Test in Minecraft** ([ADR 0026](0026-fabric-content-jar.md) D5) exports the content jar, installs it with Fabric API into a Fabric location's `mods/` (only files MSM installed, recorded in `.msm-installed.json`), optionally creates the managed Prism instance `MCSuperMods Test (<mc>)` (marker `.msm-managed.json`), and starts Prism Launcher or MultiMC with `--launch <instance>` (plus `--dir`). The user then picks or creates a world, turns on cheats, finds the items and builds a test area. Each change needs the game closed and started again, because the jar is loaded at start and blocks, items and mobs are registered then (DESIGN §10, the registry freeze). The user asked (2026-11-14): "make it easy to test, make an easier option to test whatever you build in game."

Facts behind this ADR (F1–F12 of the fact table in [ADR 0082](0082-rules-no-code-behaviour.md)'s findings): the client takes `--quickPlaySingleplayer <folder>` on both targets, but vanilla quick play only joins a world that already exists; Prism Launcher's `develop` branch has `-w/--world` (join a world on launch) and forwards a launch to a running Prism; MultiMC was not checked; `WorldOpenFlows.createFreshLevel(String, LevelSettings, WorldOptions, Function<HolderLookup.Provider, WorldDimensions>, Screen)`, `WorldOpenFlows.openWorld(String, Runnable)`, `Minecraft.reloadResourcePacks()`, `Minecraft.stop()` and `ReloadCommand.reloadPacks(Collection<String>, CommandSourceStack)` have the same signatures on 26.3 and 26.4-snapshot-7; game rules are registry ids (`advance_time`, `advance_weather`, `spawn_mobs`, ...) on both; Fabric's `ResourceLoader.registerBuiltinPack` takes packs only from a mod container, so an arbitrary folder pack needs vanilla's own folders or a Mixin. Writing `level.dat` offline was weighed and rejected: its layout is a version fact that changes between snapshots, and the game itself creates a correct world.

## Decision

- **D1 Play.** A **Play** button (toolbar in every mode; File > Play, the palette, `F5`) does, with one progress line and no dialog when everything is ready: save; stop on export-blocking errors (plain-language list in Very easy, ADR 0083 D5); build the content jar (runtime nested, GeckoLib only when needed, as the export dialog's defaults); make sure the **managed test instance** for the project's target exists (created on first Play when a Prism data folder is found; otherwise a one-time panel explains how to install Prism Launcher and sign in, with a "Find Prism" button); install the jar and Fabric API (existing `@msm/interop` `fabric/`); write the **dev files** (D3); start Prism with `--launch` as today. Play uses only the managed instance (D9); "Test in Minecraft…" stays as it is for other instances and launchers.
- **D2 The test world.** The game opens straight into a flat test world: the runtime's client dev hook (D4) handles a **play request** at the title screen, opening `saves/msm-test-<namespace>` when it exists or creating it with `createFreshLevel`: the `minecraft:flat` world preset with its default layers, creative, cheats on, difficulty easy, no structures, a fixed seed. On first join of a new world the runtime runs the app-written **setup function** (`msm-dev/setup.mcfunction`, plain vanilla commands generated per target and checked with Spyglass in tests): game rules from `TargetFacts.dev.gameRules` (time stopped at noon, weather stopped, no natural mob spawning, keep inventory), a 21 by 21 test area at spawn (smooth stone floor, a sign "MCSuperMods test area", a lever, a button, a pressure plate, redstone dust, a 3 by 3 water pool, a grass and farmland patch, a fenced pen) and chests by the spawn holding one stack of every project item, block item and spawn egg (`item replace block`); after each later Play only the chests are refilled. The project's first nine items go in the hotbar. "New test world" in the Play menu renames the old folder `msm-test-<namespace>-old-<n>` (never deletes) and the next Play creates a fresh one. Prism's `--world` is not used: the runtime hook works with MultiMC too and creates the world when it is missing.
- **D3 Dev files.** Inside the managed instance's game folder only, in `msm-dev/` (all JSON sorted, written atomically by main): `dev.json` (`format: 1`, namespaces, target, world folder name, app version), `play.json` (a play request with a sequence number, consumed by the runtime), `request.json` (reload, reopen world or quit requests, D5 and D6), `status.json` (written by the runtime: state `title`, `loading` or `world`, the world, the last handled request, a timestamp every 2 seconds), `installed.json` (written by main at Play: SHA-256 of every output path in the installed jar, for D6), `setup.mcfunction`, and the overlay folder `overlay/` (D6). Main also keeps the game's `resourcepacks/msm-dev/` folder pack enabled by adding `"file/msm-dev"` last to the `resourcePacks` line of the instance's `options.txt` (only that line; the file is created with that line alone when missing; verify at implementation that missing keys take their defaults).
- **D4 Runtime dev mode.** `msm_runtime` gains a dev mode, on only when the game is a client (Fabric environment `CLIENT`), `<gameDir>/msm-dev/dev.json` exists and the world is singleplayer (the integrated server); a dedicated server never reads `msm-dev/` (CI checks the log has no dev line with the folder present). Client side, through Fabric events only (no Mixin): `ScreenEvents.AFTER_INIT` on the title screen handles a play request (D2) once; `ClientTickEvents` polls `request.json`'s modification time every 10 ticks and writes `status.json` every 40; a quit request saves, leaves the world and calls `Minecraft.stop()`. Server side: the setup function and chest refill on join, the script and event overlays (D6) and `/reload` handling. One log line on start: `[msm_runtime] dev mode for <namespaces> (singleplayer test world)`.
- **D5 Restart in one click.** When Play is pressed while the game is running (`status.json` fresher than 10 seconds), the jar cannot be replaced (Windows keeps open jars locked, verify at implementation), so Play writes a quit request, waits up to 30 seconds for the status to go stale and the jar to unlock, installs, and starts the game again; the play request reopens the same world. If the game does not answer (an older runtime, a crash, a game started outside MSM) Play says "Close Minecraft, then press Play again".
- **D6 Reload.** A **Reload** button (and `Ctrl+R`, palette, Play menu) is enabled while the game is in the test world. It lowers the project, compares it with `installed.json` and the current overlay, and sorts the differences:
  - **Reloads in place:** data pack files (functions, loot tables, recipes, tags, advancements, machine recipes) written as a folder pack `saves/<world>/datapacks/msm-dev/` (vanilla's `/reload` enables a newly found pack; verify at implementation that it then sits above the mod's own data); scripts, including Rules' generated scripts, written to `msm-dev/overlay/msm/<ns>/script/**.js` and read by the runtime's script scanner in dev mode in place of the jar's copy with the same id; **event action lists** of definitions that already exist, written to `msm-dev/overlay/msm/<ns>/<kind>/<path>.json` and applied by dev mode on reload to the events only (a definition's components, trigger set, properties and registrations are never changed; the definition's own validation runs and an invalid overlay keeps the old events with an error line); textures, models, sounds and lang written to `resourcepacks/msm-dev/` and reloaded with `Minecraft.reloadResourcePacks()`. The runtime runs `/reload` through the command dispatcher as the server (scripts reload on `END_DATA_PACK_RELOAD` as today) and says in chat "MCSuperMods: reloaded (N changes)".
  - **Needs reopening the world:** data of registries loaded with the world (the folders in `TargetFacts.dev.worldDataFolders`: worldgen, dimension types, enchantments, damage types, variants and the like); the runtime saves, leaves and reopens the world on request (new terrain appears only in new chunks).
  - **Needs a restart:** a new, removed or renamed block, item, mob, effect, potion, particle type or other definition; any definition change outside `events` (components, triggers added to a thing, properties, block types); `fabric.mod.json`; a file removed (an overlay cannot remove what the jar has); the Fabric API or runtime version. Reload then shows **"Restart needed"** with the reasons in words ("You added a new block: Ruby Lamp. New blocks are only read when Minecraft starts.") and a **Restart** button (D5).
  A Reload that mixes kinds does the in-place part and offers Restart for the rest. Every Play clears the overlays, because the new jar holds everything.
- **D7 Game status.** A small chip by Play shows "Game not running", "Starting…", "In the test world" or "Restart needed", from `status.json` polled by main every second while the window is focused.
- **D8 What CI checks and what only Windows can.** CI (Linux) checks: the dev file formats, the options line edit, change sorting and the setup function (unit tests, Spyglass on both targets); the runtime's server side dev mode with GameTests (overlays, events swap, setup function, chest refill, `/reload`, nothing outside `events` changed, invalid overlays rejected) on 26.3, 26.3 without GeckoLib and 26.4; a dedicated server with `msm-dev/` present ignoring it; and an e2e path driving Play, Reload, Restart needed and Restart against a stub launcher that plays the runtime's part in the status files. The client hook (title screen, world creation and opening, resource reload, quit) is tested with the Fabric client GameTest route only if the particles batch's B356 found one ([ADR 0081](0081-particle-studio-flows-and-tests.md) D6); otherwise its pure parts are JUnit-tested and the rest is the user's in-game check on Windows with Prism, together with launching, the jar lock and the restart round trip.
- **D9 Safety.** Dev files are written only into an instance with the `.msm-managed.json` marker; the user's other instances and worlds are never touched; overlays and requests are plain files the runtime reads only in dev mode; nothing is sent over the network.
- **D10 Plugin API.** `TargetFacts.dev?: DevFacts` with `gameRules: { advanceTime, advanceWeather, spawnMobs, keepInventory }` (registry ids) and `worldDataFolders: readonly string[]`, filled for both targets in `packages/targets` (plugin API 1.15.0 together with [ADR 0082](0082-rules-no-code-behaviour.md) D9).

## Consequences

- Testing a change becomes Play once, then Reload for most edits; new things still need a restart, said in words, done in one click.
- The runtime carries dev-only code on the client, inert without `msm-dev/dev.json`; dedicated servers and normal play are unaffected.
- Play depends on Prism Launcher (or MultiMC through Test in Minecraft); the official launcher and CurseForge remain install-only (R6).

## Findings from implementation

Recorded at close (2026-11-14) from B364 (`TargetFacts.dev`), B366 (89d4f71), B369 (917da7d), B373 (5e3be08), B374 (54a5a0d), B376 (34664cf), B378, B379 (57944e5) and B381 (82f5a02), with the orchestrator fixes 3129377 and 3fff6d5. The fact table (F1–F24) and limits (R1–R22) are in [ADR 0082](0082-rules-no-code-behaviour.md)'s findings. Shipped in 1.5.1 (draft).

- **Dev files** (D3; B366). `@msm/interop` `fabric/dev-session.ts`: in `<gameDir>/msm-dev/`, sorted keys, `format: 1`: `dev.json { appVersion, namespaces, target, world }`, `play.json { seq, world }`, `request.json { action reload|reopen|quit, assets, changes, seq }`, `status.json { handled { seq, ok, message? } | null, runtime, state title|loading|world, time, world }` (one shared `seq`; seqs at or below the last handled are ignored), `installed.json { files { path: { sha256, frozen?, element? } }, jar { fabricApi, modId, modJson, runtime }, overlay }`; `devWorldFolder(ns)` = `msm-test-<ns>`, old worlds `<world>-old-<n>`; `isGameRunning` (10 s stale), `QUIT_WAIT_MS` 30000, `REQUEST_POLL_TICKS` 10, `STATUS_WRITE_TICKS` 40, `DEV_RESOURCE_PACK_ID` `file/msm-dev`. `options-txt.ts` writes `["vanilla","fabric","file/msm-dev"]` when the line is new and, since 3fff6d5, `onboardAccessibility:false` when the key is missing, so the first start reaches the title screen (a player's own choice is kept). `changes.ts` `classifyChanges` with restart reasons `new-definition`, `definition-changed`, `definition-renamed`, `file-removed`, `sound-events`, `mod-file`, `mod-id`, `runtime-version`, `fabric-api-version`. `setup-function.ts` writes the `# msm:setup` and `# msm:refill` sections: 18 chests of 27 items, anything past 486 left out; it passes Spyglass on both targets.
- **`TargetFacts.dev`** (D10; B364). Game rules `advance_time`, `advance_weather`, `spawn_mobs`, `keep_inventory` (bare names); `worldDataFolders` from `RegistryDataLoader`'s world and dimension registries: 53 on 26.3, 54 on 26.4 (+ `block_sound_set`). Folders are matched by path; whether `/reload` re-reads tags of world registries is unverified.
- **Runtime, server side** (D2, D4, D6; B369). `runtime/dev/` (`DevMode`, `DevFiles`, `EventOverlay`, `DevSetup`): dev mode is decided once at `SERVER_STARTING`, on for an integrated server with a valid `dev.json` or for a GameTest run with `-Dmsm.dev.testRoot`, off on every dedicated server (Fabric's GameTest server reports itself dedicated, hence the property). Log `[msm_runtime] dev mode for <ns, ns> (singleplayer test world)`. Event overlays (block, item, entity, effect) may differ only in `events`, else one error and the old events stay; potion, particle and addition kinds take no overlay ("has no events; changes to it need a restart"). Script overlays replace or add scripts. Setup then refill on a new world, refill on later first joins (attachment `msm_runtime:dev_setup`). 5 GameTests (`MsmDevModeGameTest`), `DevFilesTest` 6 JUnit.
- **Runtime, client side** (D2, D4, D5; B374). `runtime/client/dev/` (`DevClient`, `DevWorldSettings`, `DevClientFiles`), Fabric events only (`ScreenEvents.AFTER_INIT`, `END_CLIENT_TICK`, `END_DATA_PACK_RELOAD`), no Mixin and no seam. `play.json` is handled only at the title screen with no world or loading overlay, and deleted when read; the world is created flat (default layers), creative, commands, easy, no structures or bonus chest, seed 20261114, named "MCSuperMods test (<namespace>)". `reload` runs `/reload`, then the resource packs when `assets` is set; `reopen` saves, leaves and reopens (and refills the chests); `quit` saves, leaves, writes status once and stops. Timeouts: reload 2,400 ticks, world open 6,000 ticks. Measured in the client GameTest: Play about 3 s from the title screen, reload with assets about 3 s, reopen 2–3 s. Chat lines "MCSuperMods: reloaded (N changes)" and "MCSuperMods: reopened the test world (N changes)". `DevWorldSettingsTest` 5 and `DevClientFilesTest` 8 JUnit (704 in all); **the client GameTest `MsmDevClientGameTest`** (Play, reload with assets, reopen with refill, quit, a second Play, reload outside a world) runs in CI on 26.3 and 26.4, so D8's client part is checked automatically (limit R5 moved).
- **Main** (D1, D5, D6, D7; B373). `platform/play.ts` `createPlayService`: `status`, `play`, `reload`, `restart`, `newTestWorld` (refused while the game runs), results `{ ok: false, code, message }` rather than throws; managed instance only, created or updated on every Play; overlays cleared at Play, stale ones deleted at Reload; the dev data pack and resource pack `pack.mcmeta` written at every Play. Timings `STARTING_WINDOW_MS` 180 s, `QUIT_SETTLE_MS` 5 s, `STATUS_POLL_MS` 1 s. Channels `msm:v1:play:status|play|reload|restart|newWorld` and the push `msm:v1:play:statusChanged`; `window.msm.play`. Windows lock errors `EBUSY`, `EPERM` and `EACCES` are all treated as locked. The managed instance's game folder is a reveal root (3129377).
- **The renderer** (D1, D6, D7; B376, B378). `components/play/` (`PlayControls`, `RestartNeededDialog`, `PrismSetupPanel`) and `store/play-store.ts` (`connectPlay`; Play and Reload flush pending edits and save first). Chip words "Prism Launcher not found", "Game not running", "Starting…", "In the test world", "In another world", "Restart needed" (two beyond D7's four). F5 is Play and Ctrl/Cmd+R Reload in Game; Electron's window reload moved to Ctrl/Cmd+Shift+R. `lowerExpandedProject()` files carry no `elementId`, so `playOutputs` derives it from the path (follow-up: carry it from core).
- **Bug found by e2e** (B379). Play and Reload sent pack-layer files outside `assets/` and `data/` (`pack.mcmeta`, `pack.png`), so the first data change asked for a restart; `playOutputs` now drops them as the content jar does. Found after the v1.5.0 tag (47ad42c), whose build was cancelled; the release is 1.5.1.
- **Tests.** e2e `play-path` against `app/e2e/assets/stub-launcher.mjs` through a fake Prism folder (`PRISMLAUNCHER_DATA_DIR`; the real spawn path), with env hook `MSM_E2E_RUNTIME_DIR`; CI step "Headless Fabric server check (sample rules, dev mode stays off on a dedicated server)" with `msm-dev/` present, forbidding the dev lines and comparing the folder before and after.
- **Left for the user's Windows check** (`fixtures/sample-rules/README.md`): the first Prism launch, the real `stop()` and jar unlock, the Restart round trip, the resource reload on screen, the chat lines, F19–F21.

## Status

Accepted (2026-11-14; findings recorded at close the same day; shipped in 1.5.1, a draft awaiting the user's Windows test), with the defaults below; the user may still veto them. Vetoable defaults: Play always using the managed instance; creating it on first Play; `F5` and `Ctrl+R`; the world folder `msm-test-<namespace>` and the flat, creative, easy, no-structures, fixed-seed world; the game rules chosen; the test area's contents; chests with one stack of every project item and the hotbar; renaming instead of deleting old test worlds; the runtime hook instead of Prism's `--world`; the event overlay (events only) in dev mode; Restart by quit request; the 10-second staleness and 30-second wait; the status chip wording (six states); `onboardAccessibility:false` written into the managed instance; the window reload moved to Ctrl+Shift+R.
