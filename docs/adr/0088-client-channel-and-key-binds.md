# ADR 0088: The client channel and project key binds

## Context

The runtime has almost no client code and no networking channel of its own (coverage audit L2, L3; backlog B15). Everything a player can tell the server today is what vanilla sends: movement, the use and attack clicks, sneaking, chat. The user asked on 2026-11-14 for vehicles ("would it be possible to make things like tanks", then "keep going, add the vehicles too") and set the rule "anything that can be made in vanilla java should be possible through this app". A tank needs a fire key; the research of 2026-11-14 (`popular-mods.md`, section 3) ranks "key binds that fire server events" as the single feature that unlocks the most popular mod ideas (fire keys, reload, spell switching, ability keys, horns). Rules has no key trigger (ADR 0082 limit R10).

Facts read on 2026-11-14 with `javap` (JDK 25) over the Loom-cached Fabric API module jars of both targets (26.3: Fabric API 0.165.2, networking 6.4.1, key mapping 2.0.8, events interaction 5.3.10, client GameTest 6.0.12; 26.4-snapshot-7: 0.165.4, networking 6.4.2, key mapping 2.0.9, events interaction 5.3.15, client GameTest 6.0.17) and the merged Minecraft jars; the full table with every signature is in [ADR 0090](0090-vehicles.md)'s findings (fact table V1 to V24):

- **Payloads.** `PayloadTypeRegistry.serverboundPlay()` and `clientboundPlay()` register a `CustomPacketPayload.Type<T>` with a `StreamCodec<? super RegistryFriendlyByteBuf, T>` (plus `registerLarge` with a size); `ServerPlayNetworking.registerGlobalReceiver(Type, PlayPayloadHandler)` hands the payload and a `Context` (`player()`, `server()`); `ClientPlayNetworking.send(payload)` and `canSend(Type)`; `ServerPlayNetworking.send(ServerPlayer, payload)` and `canSend`. Identical on both versions.
- **Key mappings.** `KeyMappingHelper.registerKeyMapping(KeyMapping)` and `getBoundKeyOf`; `KeyMapping(String, InputConstants.Type, int, KeyMapping.Category)`; `KeyMapping.Category.register(Identifier)` makes a category of our own. Identical on both versions.
- **Vanilla already sends the movement keys.** `ServerPlayer.getLastClientInput()` returns an `Input` record (`forward`, `backward`, `left`, `right`, `jump`, `shift`, `sprint`) kept up to date by `handlePlayerInput`, on both versions. Projects need nothing new for those keys.
- **Client hooks.** `ClientTickEvents.END_CLIENT_TICK` and `ClientPreAttackCallback` (Fabric events interaction) exist on both versions.
- **Tests.** Fabric's client GameTest API has `TestInput.holdKey(KeyMapping)`, `pressKey`, `releaseKey` and `worldBuilder().createServer()`, a real dedicated server the test client connects to (`TestDedicatedServerContext.connect()`), on both versions. The headless route (Mesa EGL under Xvfb) runs in CI since the particles batch (ADR 0081 D6).

## Decision

- **D1 One runtime channel, versioned by payload id.** The runtime registers its payloads under the namespace `msm_runtime` with the version in the path: serverbound `msm_runtime:key_v1` and clientbound `msm_runtime:hud_v1` (ADR 0089). A later incompatible change adds `_v2` beside `_v1`; the old one stays as long as the runtime promises it. Each side checks `canSend` before sending, so a server or client with an older runtime simply does not receive the payload; nothing is sent to a client that has no receiver. Codecs use `StreamCodec` with bounded strings (identifiers at most 256 characters) and bounded lists; anything larger is a decoding error, which Fabric turns into a disconnect for malformed packets (vanilla behaviour, verify at implementation in B406). No configuration-phase handshake is added.
- **D2 `key_v1` carries an id and a bit, nothing else.** The payload is `{ key: Identifier, pressed: boolean }`. The client never sends coordinates, targets, amounts, item stacks or entity ids; the server derives everything from its own state of the player (position, look, held item, vehicle). This is the core of the security model (D7).
- **D3 A definition kind `msm:key_bind`.** `msm/<ns>/key_bind/<path>.json`, format 1:

  ```
  struct KeyBindDefinition {
    format: 1,
    name?: string,                     // shown in Controls; default lang key key.<ns>.<path>
    default_key: string,               // an InputConstants name, such as key.keyboard.g or key.mouse.4; "none" for unbound
    category?: string,                 // lang key of the Controls group; default key.category.<ns> (the mod's name)
    when?: ("always" | "on_foot" | "in_vehicle" | "driving"),  // default always; checked on the server
    vehicle?: #[id="vehicle"] string,  // with in_vehicle or driving: only this vehicle type
    cooldown_ticks?: int @ 0..1200,    // between two presses that fire; default 0
    hold_interval_ticks?: int @ 1..1200,  // while_held fires every N ticks; default 10
    events?: { [string]: [Action] },   // as on blocks, items and mobs
    "msm:on_press"?: string,           // event names
    "msm:on_release"?: string,
    "msm:while_held"?: string,
  }
  ```

  The player is self and the actor of each event (`run_function` runs as and at the player, as player events do today). The runtime reads the definitions at initialisation on both sides (they are part of the registry freeze: a new key bind needs a restart, and Play's "Restart needed" reasons gain "a new key"). The client registers one `KeyMapping` per definition through `KeyMappingHelper` in the client entrypoint, in one category per namespace (`KeyMapping.Category.register(<ns>:keys)`), so the keys appear in vanilla's Controls screen and are rebindable and saved in `options.txt` by vanilla. The definition kind is a sixth runtime kind beside block, item, entity, effect and potion (the scanner reads `key_bind`).
- **D4 Press, release, hold.** The client sends `pressed: true` on the key's down edge and `false` on its up edge (end of client tick, from `isDown` changes), and sends a release for every held key when a screen opens, the window loses focus or the player leaves (verify the focus case at implementation). The server keeps the held set per player, fires `on_press` and `on_release`, and fires `while_held` every `hold_interval_ticks` while held; it clears the set on disconnect, death, respawn and dimension change (firing no release events then). `when` is checked on the server at press time; a press that fails `when` or `cooldown_ticks` does nothing and is not reported.
- **D5 Runtime-owned keys.** The runtime itself registers a few key mappings in a category "MSM Vehicles" (ADR 0090 D7): fire, second weapon, horn and descend. They use the same payload with ids `msm_runtime:vehicle_fire`, `msm_runtime:vehicle_fire_second`, `msm_runtime:vehicle_horn` and `msm_runtime:vehicle_descend`, and are registered only when at least one vehicle definition is loaded, so a pack without vehicles shows no such keys.
- **D6 Scripts and Rules.** Script API 1.5 (ADR 0089 D8 lists the whole set) adds the events `key.pressed` and `key.released` (`player`, `key`), and Rules gains the triggers "When a player presses <key>", "When a player lets go of <key>" and "While a player holds <key>" on the subject kind key bind (`key_pressed`, `key_released`, `key_held`; the counts in ADR 0082's catalogue grow by three). Rules compiles them to the key bind's own events as it does for blocks and items (ADR 0082 D3). A script event handler for a key fires after the definition's events.
- **D7 Security review of client-sent input.** The threat model is a modified client that sends any payload, at any rate, with any id, at any time. Rules:
  1. Unknown id, malformed payload, a player who is dead, sleeping or in spectator mode: dropped, counted, and logged at most once a minute per player (`[msm_runtime] dropped N key packet(s) from <name>: <reason>`).
  2. Rate limit per player: a token bucket of 20 key packets a second with a burst of 40 (presses and releases together); above it packets are dropped as in rule 1. No kick: vanilla's own packet flood checks stay in charge of floods (verify at implementation which limit vanilla applies to custom payloads).
  3. `cooldown_ticks` is enforced on the server; the client's own state is never trusted.
  4. The server never reads a position, target or amount from the client (D2); vehicle fire keys aim with the driver's look as the server knows it (ADR 0090 D6).
  5. Key events run with the same permissions as other player-triggered events: `run_function` runs the function at the function permission level, as a block's `on_use` does. A key bind therefore gives every player a button for that function, at most at the rate limit. The validator says so (`controls.key-runs-function`, info) so authors treat a key like any other button in the world.
  6. The held set is bounded by the number of key bind definitions; releases for keys not held are ignored.
- **D8 What the app writes.** The kind `msm:key_bind` lives in a new built-in plugin `@msm/plugin-controls` (made with `tools/new-plugin`, with `msm:hud` of ADR 0089). It lowers to the definition and to lang keys (`key.<ns>.<path>`, `key.category.<ns>`). Validators: unknown key name (error, against the target fact list of D9), a default key that a vanilla control uses (warning, naming it), two project keys on the same default (warning), `vehicle` without `in_vehicle` or `driving` (error), an unknown vehicle (error), `controls.key-runs-function` (info). The Key bind Studio captures the default by "Press a key"; Very easy never shows key binds by themselves, only through Rules ("When the player presses a key").
- **D9 Version facts.** Plugin API 1.16.0 (additive) adds `TargetFacts.controls?: ControlFacts { keyNames: readonly string[]; vanillaKeys: Readonly<Record<string, string>> }` (the valid `InputConstants` names and vanilla's default bindings, control name to key name), filled for both targets from a dump taken in the running client by B406, never typed from memory.
- **D10 Vanilla packs, eject, modpacks.** Key binds need the Fabric mod jar: a vanilla pack export leaves them out and says so (`controls.needs-jar`, info). The Java eject leaves key binds, the HUD and vehicles out in this batch (`export.not-in-eject`, a warning per element); copying the runtime's client code into ejected projects belongs with backlog B142 (scripts in the eject), which is the same job (copy runtime sources as templates) and is deferred with it. Modpacks need the runtime on both sides, as they already do for blocks.
- **D11 Not in this batch (limits).** Mouse-wheel and axis input; key combinations with modifiers chosen by the project (vanilla's Controls screen still lets players add them); keys that work inside screens; client-side scripts (audit L2 stands: every key goes to the server); custom screens and block entity renderers for containers and machines (C3, C9 of ADR 0074 D10 and ADR 0075 D12: deferred to the next client batch, because they need a menu type of our own registered on both sides, a screen per menu and a block entity update packet, none of which vehicles need; `BlockEntityRendererRegistry` is missing from Fabric's rendering module on 26.4, so they also need a new seam); a portal overlay and entry sound of our own (P2 of ADR 0077 D10, same reason); held-item and throwable particle trails (ADR 0080 D12, same reason); the other R10 triggers (crafting, picking up, eating, sleeping, advancements), which are server events and belong to a Rules follow-up, not to the client channel.

## Consequences

- The runtime gains its first networking channel and its first client input; every later client feature (custom screens, HUD extensions, camera) reuses `msm_runtime:*_v1` payloads and the guard of D7.
- A project can have keys that do anything an event or script can do; Rules gets three triggers.
- New key binds need a restart (registry freeze), like blocks.
- Key binds, the HUD and vehicles are not ejected until B142 is done.

## Findings from implementation

Recorded at close (B432, 2026-11-15) from B406 (38250d2, the spike), B408 (60d090e), B409 (ae740fc), B410 (76baf47), B411 (36668a6), B413 (e7111c3), B415 (7b4b56b), B420 (185e7c5), B421 (ab22dda), B424 (74d70df), B424a (6507159), B426 (77008c4), B427 (371cca6) and B429 (2f5acdd). The batch's fact table (V1–V24, R1–R3), the spike's open facts S1–S12 and the limits V1–V17, from the deleted plan, are in [ADR 0090](0090-vehicles.md)'s findings. Unreleased; awaiting the user's in-game checks (`fixtures/sample-vehicles/README.md`).

- **Spike answers** (B406, both versions, singleplayer and `createServer()`/`connect()`). S6: key mappings registered in the client entrypoint appear in Controls under the lang key `key.category.<ns>.<path>` of the registered category id, save to `options.txt`, keep players' edits, and `TestInput.holdKey` drives them. S7: the payload round trip works (receiver on the server thread, client receiver on the render thread). S11: a malformed custom payload disconnects the sender in vanilla's decoder before any receiver runs, which answers D1's "verify at implementation". S4: `ClientPreAttackCallback` returning true cancels the attack entirely and fires every tick while held (not used by this batch). S9: vanilla's 62 controls and their default keys dumped per target into `docs/reference/vanilla-keys/`; 26.3 `key.socialInteractions` became 26.4 `key.otherPlayers`. Keyboard codes are SDL/HID scancodes (code 4 is `a`) and mouse codes start at 1.
- **D1 channel as built** (B411). `net/MsmNetworking.init()` registers `KeyPayload(Identifier key, boolean pressed)` as `msm_runtime:key_v1` (identifier at most 256 characters, else the decoder disconnects) and `HudPayload` as `msm_runtime:hud_v1` (ADR 0089). Init order in `MsmRuntime`: `MsmNetworking.init()`, `MsmVehicles.register`, `KeyBinds.init`, `HudServer.init`; on the client `VehicleClient.init()`, `ControlsClient.init()`, `HudClient.init()` before `DevClient.register()` (B408).
- **D3 amendments** (B406, B409, B413). The unbound key is `key.keyboard.unknown`, not "none" (`ControlFacts.unboundKey`). `category` is a category id path (default `keys`), registered as `<ns>:<category>`, with the lang key `key.category.<ns>.<category>` (S6), not `key.category.<ns>`; the name lang key is `key.<ns>.<path>`, both with `/` written as `.`. Elements add `display_name` and `category_name` (lowered to lang and stripped from the definition); keys sharing a category must share `category_name`. `events` is `{ <name>: { actions: [...] } }` as on the other kinds. The kind's default is `{ format: 1, default_key: 'key.keyboard.j' }`.
- **D4 as built** (B406, B411). The client sends presses from `consumeClick()` as well as from `isDown` edges, so one-tick taps reach the server; tests use `holdKeyFor`. `msm:while_held` fires every `hold_interval_ticks` from one interval after the press. The release on focus loss was not measured separately (open).
- **D5 amendment** (B406, B410, B411). Runtime keys: fire R, second weapon **V** (not G: G is vanilla `key.quickActions`; V and H are only F3 combinations, which do not clash), horn H, descend Left Alt; ids `msm_runtime:vehicle_fire`, `vehicle_fire_second`, `vehicle_horn`, `vehicle_descend` (`KeyBinds.RuntimeKey`), pinned in Java against the targets' `runtimeKeys` and in TypeScript against `vanillaKeys`. Runtime keys fire only `KeyBinds.KeyListener`s (weapons, horn, descend), never project events, and are **not reported to scripts**: `key.pressed` and `key.released` carry project keys only.
- **D6 as built** (B421, B424, B424a). Script events `key.pressed` and `key.released` (Script API 1.5, "Since runtime 1.5.1"), run after the definition's own event. Rules triggers `key_pressed` (option `cooldown_seconds`, lowered to `cooldown_ticks`), `key_released` and `key_held` (`interval_seconds`, default 0.5 s, lowered to `hold_interval_ticks`; it keeps the `run_script` bridge), in the group "Keys", compiling to the key bind's `msm:on_press`, `msm:on_release` and `msm:while_held`; slot type `key` with its own picker. Very easy shows keys only through Rules ("A player presses the key", the key captured by pressing it).
- **D7 as built** (B411, B426). `InputGuard`: 20 packets a second with a burst of 40, dropped not kicked; releases are never dropped for the player's state; log `dropped N key packet(s) from <name>: <reason>` at most once a minute. A press fires only after rate limit, known id, not dead, sleeping or spectating, not already held, `when` and cooldown, in that order. Rule 1 amended: a malformed payload cannot be counted (vanilla disconnects first, S11); only decodable payloads are counted and dropped. Events run with `EventContext.forItem(level, player)` (`run_function` as the player, permission level 2). `HeldKeys` (server thread) offers `isHeld`, `heldTicks` (-1 when not held), `held` and `playersHolding`. Which flood limit vanilla applies to custom payloads (rule 2) was not measured (open). Parity sends `flare` and `status` presses as raw `key_v1` bytes, including a dropped spectator press.
- **D8 as built** (B413, B415, B420). `@msm/plugin-controls` (id `msm.controls`, in `built-in.ts`, a dependency of the app and the exporters; new projects list it) with `msm:key_bind` (folder `key_bind`, lowering to `msm/<ns>/key_bind/<path>.json` plus lang) and `msm:hud`; 16 codes in `CONTROLS_PROBLEM_CODES` over validators `msm.controls.key-binds`, `msm.controls.hud` and `msm.controls.hud-references`, with plain words in `session/plain-problems.ts`. Clash rule: a vanilla clash when `vanillaKeys[c]` equals the key and `c` is not in `vanillaCombinations` (the `key.debug.*` F3 combinations); a project key on a runtime key warns when the project has a vehicle. Templates (category "Controls and HUD") `msm_key_bind_dash` (Z) and `msm_key_bind_ability` (K). The Key bind Studio maps `KeyboardEvent.code` to the HID usage, then `keyboardNamesByCode`; mouse button n is code n+1; names are never reverse-mapped.
- **D9 as built** (B410). Plugin API 1.16.0 `TargetFacts.controls?: ControlFacts { keyNames (255), unboundKey, vanillaKeys (62), vanillaCombinations (21), keyboardNamesByCode (0..400), mouseNamesByCode (0..10), runtimeKeys }`, generated into `packages/targets/mc-26.{3,4}/src/controls.ts` from the dumps and compared with them by each target's test; the AI's `target_facts` leaves out the two code tables.
- **D10 as built** (B415). The eject warns `export.not-in-eject` once per key bind, HUD element and vehicle; vanilla pack exports carry `controls.needs-jar` and `vehicles.needs-jar` (infos made in `project-session.ts`).
- **Tests.** `MsmKeyBindGameTest` (14), JUnit `KeyBindParserTest`, `InputGuardTest`, `RuntimeKeysTest`; the client GameTest `MsmControlsClientGameTest` presses a project key on a dedicated server and sees its function run, on both versions (a disconnect makes `TestDedicatedServerConnection.close()` throw; the client window is 854 by 480); e2e `controls-path` (Dash key captured as J, because G clashes with "Quick actions" in 26.3).
- **Open follow-ups.** The release on focus loss and vanilla's flood limit for custom payloads (D4, D7 rule 2) are unmeasured; `KeyBindStudio.tsx` header comment; D11's list stands (see [coverage audit](../COVERAGE-AUDIT.md) B15).

## Status

Accepted with findings at close B432 (2026-11-15; unreleased, awaiting the user's in-game checks), with the defaults below; the user may still veto them. Vetoable defaults: one channel with the version in the payload id (D1); payloads carrying only an id and a bit (D2); the kind name `msm:key_bind`, its fields and defaults (`key.keyboard.unknown` for no key, a category id with the lang key `key.category.<ns>.<category>`, default `keys`) (D3); releases when a screen opens or the player leaves, and no release events on death or disconnect (D4); the runtime's own vehicle keys R, V, H and Left Alt with their ids, which scripts do not see (D5); the trigger names (D6); 20 packets a second with a burst of 40, dropping rather than kicking, and key events at function permission level (D7); the plugin name `@msm/plugin-controls` and Very easy showing keys only through Rules (D8); leaving key binds, HUD and vehicles out of the eject until B142 (D10); deferring custom screens, block entity renderers, the portal overlay and particle trails (D11).
