# Plan: custom particles

Working plan for coverage audit backlog B14 (custom particle types and richer particle options; rows "Particle definitions (`particles/*.json`)" and "Particle types", limits L3, L13, L16). Written 2026-11-14 by the orchestrator. Decisions live in [ADR 0080](adr/0080-custom-particle-types.md) (the kind `msm:particle` as option-less types, pictures, registration, the client particle and provider, options objects, `motion` and `force`, `msm:ambient_particles`, versions, plugin API 1.14.0, lowering, validators, vanilla pack safety, eject) and [ADR 0081](adr/0081-particle-studio-flows-and-tests.md) (Particle Studio, editing where particles are used, the Particle flow, templates, example, tests including a client GameTest attempt, guide and AI helper), both Proposed. This file holds the fact table, the rules, the briefs B346–B361 in eight waves, the vanilla pack safety interaction, the limits and an empty "Notes from implementation". It is deleted at close (history goes to `DEVLOG.md`, the fact table and limits into ADR 0080's findings, the other findings into their ADRs).

What B14 leaves to B15 (client side for power users): key binds, HUD, screens, block entity renderers, a portal overlay of our own, client scripts, and any client particle logic beyond ADR 0080 D4 (trails on held or thrown items, entity-attached emitters; ADR 0080 D12).

## Rules for every brief

- Read root `CLAUDE.md`, the scoped `CLAUDE.md` of the area, the latest `docs/DEVLOG.md` entry, this plan's "Notes from implementation" and the ADRs named in the brief. Version facts live only in `packages/targets`; engine-mod uses Mojang names, Java 25, Fabric events over Mixins (no Mixin is planned in this batch); a 26.3/26.4 difference goes behind a seam in `engine-mod/src/mc/<mc>/` (every version implements every seam). None is expected: never touch the members of F6, F9's `Layer` constructors and accessors, `uvFlip`, F10's `size()` or `ParticleLimit`.
- **Clean room.** Vanilla classes are read with `javap` for their rules and signatures; no vanilla method body is copied or transcribed. `MsmParticle`, `ParticleLook` and `particle-sim.ts` are written from ADR 0080 D1 and D4.
- **Worktrees.** Each executor works in its own git worktree in the scratchpad (`<scratchpad>/wt-B<nnn>`, a unique name, from the commit the orchestrator names), builds and tests there (parallel Gradle builds in one checkout collide), commits on its own branch, does not push and does not merge. Commits carry no `Co-Authored-By`, `Claude-Session` or other credit lines and are authored as the user (HANDOFF).
- **Disk.** Check `df -h` before building (the disk has filled before: old worktrees took about 18 GB). Delete your worktree's build outputs before reporting (`engine-mod/build`, `engine-mod/parity/build`, `engine-mod/.gradle`, `app/out`, `app/dist`, `node_modules/.cache`, scratch servers and ejected projects); the orchestrator removes the worktree after merging.
- **Stubs first.** Every new GameTest and parity class of the batch is registered in Wave 0 (B346) as an empty class, so no later brief edits `engine-mod/src/gametest/resources/fabric.mod.json` or `engine-mod/parity/src/main/resources/fabric.mod.json`.
- **One owner per shared file per wave.** Parallel briefs in one wave never touch the same file; ownership is listed per brief. A brief that needs a file owned by another brief of the same wave stops and reports. Registration lines (a plugin's `index.ts` lists, `MsmRuntime` and `MsmRuntimeClient` calls, `studios.tsx`) belong to the brief that owns the file in that wave.
- **Notes.** Each executor ends its report with "Notes for the plan": new facts, names, signatures, labels and test ids, and what a later brief must change, with its brief number. The orchestrator appends them to "Notes from implementation" below when it merges the brief; executors do not edit this file. Each executor appends one DEVLOG entry in its commit (the orchestrator resolves append conflicts at merge).
- **Format moves in order.** A format change moves the mcdoc, the corpus (`packages/schemas/mcdoc/msm/conformance/definition/`, new files prefixed `particle-`, `action-particle-` and `ambient-particles-`), the runtime Codecs and the generator together across ordered waves; each brief keeps its own package green. Run `node tools/build-msm-mcdoc/index.ts --check` after any mcdoc change. Until the Codec lands, `ConformanceCorpusTest`'s `PENDING` list skips the new prefixes (B347 adds all three, B350 removes `particle-`, B352 removes the other two).
- **Exit criteria** always include, for the touched packages: `pnpm lint`, `pnpm typecheck` and the package tests; for engine-mod `JAVA_HOME=/root/jdk/jdk-25.0.5+8 ./gradlew build` (26.3), `./gradlew build -Pmc=26.4` and `./gradlew build -PwithoutGeckolib` (JUnit and the GameTests run in each). App and library briefs also run `pnpm build` and `node tools/check-size/index.ts` and report `app.asar` (26.9 MB of 32 MB at the start; stop and report above 31 MB: the next reserve is gzip, ADR 0079 D4). A runtime behaviour without a GameTest (or, for client code, a JUnit test or the golden) is refused at review; a parity-visible behaviour without a parity test is refused at B359's review. No brief adds a dependency except B356 (Fabric's client GameTest module comes with Fabric API; no lockfile change in this batch).
- Executors: Opus (`claude-opus-5-5`) at medium effort; Sonnet (`claude-sonnet-5-5`) for B346 and B360. A stuck brief is rerun on Opus at high effort.

## Vanilla pack safety (ADR 0066)

- `particle_type` joins the mod-only registries (ADR 0066 D2; `RUNTIME_REGISTRIES`, B351). Consequences under the existing rules: a biome (`worldgen`) or an enchantment naming a project particle is left out with `export.mod-only-reference` (D3, fatal folders); a function running `particle <ns>:<id>` or `execute … run particle …` is kept with `export.mod-only-function` (D5: a vanilla server drops only that function, as for any unknown id in a command; the brief's "left out" is ADR 0066's "kept and warned" for functions, which loads more of the pack); a function tag naming that function gets an optional entry (D4).
- `dimension_type` and `timeline` were "not probed" by ADR 0066 because no field could name a mod-only id; environment attributes can now name a particle (F19). B346 probes both on vanilla servers of both targets; B351 adds them to `FATAL_DATA_FOLDERS` only if a whole pack fails, and records the outcome in ADR 0066's table at close.
- The particle definition (`msm/`), the `spawn_particle` action, `msm:ambient_particles` and scripts never reach a vanilla pack. The vanilla resource pack keeps project descriptions and pictures: a description for an unknown type is ignored by the client (F14), so nothing breaks; a `minecraft:particle` retexture of a vanilla particle works in a plain resource pack.
- The library flow writes no function, so the CI library vanilla server check needs no new allowance; the example and the flow's packs are checked automatically on both targets.

## Limits found

The hard limits of this batch, in the style of the coverage audit's L rows; they go into ADR 0080's findings and the audit at close.

| # | Limit | Why | What users see | Mitigation in this batch |
|---|---|---|---|---|
| K1 | **Project particles need the Fabric mod jar on client and server.** | A particle type is a registry entry with client code (a provider); packs cannot add either (L1, L3); registry sync refuses clients without the mod. | Vanilla packs have no project particles; a resource pack can only retexture vanilla's. | `minecraft:particle` kind for retexturing; validators and the guide say so. |
| K2 | **Behaviour is fixed per type.** | Option-less types (ADR 0080 D1) carry nothing per spawn but position, velocity and count. | No per-spawn colour or size for a project particle. | Make another particle element; vanilla dust, block and item particles take per-spawn options. |
| K3 | **Definitions are read separately on each side.** | The client reads its own jar's definition. | A client and server with different jars may disagree on looks. | Guide: update client and server together. |
| K4 | **Drawing is checked automatically only if B356 finds a client route.** | No client run in CI so far (L16). | Looks and feel reach the user first. | The `ParticleLook` golden ties runtime and preview; B356's attempt; the README checklist. |
| K5 | **Ambient block particles are client-only.** | `animateTick` runs only on the client (F22). | None, but parity cannot see them. | The spawn plan is tested on the server with a seeded random. |
| K6 | **Distance and the Particles option apply.** | The client culls beyond 32 blocks and under Minimal (F17). | Far particles vanish. | `always_show` per type, `force` per spawn. |
| K7 | **Fixed at start.** | Registry freeze (L1). | New particle types and knob changes need a restart; pictures and descriptions reload with resource packs (F3 + T). | Documented. |
| K8 | **Camera-facing single quads only.** | `SingleQuadParticle` (ADR 0080 D12). | No trails, ribbons, models, lit or shaded particles, no light cast on blocks. | Documented; later work. |
| K9 | **Items and mobs show particles only through triggers.** | No client hook for held or thrown items in this batch (B15). | No held-item shimmer or throwable trail drawn by the client; server-sent bursts work. | `while_held`, `on_use`, `msm:on_tick` with `spawn_particle`. |
| K10 | **A particle without pictures shows nothing.** | The provider refuses an empty sprite set rather than crash the client (F17). | Nothing appears; one client warning. | App-reported missing pictures; vanilla's "Missing particle sprites" line. |
| K11 | **Options objects are checked late in the runtime.** | Block and item options name registry entries that do not exist at init. | A broken object is an error at server start, not at load. | Validators check them at edit time; the eject refuses them. |
| K12 | **Vanilla data packs leave out or warn.** | ADR 0066. | Biomes and enchantments naming project particles are left out; functions are kept and skipped by vanilla servers. | Warnings name the file and the id. |
| K13 | **Network cost.** | Each `spawn_particle` with `motion` sends one packet per particle per player. | Many-particle bursts with `motion` cost bandwidth. | `count` cap 1000; the guide recommends `spread` bursts. |
| K14 | **`BlockComponents` has one field left.** | ADR 0074 C18; `msm:ambient_particles` is the 15th. | None. | The next block component needs a nested group. |
| K15 | **Eject on 26.3 only.** | Audit L10. | Particles in ejected projects only for 26.3. | As every runtime feature. |
| K16 | **Scripts run on the server only.** | L2. | Scripts send particles; they cannot draw or move them on the client. | `world.spawnParticle` with options objects. |
