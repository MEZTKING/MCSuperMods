## Decisions (ADR drafts)

- [ADR 0031](adr/0031-rhino-runtime-and-typescript-es5-scripts.md): Rhino 1.9.2 nested in `msm_runtime` through Loom `include`; scripts transpiled by **TypeScript `transpileModule` to ES5 CommonJS in the Electron main process, not esbuild** (Rhino cannot parse classes, for-of, call spread or async, and esbuild cannot lower them); sandbox (safe standard objects, a deny-all `ClassShutter`, interpreted mode, stack depth 1000, a 2000 ms wall-clock budget per call through the instruction observer); lifecycle (load on `SERVER_STARTING`, reload on `END_DATA_PACK_RELOAD`); error reporting and the `[msm_runtime] loaded S script(s); E error(s)` line; the validation gate (`language: 'typescript'`, syntax errors block, type errors warn); the renderer size budget rises to 16 MB for the lazy Monaco TypeScript worker. Closes DESIGN Open Question 2 and supersedes the esbuild half of ADR 0003.
- [ADR 0032](adr/0032-script-api-v1-and-typings.md): script API v1 described once in `packages/plugins/scripting/api/script-api-v1.json`; generated `msm-runtime.d.ts` (golden) and a JUnit contract test on the runtime side; the API surface (`msm.log`, `msm.events.on` over nine Fabric-backed events, `msm.actions.define`, `msm.schedule`, `World`, `Entity`, `Player`, `Pos`); the `msm:script` element (`{ lines }`, lowered to `msm/<ns>/script/<path>.ts`, transpiled to `.js` by the content-jar exporter); the `run_script` action (format 1 addition); typings written to `<project>/.msm/msm-runtime.d.ts`.
- [ADR 0033](adr/0033-java-project-eject-v1.md): the `java-project` exporter: scope (blocks, items, entities with GeckoLib, every action; **scripts are not ejected** and are reported), the generated layout, the Java generator as a **target fact** (`Target.javaProject`), the Gradle wrapper served by the host from `engine-mod/gradle/wrapper/`, determinism and the empty-folder rule, CI builds of the ejected `sample-mod` and `sample-mob`, and behaviour-parity GameTests (`engine-mod/parity/`, a black-box GameTest mod run by `tools/run-fabric-server --gametest` on a production server against the content jar and against the ejected jar).
- [ADR 0034](adr/0034-plugin-api-0.8.md): plugin API 0.8.0: `FabricFacts.gradle`, `Target.javaProject?: JavaProjectGenerator` (`JavaProjectInput`, `DefinitionInput`, `GeneratedFile`), the `typescript` output language; every built-in plugin moves to `^0.8.0`.

Fallbacks recorded for completeness: had TypeScript's ES5 output failed in Rhino, Phase 6 would have moved to GraalJS (ADR 0003's documented fallback) at a 50 MB cost; it is not needed. If B131 finds that production-server GameTests cannot run, parity drops to the server tool's registration-line check on both jars plus the runtime's own GameTests, and the ROADMAP deliverable is reworded at close.

### B130 — Scripting spike (engine-mod)

**Owns:** `engine-mod/` except `engine-mod/parity/` (build files, `src/main`, `src/gametest`, `src/test`). Also appends findings to the "Status" section of ADR 0031 (results only; do not rewrite the decisions).

**Purpose:** prove on 26.3, before any editor work, that `msm_runtime` can nest Rhino 1.9.2, load an ES5 CommonJS script from a content jar's `msm/<ns>/script/`, run it in the sandbox of ADR 0031 D3, bridge three Fabric events to it, and that GameTests can observe it; settle the unverified items of the facts table that concern the runtime.

**Scope:**

1. Gradle: `rhino_version=1.9.2` in `gradle.properties`; `implementation("org.mozilla:rhino:${rhino_version}")` and `include("org.mozilla:rhino:${rhino_version}")` in `build.gradle.kts`. Check the built jar: `META-INF/jars/rhino-1.9.2.jar` (or whatever Loom names it) is nested and `fabric.mod.json` lists it in `jars`; record the generated nested `fabric.mod.json` (its id) in the report. If `include` refuses a plain library in the non-remapping variant, try `include` on a `files(...)` dependency, then report; do not move to Shadow in this brief.
2. Copy Rhino's `LICENSE.txt` (MPL 2.0, from `https://raw.githubusercontent.com/mozilla/rhino/Rhino1_9_2_Release/LICENSE.txt`) to `src/main/resources/META-INF/licenses/rhino-LICENSE.txt`.
3. `scripting/` package (spike quality, replaced by B133): `MsmContextFactory` (ADR 0031 D3 settings: `VERSION_ES6`, interpreted mode, threshold 10,000, depth 1000, deny-all `ClassShutter`, 2000 ms wall-clock budget measured from the start of each top-level call, `ScriptTimeout extends Error`), `ScriptScanner` (every mod container, `msm/<ns>/script/**/*.js`, id `<ns>:<path>`), `ScriptHost` (one per server; `initSafeStandardObjects`; defines `msm` with `log.info/warn/error`, `events.on(name, fn)` for `block.interact`, `block.break`, `server.tick`, and `schedule(ticks, fn)`; `require` resolving only `msm:runtime` to `{ msm }`; `module`/`exports` per script; loads scripts on `SERVER_STARTING`; `processMicrotasks()` after every handler call), the three event bridges (`UseBlockCallback` with `cancel()` returning `InteractionResult.FAIL`, `PlayerBlockBreakEvents.BEFORE` returning `false` on cancel, `ServerTickEvents.END_SERVER_TICK`), wrappers `ScriptWorld` (`setBlock`, `getBlock`) and `ScriptPlayer` (`name`, `give`), `Pos`.
4. GameTest mod resources: `msm/msm_spike/script/glow.js` written **by hand as ES5 CommonJS** in the shape TypeScript emits (`"use strict"; var runtime = require("msm:runtime"); ...`): on `block.interact` of `msm_spike:glow_ore` sets the block above to `minecraft:glowstone` and gives the player one `msm_spike:shard`, then `cancel()`; on `block.break` of glowstone cancels; a `server.tick` handler counting ticks into `msm.log.info` every 100 ticks; a `schedule(5, ...)` call; one handler that throws; one script `msm/msm_spike/script/broken.js` with a syntax error; one script `loop.js` whose `block.interact` handler loops for ever on `minecraft:bedrock` interaction.
5. GameTests (`gametest/MsmScriptSpikeGameTest.java`): the log line `[msm_runtime] loaded 3 script(s); 1 error(s)` (through a `ScriptHost` report accessor); interacting with a mock survival player on `glow_ore` places glowstone above, gives one shard and returns `FAIL` (vanilla use did not run: assert the block's own `msm:on_interact` event did **not** fire via `EventRunner.setListener`); breaking glowstone is cancelled (block still there); the throwing handler leaves the server running and is logged once; the endless loop is aborted within 3 s and the test continues; `schedule` runs after the given ticks; a regular expression with a named group works inside a script (checks `ServiceLoader` for `RegExpLoader` from the nested jar); `typeof java` is `undefined` inside a script.
6. Microbenchmark in a GameTest: 10,000 calls of a trivial `server.tick`-style handler; report the mean time per call.
7. Report: the Loom `include` outcome and the nested file name, the ServiceLoader outcome, the `InteractionResult` that stops both hands on 26.3, the benchmark, whether `SERVER_STARTING` is early enough on the GameTest server, and the passing GameTest log lines.

**Acceptance:** `./gradlew build` passes with the Phase 5 78 JUnit tests and 38 GameTests plus at least the eight spike GameTests; the built `msm_runtime-0.5.0.jar` (version unchanged in this brief) nests Rhino and contains no `org/mozilla` classes of its own; `fabric.mod.json` of the runtime has no new hard dependency besides the nested jar entry; ADR 0031 "Status" lists the findings; a DEVLOG entry.

## Risks

- **Rhino nesting under the non-remapping Loom** is the one thing B130 must settle first; the Shadow fallback is cheap but changes the jar layout. The `ServiceLoader` check for `RegExpLoader` is part of the spike because a silent regex failure would surface only in users' scripts.
- **TypeScript 7 drops the ES5 target.** The transpiler's TypeScript is pinned to 6.x by the catalog; moving the repository's `tsc` to 7 later must keep a 6.x copy for the transpiler (or Rhino 2.0 must parse ES2015 by then). ADR 0031 records the trigger.
- **Interpreted Rhino on the server thread.** `server.tick` handlers run every tick; B130's benchmark decides whether the event ships. The 2 s budget protects the server, not the frame rate; the guide says so.
- **Two implementations of every component** (runtime Java, generated Java). The parity GameTests are the guard; a component added without a parity test is the thing to refuse at review.
- **CI time.** Two ejected Gradle builds and four production-server GameTest runs add minutes; B139 reports timings and trims artefacts first, parity runs last.
- **Size budgets.** The TypeScript worker (about 7 MB) and `typescript` in main (about 3.6 MB) are the largest additions since Monaco itself; both are lazy. The asar budget of 25 MB is expected to hold at about 17 MB; B141 records the real numbers.
- **Counts:** 59 kinds, 116 templates, 13 starters, 69 examples are targets, not facts; B141 counts from the plugins.
