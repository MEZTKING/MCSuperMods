## Rules for every brief

- Read root `CLAUDE.md`, the scoped `CLAUDE.md` of the area, the latest `docs/DEVLOG.md` entry, this plan's "Notes from implementation" and the ADRs named in the brief. Version facts live only in `packages/targets`; engine-mod uses Mojang names, Java 25, Fabric events over Mixins (no Mixin is planned in this batch); a 26.3/26.4 difference goes behind a seam in `engine-mod/src/mc/<mc>/` (every version implements every seam). The fact table's "never override or call" members stay untouched.
- A format change moves the mcdoc, the corpus (`packages/schemas/mcdoc/msm/conformance/definition/`, new files prefixed `entity-mx-`), the runtime Codecs and the generator together; the briefs split them into ordered waves, and each brief keeps its own package green. Run `node tools/build-msm-mcdoc/index.ts --check` after any mcdoc change.
- Commits carry no `Co-Authored-By`, `Claude-Session` or other credit lines. Each executor works in its own worktree folder with a unique name in the scratchpad (`wt-B<nnn>`), commits on its branch, does not push, and appends a DEVLOG entry. New facts or names a later brief needs go into "Notes from implementation" below (append only).
- Exit criteria always include, for the touched packages: `pnpm lint`, `pnpm typecheck`, the package tests; for engine-mod `JAVA_HOME=/root/jdk/jdk-25.0.5+8 ./gradlew build` (26.3), `./gradlew build -Pmc=26.4` and `./gradlew build -PwithoutGeckolib` (all run JUnit and the GameTests). App and library briefs also run `pnpm build` and `node tools/check-size/index.ts` (asar budget, audit L15). A runtime component without a GameTest is refused at review; a parity-visible behaviour without a parity test is refused at the parity brief's review.
- Parallel briefs in one wave never touch the same file; ownership is listed per brief. A brief that needs a file owned by another brief in the same wave stops and reports.
- Executors: Opus (`claude-opus-5-5`) at medium effort; Sonnet (`claude-sonnet-5-5`) for B305 and B307. Reruns of a stuck brief go to Opus at high effort.

Overrides whose signatures differ between versions (F2, F6, F9) are not added.
- **Exit criteria:** every existing GameTest (239 per variant) and JUnit test passes on 26.3, 26.3 without GeckoLib and 26.4; no behaviour change (no corpus or golden changes); the DEVLOG entry lists the hook methods per module with signatures, copied into "Notes from implementation".
- **Out of scope:** any new behaviour; Codecs (B286).

## Vanilla pack safety (ADR 0066)

- Every entity id is mod-only, so nothing that names one stays in a vanilla data pack. New in this batch: the `#minecraft:can_equip_saddle` entry written by lowering for saddled mounts; ADR 0066 already turns entries of mod-only ids into `required: false`, so the vanilla pack loads on a vanilla server and simply does not list the mob. B288 tests it; the CI library vanilla server check covers the new starters and examples (B299) on both targets.
- Breeding, taming and tempting items, projectiles and variant biomes live in the `msm/` definition, never in vanilla data. Loot tables of mobs name only items; a loot table naming a project item is left out of the vanilla pack by the existing rule.
- Nothing in this batch needs a new rule or code path in `@msm/exporters`' mod-only check.

## Limits found

These are the hard limits of this batch, in the style of the coverage audit's L and S rows; they go into the ADR findings and the audit at close.

| # | Limit | Why | What users see | Mitigation in this batch |
|---|---|---|---|---|
| M1 | **Ridden mobs are moved by the rider's client.** | A player-controlled vehicle is client-authoritative in vanilla; the server receives its position (F9). | Steering, speed and jumping run the rider's copy of the definition; a server and a client with different content jar versions disagree silently. The server's vehicle movement check (threshold verify at implementation) may snap very fast mounts back. | Same jar on both sides (Fabric registry sync already requires the ids); steering is an in-game check (B305); `speed` capped at 5x in the validator range. |
| M2 | **Server-side motion of a ridden mob is overwritten by the rider's client.** | Same class as the velocity problem (ADR 0052, audit 2.3). | `launch`, teleports or knockback applied to a ridden mount may be lost or jitter. | Recorded; in-game check of `launch` on a ridden mount; a vehicle sync like ADR 0052's is a follow-up if it fails. |
| M3 | **One triggered animation per tick in the vanilla renderer.** | `DATA_ANIM` is synched data: the client sees the last value of a tick. | Two `play_animation`s in one tick play only the second (GeckoLib plays both through its own packets). | Documented in the guide. |
| M4 | **Definitions are read separately on each side.** | Registry sync compares ids, not definition content. | A modpack that updates only the server jar shows wrong variant textures, renderer states or steering. | Guide note: update client and server together. |
| M5 | **No client test route.** | No OpenGL or Vulkan in the container (audit L16). | Drawing, animation feel and textures reach the user first. | Pure readers and the cross-language vertex golden (B285), animation conversion tests (B295), in-game checklist (B305). |
| M6 | **The vanilla renderer is a subset of GeckoLib.** | Vanilla keyframes have no Molang, easings or keyframe events (F12). | On 26.4 (and `renderer: vanilla`), Molang plays as 0, easings as linear; sound and particle keyframes are silent. | `entities.vanilla-renderer-subset` warning; presets stay inside the subset. |
