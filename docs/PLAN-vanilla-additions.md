## 2. Decisions (ADR drafts)

### 2.1 ADR 0060 (draft): Adding to vanilla content

- **D1 Route per addition, chosen by V1–V6.** Features and spawns into vanilla biomes: runtime kind over Fabric `BiomeModifications`. Extra drops: runtime kind over `LootTableEvents.MODIFY`. Fuel and composting: vanilla components on the project's own items, no runtime code. Trades: vanilla data kinds and a tag, no runtime code, valid in vanilla packs. No mixin anywhere.
- **D2 `msm:biome_addition`** (kind in `@msm/plugin-blocks-items`, folder `biome_addition`, lowered to `msm/<ns>/biome_addition/<path>.json`): `{ format: 1, biomes: [#[id(registry="worldgen/biome", tags="allowed")] string] @ 1.., features?: [{ feature: #[id="worldgen/placed_feature"] string, step: <the eleven steps in lower case> }], spawns?: [{ entity: #[id="entity_type"] string, category: MobCategory, weight: int @ 1.., min_group, max_group: int @ 1.. }] }`, at least one of `features` and `spawns`. The runtime registers one `BiomeModifications` call per entry at initialisation with the selector code of V2 (moved into a shared helper). Unknown biome, tag, placed feature or entity type: a late warning after start, as for spawns today. Frozen per world load (V1); only new chunks get the features; the guide says so.
- **D3 `msm:loot_addition`** (same plugin, folder `loot_addition`): `{ format: 1, tables: [#[id="loot_table"] string] @ 1.., pools: [<vanilla loot pool>] @ 1.. }`. The runtime keeps each pool as JSON and decodes it with `LootPool.CODEC` over the `HolderLookup.Provider` of every `MODIFY` call (project items, enchantments and predicates resolve; additions survive `/reload` without doubling). Applied when `source.isBuiltin()`: a world data pack that replaces the table wins, as Fabric recommends. A pool that fails to decode is one logged error per load and is skipped.
- **D4 Fuel and composting.** Element-only fields on `msm:item` and on the block's `item`: `fuel?: { burn_seconds: float @ 0.05.. }` and `compost?: ("30%" | "50%" | "65%" | "85%" | "100%")`, lowered to `minecraft:cooking_fuel { burn_time: ticks }` and `minecraft:compostable { layers: <provider id> }` inside `msm:components` (the editor-only pattern of ADR 0059 D2). The chance-to-provider table is a target fact (read the five files at implementation). The definition gains `BlockItem.components?` with the same passthrough as items. No friendly field for `brewing_fuel` (passthrough only).
- **D5 Trades.** `@msm/plugin-datapack` gains generic kinds `minecraft:villager_trade` and `minecraft:trade_set` and the tag registry `villager_trade`; both targets gain the two data folders. "Add to a villager" is a tag element `minecraft:<profession>/level_<n>` (or `wandering_trader/common`); the existing tag merge keeps `replace: false`. The guide states V6's limit (a candidate among `amount`), and that a guaranteed trade means a project `trade_set` override, which replaces vanilla's.
- **D6 Custom ore generates.** The Custom ore and Scripted ore starters add a `worldgen/feature` (ore, targets `#minecraft:stone_ore_replaceables` and `#minecraft:deepslate_ore_replaceables`), a `worldgen/placed_feature` and an `msm:biome_addition` for `#minecraft:is_overworld`, step `underground_ores`. New wizard step "World": generate (on), vein size, veins per chunk, lowest and highest Y. With "generate" off the output equals today's byte for byte.
- **D7 Vanilla packs.** The two `msm:` kinds lower only into the jar's `msm/` layer, as blocks and items do; the starter text and the guide say that world generation and extra drops need the Fabric mod export. Trades and the feature files are plain data and stay in the data pack.
- **D8 Plugin API 1.8.0 (additive).** `DataFolderKey` gains `villager_trade`, `trade_set`; `JavaProjectInput.biomeAdditions?`, `lootAdditions?: DefinitionInput[]` ("Since 1.8.0", absent means empty); `TargetFacts.items.compostProviders?: Record<string, string>`.
- **D9 Java eject (26.3).** `ModWorldgen.java` (the same `BiomeModifications` calls) and `ModLoot.java` (the pools as embedded JSON text decoded in a `MODIFY` listener, the same source rule); fuel and compost need nothing (components).
- **D10 Versions.** Shared runtime code only; no seam. Nothing uses `fabric-content-registries-v0` (V5).
- **D11 Deferred, stated so nobody expects them:** flammable blocks, strip, wax and oxidise pairs (the Fabric module is missing on 26.4, V5: needs a seam or a mixin), fuel or compost values on *vanilla* items (`DefaultItemComponentEvents`), custom compost chances (a `context_int_provider` kind, audit B11), removing vanilla features or spawns, carvers, new professions and POI types, a bespoke Loot Studio.

### 2.2 ADR 0061 (draft): More triggers

- **D1 Item components** (each `{ event }` plus the fields named): `msm:on_hit` (`postHurtEnemy`; self is the attacker, player or mob; `other` the entity hit); `msm:on_use_on_block` (`useOn`; `cooldown_ticks?`; `base` and `block` are the clicked block; the result and cooldown are applied on both sides as `msm:on_use` does, the event on the server; an error together with `msm:throwable`-style right-click owners is not needed, since `useOn` runs before `use`); `msm:while_held` (`interval_ticks?: int @ 5..` default 20, `hand?: ("main" | "off" | "either")`); `msm:while_worn` (`interval_ticks?` as above; fires in the armour slot of `msm:armor`, an error without it).
- **D2 Block components:** `msm:on_break` (`playerWillDestroy`, any game mode; self is the player); `msm:on_place` (`setPlacedBy`; self is the placer when there is one); `msm:on_random_tick` (`chance?: float @ 0..1` default 1; `randomTicks()` only when present); `msm:on_entity_inside` (`cooldown_ticks?: int @ 5..` default 20, per entity, actor rule of ADR 0058 D1; fires only for blocks an entity can be inside, so the validator warns unless `msm:shape` is non-full or walk-through).
- **D3 Entity components:** `msm:on_tick` (`interval_ticks?: int @ 5..` default 20; `customServerAiStep`) and `msm:on_spawn` (`finalizeSpawn`: natural, egg, spawner; not on chunk load).
- **D4 Tick cost limits.** Intervals are at least 5 ticks; firings are staggered by entity id; one shared counter stops tick-trigger firings (`while_held`, `while_worn`, `on_tick`, `on_entity_inside`, `on_random_tick`) at 2,000 per server tick and logs once a minute when it skipped any; the per-entity cooldown map of `msm:on_step` is generalised and bounded. Validator info `blocks-items.fast-tick-trigger` when an interval under 20 runs `run_function` or `run_script`.
- **D5 No script API change.** Scripts reach every trigger through `run_script` (`ActionEvent` already carries `player`, `entity`, `other`, `block`).
- **D6 Eject and versions.** The 26.3 generator mirrors each override; shared runtime code (V9–V11), no seam. Deferred: `on_crafted`, block neighbour-change, entity `on_death` beyond the existing triggers, client-side triggers.

### 2.3 ADR 0062 (draft): Persistent script data (amends ADR 0032; closes L4)

- **D1 API, additive.** Type `DataStore`: `get(key): unknown`, `set(key, value): void`, `remove(key): boolean`, `has(key): boolean`, `keys(): string[]`. `Entity.data: DataStore` (so `Player.data`) and `msm.storage: DataStore`. Values are JSON values (string, finite number, boolean, null, arrays, plain objects), copied in and out; anything else is a `TypeError`.
- **D2 Scope.** Both stores are per script namespace: a script sees only its own namespace's keys, so two mods never clash.
- **D3 Storage.** Fabric data attachments (V12): one persistent attachment `msm_runtime:script_data` of type `Map<namespace, JSON text>`, `copyOnDeath()`, on entities; world storage is the same type as a global attachment (or on the overworld level if the server does not provide one: executor's finding goes into the ADR). JSON text gives an exact round trip and is readable with `/data get`. Not synced to clients.
- **D4 Limits.** Key at most 64 characters; 16 KiB per namespace per entity, 1 MiB per namespace for `msm.storage`; over the limit is a script error and the old value stays.
- **D5 Lifetime.** Survives `/reload`, restart, death and dimension change. `msm.schedule` stays unsaved; the guide shows rebuilding timers from storage in `server.started`.
- **D6 Tests and parity.** Scripts are not ejected, so parity is content-jar only (`SampleScriptParityTest`, ADR 0058 D4). A real restart is tested by running `tools/run-fabric-server` twice on one world folder.
- **D7 Deferred:** no-code conditions on stored data (actions have no conditions yet), block or chunk data, client sync, data on items (vanilla `custom_data` passthrough covers it).

**Creator, AI helper and eject, in one place.** Creator: Custom ore gains the "World" step (D6); new flows "Villager trade" (profession, level, price, product) and "Extra drop" (mob, block or chest table; item, count, chance, player kill only); no Creator questions for triggers (Studios only). AI helper: one prompt paragraph per part, catalogue stays at 22 tools. Eject: ADR 0060 D9 and 0061 D6; nothing for Part C.

## 4. What needs the user

Defaults the plan uses unless the user says otherwise:

1. **Additions never override:** a world data pack that replaces a loot table wins over an extra drop (ADR 0060 D3). Default: as written.
2. **A new villager trade is a candidate, not a guarantee** (V6); guaranteeing it would override vanilla's trade set. Default: accept and document.
3. **Custom ore generates by default** in new projects; existing projects are unchanged until the flow is reopened. Default: on.
4. **Trigger limits:** 5-tick minimum interval and 2,000 tick firings per server tick (ADR 0061 D4). Default: as written.
5. **Script data limits** of 16 KiB per entity and 1 MiB per world, per namespace (ADR 0062 D4). Default: as written.
6. **Names:** kinds `msm:biome_addition` and `msm:loot_addition`, Studio labels "World addition" and "Extra drops". Default: as written, vetoable.
7. **Deferred** (ADR 0060 D11, 0061 D6, 0062 D7): flammability and block pairs, values on vanilla items, custom compost chances, `on_crafted`, no-code conditions on stored data. Default: accept; they stay in the audit backlog.

In-game checks only the user can do: the ore appears underground in a **new** world (and not in already generated chunks); a zombie drops the extra item; a furnace burns the fuel item for the stated time and a composter takes the compostable; a villager of the chosen profession offers the trade at some point; each trigger feels right in play (on-hit, use on a block without a ghost placement, held and worn effects starting and stopping when the item is moved); a counter in `player.data` survives quitting and reopening the world, death and a trip through a portal.
