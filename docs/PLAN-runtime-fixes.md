## 2. Decisions (ADR drafts)

### 2.1 ADR 0057 (draft): Project sound events and mob sounds

- **D1 Registration.** At initialisation, before effects, `msm_runtime` registers one `SoundEvent.createVariableRangeEvent(<ns>:<key>)` for every event key of every `assets/<ns>/sounds.json` found in a mod container that has an `msm/` folder or declares a dependency on `msm_runtime` (R3; hand-written mods opt in either way). Keys already registered and the namespace `minecraft` are skipped silently (overrides of vanilla sounds stay resource-pack only); an invalid id or unreadable file is a warning. Mods and keys are visited in sorted order so client and server register alike. `LoadReport` gains `sounds`; the start-up log line names the count. Nothing else in the runtime changes: every existing lookup (R2), the passthrough components and `World.playSound` then resolve project sounds. Like every registry entry (audit L1), a new sound key needs a game restart; the audio file and its `sounds.json` entry still reload with the resource pack.
- **D2 No new file format.** The runtime reads the resource pack's own `sounds.json`; there is no `msm/<ns>/sound/` kind and no manifest, so hand-written and exported jars behave the same.
- **D3 App: kind-aware sound ids.** In elements of `msm:*` kinds, project event keys count as `sound_event` ids: offered by completion and the Studios' sound pickers and valid as plain strings anywhere in the element, including `msm:components` passthrough. In vanilla kinds nothing changes: keys stay `weighed_sound_event`, and a bare key stays the error `schema.unregistered-sound-event` asking for `{ "sound_id" }`.
- **D4 Bare strings in vanilla data stay an error in the app**, although R1 makes them valid in a jar with the runtime: the same project also exports as vanilla packs, where the string breaks data pack loading (S2), and the inline form works everywhere. The ADR records that hand-written jars may use the bare form. The Music disc starters keep `{ "sound_id" }`.
- **D5 Java eject.** `ModSounds.java` registers the same ids first in the mod initialiser; the exporter passes them as `JavaProjectInput.soundEvents?: string[]` (plugin API 1.7.0, additive, "Since 1.7.0"), read from the `assets/<ns>/sounds.json` files it already copies.
- **D6 Mob sounds.** The entity definition gains `sounds?: struct { ambient?, hurt?, death?, step?: #[id="sound_event"] string, ambient_interval_ticks?: int @ 20.. }` (default interval: vanilla's). `MsmEntity` overrides the four methods of R5; an unknown id is a warning and the vanilla default stays. Vanilla ids work too. The eject mirrors it. No Creator question in this batch; the Mob Studio gets four pickers.
- **D7 Versions.** Shared code only; no seam expected (R1, R5). A content jar already depends on the exporting app's runtime version, so no extra version floor.

### 2.2 ADR 0058 (draft): Event actors, entity-scoped script commands and cancel resync

- **D1 Step events carry the stepper (S4).** `EventContext` gains a `source` enum (`BLOCK`, `ITEM`, `ENTITY`, `EFFECT`, `THROWN`) and a factory `forBlockStep(level, pos, stepper)`: `player` is the stepper when it is a player; `entity` is the stepper when it is not; `other` is the stepper when it is living. Hence in `msm:on_step` both `self` and `other` mean whoever stepped, for players exactly as before, and `launch` also moves non-living steppers (items, minecarts). Rules made explicit by `source`: block events keep `SoundSource.BLOCKS`; in a block step event `run_function` runs as the stepper (`@s`, its rotation) when there is no player. Entity, effect and thrown-item events keep today's function source (player only); changing those is not part of this batch. `ActionEvent.entity` is the stepping mob (R7; doc string only). The cooldown key gains the dimension (S10). Thin shapes and sneaking still follow vanilla's `stepOn` rules; `on_entity_inside` stays in audit B4.
- **D2 Script commands (S6), additive.** Existing calls keep their behaviour and get an honest doc string ("at the world spawn point, with no `@s`", R8). New: `World.runCommand(command, at?: Pos)` and `World.runFunction(id, at?: Pos)` run at `at`; `Entity.runCommand(command): number` and `Entity.runFunction(id): boolean` run as and at the entity (its level, position and rotation; `@s` is the entity), permission level 2, output suppressed, same return values as the `World` forms; both do nothing and return 0 or `false` for an entity that is not in a server level. Contract `version` stays 1.
- **D3 Cancel resync (S7).** After a script cancels: `block.interact`, `item.use`, `entity.interact` and `block.break` send the player's inventory state (`inventoryMenu.sendAllDataToRemote()`); `block.interact` also sends block updates for the six neighbours of the placement position (clicked position offset by the clicked face), covering two-block placements beyond what vanilla resends (R9); `item.use` also clears a client-predicted cooldown of the used stack if a packet for that exists (verify at implementation; else recorded as a known limit). `block.break` relies on vanilla's own block resend (R9) and adds the block entity packet only if a GameTest shows a gap. `entity.hurt` needs nothing. Resync runs once per cancelled call, only for real `ServerPlayer`s, and is skipped when no script cancelled. No API change; the guide says what a cancel restores.
- **D4 Parity for script behaviour.** Scripts are not ejected (R14), so D2 and D3 get runtime GameTests plus a new content-jar-only parity class `SampleScriptParityTest` (a fifth parity run per version); the "ejected jar" half is not applicable and the plan says so instead of skipping silently.

### 2.3 ADR 0059 (draft): Block shapes and see-through blocks (Part B)

- **D1 Component `msm:shape`** in `BlockComponents` (definition): `boxes?: [[float @ 0..16] @ 6] @ 1..16` (pixel boxes `x1 y1 z1 x2 y2 z2`, as model elements), `collision?: boolean` (true; false is walk-through, as plants), `see_through?: boolean` (default: true when `boxes` is present and is not the single full cube, else false). Absent component: today's full solid cube, byte-identical behaviour.
- **D2 Presets are editor-only** (R13): element field `preset?: ("full" | "slab_bottom" | "slab_top" | "carpet" | "pillar" | "cross" | "custom")` inside the component, stripped in lowering, which writes the preset's `boxes` (`cross`: a 12 by 12 by 16 outline with `collision: false`). `custom` keeps the user's `boxes`. "From the model" is an app action in the Block Studio: it reads the block's model element (following project parents; vanilla parents only for the known `cube*`, `slab`, `cross`, `carpet` families) and writes `custom` boxes in one undoable change. The runtime never reads models.
- **D3 Runtime.** `MsmBlock` precomputes one `VoxelShape` (`Shapes.or` of `Block.box`) and returns it from `getShape`; collision follows it unless `collision` is false (`Properties.noCollision()`). `see_through` sets `noOcclusion()`, light passes (`propagatesSkylightDown` true, shade brightness 1), faces between two blocks of the same definition are skipped (glass rule, R11) and the block never suffocates, blocks view or conducts redstone. The shape is the same for every state (`POWERED` does not change it).
- **D4 Render layer: no code** (R12). Cutout and translucent come from the texture's pixels on both targets. The guide says so; the Studio shows which layer the block's textures give ("solid", "cut-out", "see-through") and a new validator warning `blocks-items.transparent-texture-on-solid-block` fires when a block's model textures have transparent pixels and `see_through` is off (holes into the world), plus `blocks-items.model-not-cube` when a non-`cube*` project model has no `msm:shape`. Texture pixels are app-side knowledge, so the first warning is produced by the app session (as the effect icon warning is), the second by the plugin.
- **D5 Deferred to a later batch (audit B2), stated here so nobody expects them:** rotation and any new state property (facing, axis, half), connecting shapes (fences, walls, panes), stairs, slab stacking (double slabs, waterlogging), doors and trapdoors, crops, per-state shapes and models, block families from one texture. A `slab_bottom` preset here is a fixed half block, not a vanilla slab.
- **D6 Eject and versions.** The 26.3 generator writes the same overrides into the block class; shared runtime code only (R11 on both).
